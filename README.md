# TerraForma

The TerraForma RPG Engine runs browser RPGs. A game is a module: its content (seed data), assets and rules settings, plugged into the engine. The engine provides the rest:
- accounts and security;
- the server calls and live fights over WebSockets;
- the database layer on Postgres, MySQL or SQLite;
- a map-ready world.

[Vanguard Tavern](https://github.com/wilminator/terraforma-vanguard-tavern) is the first game built on it. [terraforma-example-game](https://github.com/wilminator/terraforma-example-game) shows how to build your own.

## Making a game

A game is a Python package that hands the engine a `Game` and builds the app:

```python
from terraforma.app import create_app
from terraforma.game import Game
from terraforma.settings import load_settings

GAME = Game(name="My Game", seed_dir=..., assets_dir=...)

def app():
    return create_app(load_settings(), GAME)
```

To serve it, run `python -m terraforma serve my_game:app`. It checks the settings, brings the database up to date, then serves.

For tests, add `pytest_plugins = ["terraforma.testing"]` to the game's `tests/conftest.py`. Override the `game` fixture there, and `app_client` serves your game on every database under test.

## Add-ons

An add-on is a package that adds content to a game without being a game: a seed folder and an assets folder like the game's (`terraforma.addons.AddOn(key, name, seed_dir, assets_dir)`). The engine never imports one; the game lists the ones it supports and the operator picks which to use. `AddOn` and `Game(addons=...)` are public interfaces (the license exception covers them), and later slices add to them (Rules options, client code).

```python
from terraforma.addons import AddOn

GAME = Game(name="My Game", seed_dir=..., assets_dir=..., addons=(AddOn(key="monster_pack", name="Monster pack", seed_dir=..., assets_dir=...),))
```

```toml
# settings.toml
addons = ["monster_pack"]
```

- **Keys.** An add-on's `key` is 2 to 32 lowercase letters, digits or `_`, starting with a letter. A key in `settings.toml` that the game does not support, or one listed twice, stops the server at start.
- **Layers.** A listed add-on's seed rows and assets are added to the game's: the game's first, then each add-on in the order listed. Seed files are read like a game's (same formats), and the merged seed is checked as one, so an add-on's row may name the game's abilities and the game's may name the add-on's.
- **No collisions.** A seed key used in two layers (`items.json` `herb`), or an asset file name used in two (`goblin.png`), stops the server, naming both owners. An add-on cannot replace what is there: every layer's rows and files stay visible to the engine side by side, and none hides another's. A `job_abilities.json` row follows the same rule: one that gives a job an ability the game's job row, the game's own `job_abilities.json` or another add-on already gives it stops the server, naming both.
- **Licenses.** An add-on's assets folder needs an `ASSETS.md` in the form of the example game's: a table row per file or files (the names in backticks, paths for files in folders) with its source and license. A file not recorded, a row with no source, no license, an unknown or `TBD` one, a non-commercial or no-derivatives one (`CC-BY-NC`, `CC-BY-ND`) or `CC-BY-SA` before 4.0 stops the server. The engine reads what the cell says; whether it is true is for whoever adds the asset. Its animations and color maps are checked like the game's.
- **Serving.** `/assets/` serves a file from the first folder that has it.
- **Components start off.** The rows an add-on brings (abilities, drop tables, items, jobs, job abilities, monsters, personalities, statuses) are loaded **inactive** the first time they are seen, and loading the seed never changes their `active` again. An add-on's seed may only have those kinds of file: maps, dialogs, NPCs and quests can't be switched off yet, and an add-on that has them stops the server.
- **Component states.** Which components are on is the `components` section of the settings document (see Planned and live state), `{"states": {"<add-on>": {"<kind>": {"<row key>": "on"}}}}`. A row not listed is off, which is *no new use*: not offered, sold, dropped, spawned or picked, and what exists keeps working (a hero keeps its job). The states are `on` and `disused` (force disuse, below). The same states always make the same document and hash, so an entry that says what is already true (or an empty add-on or kind) is refused. The check also refuses an on row that needs a row that is off: a job needs its abilities; a monster its abilities, items, equipment, drop table and personality; a drop table its items; an ability or item the status it causes. (A row may need the game's rows, which are always on.) `Components.switch(value, addon, on, kind=None, section=None)` returns a new value with a whole add-on, one kind or one section turned on or off: the bulk switches of the admin's tree.
- **Force disuse.** The second degree of off. A row listed as `"disused"` is off (no new use, like a row not listed) and the heroes that hold it must stop: a hero whose **job** is disused, one that knows a disused **ability**, one that carries a disused **item** (monsters, drop tables, personalities and statuses are held by no hero, so for them `disused` is the same as off). A commit marks the rows (`disused` beside `active`) and touches no hero: a player who never returns costs nothing and stays in limbo, with social screens and playbacks working as usual, and the moment they return they settle whatever is disused *then*. A hero that holds something disused **can't fight** (a team or party fight, joining one, or a duel is refused, naming the hero) until it is settled, and a party waits for it.
  - *Calls.* `GET /api/heroes/{id}/disuse` says what the hero has to settle (`pending`, `lost`), what would come back (`restorable`) and the scene it is in. `POST .../disuse/start` (login and CSRF token; refused for a hero in a fight) first gives back what was set aside and is no longer disused, then runs the game's scene; `POST .../disuse/next` goes on with `{"choice": n}` or `{}`. The frames are like an NPC talk's (`events`, `prompt`, `ended`) plus `pending` (the hero still has something to settle: a scene that ended without a new job leaves it so, and it goes through the scene again).
  - *The scene* is a dialog (`terraforma.npcs.script`) the game writes entirely: `Game(disuse=Disuse())` (`terraforma.disuse.hooks.Disuse`, a public interface: the license exception covers it) has `scene(session, hero, lost)`, which returns the dialog text for what the hero has `lost` (`Lost`: the job, abilities and items), and `jobs(session, hero, lost)`, the jobs a hero may take instead (every active job by default). The default scene is an all-black screen (`scene,black`) and a dialog written as if the player were asleep: it apologizes, says what is lost and that it is put away safe, and for a job asks for a new class. A game stages its own with `scene,name` (an event the game's browser code can draw into; the engine's client shows the black overlay for any scene) and the tags `set_job,job,label` and `lost,job|ability|item,label` (only in a scene), beside every other dialog tag and `include`.
  - *What happens.* A new job keeps the hero's level, experience and stats (nothing is rolled again), teaches what the job grants at that level, and keeps the abilities the old one taught. When the scene ends, the abilities and items the hero still has to stop using are **set aside** (`hero_set_aside`): it no longer knows or carries them (what it wore comes off) and nothing is deleted. Turning the component back on or just off (a hero keeps what it already has when a component is only off) gives them back at the hero's next `start`: abilities at once, items as far as the pack has room. The old job is only a record: a hero keeps the class it chose.
  - *In the browser.* When the play page opens (and the hero is not in a fight it must finish first), each hero is asked about (`GET .../disuse`); one with something to settle, a scene in progress or something kept that can come back goes through its scene before play, over the whole page (`disuse.js`, `#disuse-scene`): black, with the words, Next and the choices, and a note when the scene ends with something still to settle. A scene staged with `scene,name` sets `data-scene="name"` on the overlay (a game styles it) and emits the shell event `scene` with `{name, host, heroId}`, `host` being an empty element in the overlay a game's module may draw into.
- **Job abilities.** An add-on teaches the game's jobs (or its own, or another add-on's) abilities with `job_abilities.json`, and each row is a component of its own, keyed `job:ability` (`scout:pack_fire`) and switched like any other (it starts off). A job is stored with its own abilities and the game's `job_abilities.json` rows; a commit, and every start, adds the add-on rows that are on after them, in the seed's order, so the job's `abilities` always follow the live states. An on row needs its ability and, if the job is an add-on's, the job.
- **Sections.** `AddOn(sections={"items": (SectionNode("potions", "Potions", (SectionNode("tonics", "Tonics"),)),)})` declares the tree an add-on groups its rows of a kind in, as deep as it likes. A row of the add-on's seed says where it sits with `section` (the node's `key`; none: directly under the kind). A section key is used once per kind; a row naming a section its add-on does not declare for that kind, and a game's row with a section, stop the server. Switching a section switches the rows in it and in the sections inside it. `section` is read from the seed and is not a column.
- **Following the live state.** The engine registers the `components` section before the game's own. A commit, and every start of a server that lists add-ons, sets `active` on each add-on row to match the live states (a commit does it in its own transaction). Every offer, shop, drop, spawn and job pick already reads `active`, so none of them knows add-ons exist; the planned state changes nothing until it is committed.
- **Listing is for good.** Listing an add-on integrates it into the game; the plan is that its keys are never deleted, so recordings keep replaying.
- **Tests.** The `addons` fixture of `terraforma.testing` (none by default) is the list `app_client` puts in the settings.

## The browser client

The engine serves its own browser client: plain ES modules and CSS, no build step, no bundler, no Node. The pages know nothing of any game; they draw what the server's calls send.

| URL | What it is |
|---|---|
| `/` | The marketing site: the game's name and a way in. |
| `/play/` | The game client. Landscape only: held upright it shows "turn your device sideways". A logged-out player is sent to `/account/?next=play` (the one login, which works in any orientation) and back here once logged in; only `next=play` is understood, never an address. Then the stage (a fixed design resolution, 480 by 270, shown at the largest whole-number scale that fits), which shows the map of the party the Party panel has chosen (before a team plays: "Choose a team in Party and press Play"). **Once a player is in the game, `/play/` is the whole experience**: the map, the fight (a later slice) and every panel are drawn on this one page, and nothing loads another with the menu in the bar below it: **Teams** (the player's teams and a form that makes one by its name; each opens its own page), **Party** (a team plays as a party; in a town it says when it is ready to leave, comes back or leaves the party; when the hub offers the party a running fight to join, it asks without saying what the fight is, and the party's leader answers Join or "No, start our own"; see Joining a running fight) and **Nearby** (what a hero can reach for an action, nearest first; an NPC in the talk list has a Talk button) and **Talk** (the conversation a hero is in: what is said, Next, the answers to pick, the shop and the inn). and **Pack** (a hero's gold and items, the forms that give gold or part of a stack of items to another hero, and the ledger of what the hero gave and received: `GET /api/heroes/{id}/inventory`, `GET .../trades`, `POST .../give-gold` and `.../give-item`; the player's other heroes are offered, or a hero's number, and who may be given to is the game's trade policy, so a refusal is shown in the server's own words; the hero is the one Nearby acts with). Each stack in the pack also has Wear (with a side choice for sided slots) or Take off, Use (on any of the player's heroes, outside a fight) and Throw away: `POST .../equip`, `.../unequip`, `.../use-item` and `.../inventory/discard`; the inventory says which a stack allows (`wearable`, `sided`, `usable`, and `refused` with the reason when the game's rules bar the hero from wearing it), and a refused equip answers with `detail`, the words to show). **Drops** (loot a fight held for the party, from `GET /api/heroes/{id}/pending-drops`: Need, Want or Pass on a need/want drop, a hand-out to a hero of the party, and a line for what each settled drop came to; the fight log also says when a drop is held). A player who is not logged in is sent to the login; a team that is not theirs is "no team with that address". |
| `/profile/` | The player's own page settings, for any screen and orientation: make the public page (and give it a new address), write the bio, list the handle in the directory or not, and show or hide each team (a shown team has its own page and address). A logged-out player is sent to `/account/?next=profile` and back; only `next=play` and `next=profile` are understood. |
| `/alliances/`, `/alliance/{id}` | The player's alliances, for any screen and orientation: the alliances their teams are in, the invitations waiting (accept or decline), and founding one; then one alliance as one of the player's teams sees it (`?team=` picks the team, and a switch appears when two of the player's teams are in it): the roster (a team links to its page only while visible, and shows its player's handle only if the player is in the directory), invite (search teams by the start of a name, or give a team number) and withdraw, roles (appoint), hand over, remove, leave and disband (each asks twice), the alliance's page and bio, ballots (open, vote, close) and how the alliance sees other teams. The controls shown follow what the server says the role may do (`can`); the server still decides each call. A logged-out player is sent to `/account/?next=alliances` (`next` understands `play`, `profile` and `alliances`). |
| `/fights/` | Fights to watch, for any screen and orientation. Anyone sees the public fights (the coliseum list) and can ask for a random best fight (one button per tag kind); a signed-in player also sees the fights they can view (with why) and a team's history (pick the team), with the team's best fight of each tag kind, how many fights it keeps by hand and a Keep / Let go button on each fight. `?fight={number}` opens a viewable fight and `?watch={public name}` a public one, played back in the fight scene with the speed and skip buttons; a finished fight's *Leave* button returns to the lists. The account page links here. |
| `/admin/` | The admin's page, for any screen and orientation, with seven sections. **Events**: the manual quests (see Manual quests), narrowed by stage; write a draft (times are in the admin's own clock; the game's `spec` is JSON), rewrite it, publish it, open one to see its entries and judge a running entry won or lost with a score, and cancel a published event (asked twice). **Monsters**: the game's monsters with their strength (`pxp`), narrowed to the admins', the seed's or the retired; write a monster (stats and the `ai` weights one `Name: number` per line, abilities, items, equipment and drop tables as keys), rewrite or retire and restore one an admin wrote, or copy a seed monster as a start (the seed's own are changed in the seed). **Quest slots**: end a rotating slot's quest now (asked twice; the admin types the slot's key, as the engine keeps no list of a game's slots). **Quest proposals**: the quests the engine made for gaps in the world's progression, narrowed by stage (waiting, live, turned down, retired); approve a waiting one to make it live in its slot, turn it down, retire a live one, or run the gap check now. The game's own `spec` is shown as text and never edited. **World**: the living world's realms and settlements (see Realms): each realm's strength with a field to set it, each settlement's realm, tier and state with a button to let a live one fall or to found a dormant one or one in ruins, and a settlement's supplies (level, capacity, rate, drain and cut) with a field to cut the sources of one (0 puts them back). **Saved maps**: the maps a game generated and kept for reuse (see Maps kept for reuse), with their size, objects and how often they were copied; approve a waiting one so it is copied for later places, turn it down, or drop one (maps already made from it stay). **Settings**: the planned and live state (see Planned and live state): which snapshot is live and where the draft stands, one section of the draft edited at a time as JSON (the game's own; the server checks it again), Check, Commit to live (with a note; a draft that does not check out is shown and not committed), Drop my edits (asked twice), the committed snapshots, and links to export the draft or the live state. An export file is imported from a file picker (the file is sent as it is, since the server hashes its text; a refusal lists every problem it found and changes nothing). Nothing on the page decides who is an admin: it logs in through `/account/?next=admin` and its first admin call answers 403 to anyone else, which the page says. The server checks every field again and its words for a refusal are shown as they are. |
| `/monsters/` | Command a fight's monsters with no login, landscape only like `/play/`. A person joins the queue (the server makes a guest and answers with a token, which the page keeps in the browser's storage and sends with every call), waits as the card says, and when a fight seats them commands its monsters with the same fight scene and command menu `/play/` uses, fed by the guest calls and the guest socket. Where the game's rules refuse guests the card says why. A game's modules load here too, and see `shell.page` as `"monsters"`. |
| `/p/{token}`, `/p/team/{token}`, `/p/alliance/{token}` | The public pages, no login, any screen: a player's page (handle, bio, shown teams), a shown team's page (its alliances and, if its player is in the directory, the handle) and an alliance's page (bio and teams by role). The address is a random token; a wrong or renewed one says "No such page". |
| `/account/` | The account pages, for any screen and orientation: log in (with a password or an external provider), create an account, ask for a password reset, and once logged in the handle, the email address, the ways to sign in and two-factor login. |
| `/confirm-email`, `/change-email`, `/reset-password`, `/confirm-2fa` | The pages the links in the engine's emails open. Each takes the token from the address (and removes it from the address bar) and waits for a button, so a mail scanner opening the link changes nothing. The account pages' words are all in `strings.js`, so a game changes them with `shell.text.set`. |
| `/client/...` | The engine's own code and styles (`src/terraforma/client/static/lib`). |
| `/game/...` | The game's `client_dir`. |
| `/assets/...` | The game's `assets_dir`. |
| `GET /api/client` | What a page needs to start: the game's name, the URLs of its modules and styles, and its assets folder. |
| `GET /api/jobs` | The jobs a new hero can take (login), each with its `key`, `name` and the `stats` a hero of it starts with; the Teams panel's job list. |
| `GET /api/team-rules` | What the game says about teams (login): `team_min` and `team_max` heroes in one (never above 5) and `max_teams` for a player. |
| `GET /api/session` | Who is logged in (or `account: null`, still a 200) and the CSRF token to send back; a page that reloads has lost the token it got at login. |

**Pages run only files of the engine's and the game's own**: every page answers with a Content-Security-Policy that allows nothing inline and nothing from another site, so a game's code goes in files, not in the page.

**Browser code in a game.** A game adds its own browser code with three fields of `Game` (a public interface, covered by the license exception):

```python
Game(name="My Game", client_dir=HERE / "client", client_modules=("my_game.js",), client_styles=("my_game.css",))
```

Every page, once it knows the manifest, adds the stylesheets and then imports each module in order and calls its default export with the **shell**:

```js
export default function register(shell) {
  shell.text.set({ "login.title": "Enter the tavern" });     // any of the engine's words (strings.js)
  shell.on("login", ({ username }) => { /* ... */ });
}
```

| The shell has | |
|---|---|
| `shell.page` | `"site"`, `"account"`, `"play"` or `"monsters"` (the page where a guest commands monsters). |
| `shell.game` | The manifest: `engine`, `game`, `modules`, `styles`, `assets`. |
| `shell.assetUrl(name)` | The URL of one of the game's assets. |
| `shell.text.get(key, values)` and `shell.text.set({key: text})` | The page's words; `{name}` in a text is filled in. An element with `data-text="key"` shows the key's text. |
| `shell.api` | `get`, `post`, `call` and `ApiError`: the server's calls, with the CSRF token added to the ones that change something. |
| `shell.account` | `null`, or `{username, handle}` once logged in. |
| `shell.art.load(reference)` | A picture from the game's assets: a file name or a sheet reference (see Art). Resolves to `{source, frame, grid, frames, palette, animations}`. |
| `shell.on(event, handler)` | Events `ready` (every module registered, nothing drawn yet), `login` and `logout`, and on the play page `game` (the panels are drawn; the detail is `{roster}`) and `scene` (a force-disuse scene staged one with `scene,name`; the detail is `{name, host, heroId}`: draw into `host`). Returns a function that stops listening. |
| `shell.panels.add(id, build)` | Adds a panel to the play page's menu after the engine's (Teams, Party, Nearby, Talk, Pack, Market, Chat, Drops, Quests, Ratings). `build(shell, roster)` runs once the player is logged in and returns an element, or `{element, show}` where `show()` runs each time the panel is opened. The menu button says `shell.text.get("panel.<id>")`. `roster` is the player's heroes, teams, jobs and the game's team rules (`heroes`, `teams`, `jobs`, `rules`, `heroId`, `teamId`, `onChange(listener)`, and the calls that change them). |
| `shell.actions` | The actions the Nearby panel can ask for: `talk`, `invite`, `open`, `search`, `fight`, `help`. A game pushes the names of the ones it adds (the words are `action.<name>`). |
| `shell.activities.add(command, build)` | What the Talk panel shows when an NPC's dialog reaches an *activity* (a tag the engine leaves to the browser): the engine adds the shop for `vend`, `hawk` and `shop` and the guild's screens for `add_team`, `find_party` and `party_requests`, and a game adds a screen for a tag its `Npcs.tag` doesn't handle. `build({shell, roster, heroId, prompt, finish, proceed, problem})` returns the element; `prompt` has the `command` and its `parts`; the conversation goes on only when the screen calls `finish()` (as Next does) or, when a call of its own already moved the server's dialog on and answered with the next frame, `proceed(frame)`, and `problem` is an element to show a refusal in. A tag with no screen shows a note and a Next. |
| `shell.conversation` | The conversation the hero is in: `lines` said so far, the `prompt`, who `speaker` is, and `talk(heroId, npcId)`, `next(choice)`, `leave()` and `close()`. The server runs the dialog; the browser only shows it. |
| `shell.audio` | The page's sound (`audio.js`). The engine carries no sounds: a game's module says which of its files go with what happens, `shell.audio.add({ cue: "audio/sfx/hit.mp3" })` for effects and `shell.audio.addMusic({ scene: "audio/music/map.mp3" })` for tunes (file names under the game's assets, see Sound below). `play(...cues)` plays the first of the cues that has a file, `music(scene)` sets the looping tune (`null` stops it), `set({ muted, effects, music })` changes and keeps the player's choice, and `onChange(listener)` hears it. A game with no sound gets no sound button. |

A module that fails to load is reported in the console and on the page, and skipped; the rest still run. A game changes the look with a stylesheet, usually by setting the custom properties at the top of `engine.css`. Each later client slice adds its own hooks here (map objects).

The client's files are checked when the app is made: a module or style that isn't in `client_dir`, a name with a path out of it, or a folder that doesn't exist stops the server at start.

The map scene (`map-scene.js`) draws the party's map on the stage's canvas at the design resolution, 32-pixel tiles with the view centered on the party (held inside the map, or following it where the map wraps; a map smaller than the view sits in the middle), the pictures from the tileset's `art` (a file or a sheet reference, through `shell.art`; a tile with no picture is a flat color) the party as its first hero's `map_art` (the stage's `data-pose` says the pose it draws, `stand_<dir>` or `move_<dir>` for the way it last stepped, or `marker` for a hero whose personality has no map art; `GET /api/teams` gives each member its `map_art`, found through the personality that has its job's key, as in a fight) and a marker for each object (S for a sign, D for a door, C for a chest). A tap or click on a tile, or the arrow keys or WASD, proposes a route (`POST /api/parties/{id}/route`: the server fills in the gaps or says why not, shown in the stage's note) and the party then walks it one tile at a time, checking in with the server at each (`.../route/step`); if the server does not confirm a tile, the party is put back where it really is. A walk stops at a fight (the fight scene takes the stage, see below), at a town (the Party panel opens to leave it) and at an event at an edge of the map (its dialog opens in the Talk panel). A tap on a chest, door or sign uses it (`POST /api/heroes/{id}/objects/{id}/use`, which the server refuses out of reach): a script that asks something opens the Talk panel, and one that only says something is shown in the note. A warp (stairs, a door) moves the party to another map and the stage loads it. The stage's `data-map`, `data-party-x`, `data-party-y` and `data-walking` attributes say what it shows. `GET /api/teams` says which party (`party`) each team is in, which is how the stage finds its party again after a reload.

**Sound.** `shell.audio` plays what a game registers; the engine plays the cue when the thing happens and sets the tune when the scene changes. The cues: `panel.open` and `panel.close` (a panel opening or closing), `menu.confirm` and `menu.cancel` (the fight menu), `fight.start`, `fight.victory` and `fight.defeat` (how a finished fight went for the player; `fight.over` when they only watched), and one for each event of a fight's log as it is played: `fight.act` (a turn's action; `fight.<cue>`, such as `fight.attack_close`, is tried first), `fight.damage`, `fight.miss`, `fight.heal`, `fight.died`, `fight.fled`, `fight.revived`, `fight.defend`, `fight.status` and `fight.level`. A fight that is skipped ahead makes no sound for the events it skips, and sound is no motion, so reduced motion keeps it. The tunes are `map` and `fight`; a game plays more of its own with `shell.audio.music(name)` and `shell.audio.play(name)`. A browser keeps a page silent until the player has touched it, so a tune asked for earlier starts at the first tap or key; a file the browser cannot play is left alone. The bar shows a *Sound on* / *Sound off* button when the game gave the page any sound, and the choice (off, and the two volumes) is kept in the browser's storage. The example game registers its own tunes and effects (`audio/` among its assets, each file's source and license are in its `ASSETS.md`). `shell.audio`, the cue names and the tune names are covered by the license exception.

The fight scene (`fight-scene.js`) is the other scene of the same stage: when a walk or the Party panel's Leave Town starts a fight, the shell is told (`shell.emit("fight", { fight })`), the map is suspended, any open panel is closed and a layer over the stage (still the 480 by 270 design resolution, scaled with it) draws the fight, so the page is never left. The scene is built from `GET /api/fights/{id}` (the `vital` it names is the resource whose loss is damage) and kept up to date by the fight socket (`fight-link.js`, `/ws/fights/{id}`: it retries a few times if the socket drops and the scene asks the server how the fight stands once it is back). Each `round` message holds the events of a round; they are played one at a time through the fight model (`fight-model.js`, which follows the events exactly as the server's replay does, so the gauges end where the server has them): what is said goes to the log under the stage, the gauges move, and the fighters move with the Web Animations API (the scene waits for each animation to finish), at a reading pace the player can speed up (1, 2, 4 times) or skip, and with no movement for a player whose system asks for less motion. Heroes of party 0 and the player's own are drawn on the left, the rest on the right, as a name and a gauge each, and a picture above them when the fighter has `fight_art` (the fight view gives each such fighter an `art`, the same file name or sheet reference; it is loaded through `shell.art` and drawn 48 pixels square, playing `base` (the left side's `base_up`, the right side's `base_down`; see Art, Back and front) if the reference names an animation file, else the reference's `frame` as a still, and the first frame only for a player who asks for less motion; a fighter without art, or whose picture fails to load, stays a card). The stage's `data-sprites` says how many fighters show a picture and `data-animated` how many of those move. When the fight is over the player leaves it with a button and the map comes back; a page that opens in the middle of a fight (`GET /api/fights?running=true`) goes straight back to it. The stage's `data-scene` (`map` or `fight`), `data-fight`, `data-link`, `data-round`, `data-playing`, `data-over`, `data-speed` and `data-shown` say what it shows. The command menu (`fight-menu.js`) is how the player commands their heroes on that screen: the fight view (`GET /api/fights/{id}`) gives each of the caller's own fighters a `menu` (the weapons it can attack with, its skills and spells with their cost and whether it can pay it, its items that do something when used, whether it may flee, and for each whom it is aimed at: `enemy`, `ally`, `downed` or `none` when the ability names its own targets), and the page only offers those choices. The player commands each hero in turn (Attack, Skill, Spell, Item, Defend, Flee), picks a target by its card where one is needed (the cards that can be aimed at light up, take Enter or Space, and Escape or Back steps out), may pick another of their heroes by its card to choose again before the round plays, and the command goes through `POST /api/fights/{id}/commands`. The menu hides while a round is played and when the fight is over, and asks the server again after each round (items and MP change). The stage's `data-menu` (`commands`, `list`, `target`, `waiting` or `off`) and `data-hero` say what it shows. The log names a hero's skills, spells and items by their names (the menu lists them), and a fighter that defends is told by a `Defend` event with its address at the start of the round (it takes no turn), so the log, or a game's own client code, can show it (`fight.defend`). Not in the menu yet: changing gear in a fight (the `equip` and `equip_weapon` commands). `shell.panels.close()` closes the open panel.

**Old tilesets.** `python -m terraforma.tools.qbtiles MAP.MAP out/tiles --preview out/look.png` turns a QBasic tile file (what a `PUT` of an array of 32 by 32 pictures in SCREEN 13 writes, with the `PALETTE r + g * 6 + b * 36` colors) into a tilesheet: `out/tiles.png`, `out/tiles.sheet.json` and, if some pixel has no color in the palette, `out/tiles.alpha.png`. The two 16-bit numbers the game kept with each tile are written to the sheet's JSON (`tag` and `mark`). `--preview` writes an enlarged picture to look at, and `--missing "#ff00ff"` draws pixels with no color instead of leaving them clear. Standard library only.

**Making sheets.** `python -m terraforma.tools.tilesheet knight.png out/knight --frame 32x32 --scale 2 --colors 32` turns a picture, or a GIF (`walk.gif`), into the tilesheet format of Art below: `out/knight.png` (indexed), `out/knight.alpha.png` (the 8-bit transparency, written only when some pixel is not opaque) and `out/knight.sheet.json`. A still picture is cut into frames of `--frame` (the whole picture is one frame if left out; `--frames N` keeps only the first N cells), left to right and then down; a GIF gives one frame for each of its frames, and the tool also writes its timing as `out/walk.anim.json` (an animation named `base`, or what `--animation` says; `--no-animation` writes none; the most common frame time is the animation's `ms`, a frame with another says its own, and the animation loops if the GIF does). `--scale` resizes each frame (above 1 by whole pixels), `--colors` is the most the palette may hold (2 to 256; a picture with fewer keeps its colors exactly, and the palette is made from the pixels that can be seen, so a color under a clear pixel costs none), `--columns` sets how many frames lie across the sheet, and `--combined` writes one RGBA picture instead of the color and alpha sheets. It needs Pillow, which only the tool uses: `pip install "terraforma[tools]"`.

**Making color maps.** `python -m terraforma.tools.colormap` makes and checks the recolors of Art below (`name.colors.json`), with these commands (a sheet or map is written without its extension):

- `colors out/knight` lists the sheet's palette.
- `make out/knight out/red_team --hue 150` writes a map that turns the palette colors 150 degrees round the color wheel; `--saturation` and `--lightness` multiply those, `--only "#3050a0,#7090e0"` and `--skip` choose which colors the three touch, and `--swap "#102040=#403010"` (repeat for more) sets a color outright and wins over the shifts. The map lists only the colors that change; a map that would change nothing is refused.
- `check out/red_team.colors.json --sheet out/knight` checks the format and, with `--sheet`, that every color the map changes is in the sheet's palette (a color the palette lacks never matches, so such an entry does nothing). The server runs the format check on every `*.colors.json` in the game's assets folder when it starts, and refuses to start on a bad one.
- `merge out/red_team out/dark out/dark_red --sheet out/knight` writes one map that does the first and then the second.
- `preview out/knight out/red_team out/look.png --scale 4` draws the sheet recolored the way the browser does (pixels snapped to the palette, then swapped), to look at before it goes in a game.

Only `preview` needs Pillow; the rest is standard library.

**Making hero art.** A player's hero is drawn with the personality that has its job's key, and that personality needs a fight sheet with a back view (see Art, Back and front) and a map sheet. `python -m terraforma.tools.heroart looks.json --out assets/` draws both for every class in a looks file (name classes after it to draw only those): for a class `knight`, `knight_fight` (twelve frames: eight from the front, four from behind, with `base_up` and the rest of the fight animations) and `knight_map` (nine frames, standing and walking down, up and right), each with its `.anim.json` and written through `terraforma.tools.tilesheet`, so `"fight_art": {"sheet": "knight_fight", "animations": "knight_fight"}` and the same for `map_art` is the whole personality. The looks file belongs to the game (it is the source of the game's hero art, kept beside its asset notes); the engine only holds the pieces: `{"knight": {"colors": {"cloth": "#7e8aa0", "accent": "#c03030"}, "head": "helm", "weapon": "sword", "offhand": "kite", "body": "tabard"}}`. A look's `colors` change any of the roles in `terraforma.tools.heroart.BASE` (and `hood` and `mask`); `head` is one of `hair helm hood feather_cap headband mitre bard_hat antlers cowl`, `weapon` and `melee` (what it strikes with, the weapon if left out) one of `sword dagger bow mace lute rapier staff wand` (none: fists), `offhand` one of `kite dagger symbol tome`, `body` one of `tabard scarf quiver sash stole doublet vines runes`, `ranged` (what the shoot pose draws) `bow`, `throw` or `spark`, and `bald` and `down_cap` (the color of what is on the head when the hero is down). Every problem in a looks file is listed at once, and the same file draws the same pictures every time. Needs Pillow (`pip install "terraforma[tools]"`).

**Balancing a game.** `python -m terraforma.tools.balance --content src/my_game/seed --rules my_game.rules:MyRules --levels 1,10,25,50 --fights 200` plays whole teams of heroes against monsters of their own strength with the engine's rules, many times at each level, and reports what each job did: damage dealt (and its share of the team's), damage taken, healing, mana spent, how often it fell, and for every ability that hits several foes how much of the enemy party's life one cast takes (the "AoE gauge"). `--content` is the game's seed folder and `--rules` its `Rules` class as `module:Class` (the engine's own if left out; the module must be importable, so run it from the game's environment). A hero at level L is built as the engine builds one (the job's growth rounded at level 1, then 75 to 100 percent of it for each level after), has the abilities its job grants by then and wears nothing, so the numbers show stats and abilities and not gear. Without `--team a,b,c,d` each fight draws four different jobs, so a job's numbers average over many teams; `--difficulty` sets the encounter's strength as a multiple of the team's (1 by default, the PXP the two sides add up to), and the encounter's size follows the level (3 to 5 monsters at level 1, 4 to 30 at level 50; `--foes 3-5` fixes it), heroes standing in groups of five and monsters in groups of ten. Monsters and heroes are both played by the engine's AI, every fight has its own stream of dice taken from `--seed`, so a run repeats exactly, and `--json out.json` keeps the numbers for a spreadsheet. Two more modes play named teams from a scenario file (`--scenario teams.json`), so a game keeps the line-ups it cares about, such as the usual party and a party with no healer. `--mode attrition` starts every fight from a rested party and reports what one fight costs it on average (the share of the party's life and mana lost, and how often it wins). `--mode endurance` has one party fight encounter after encounter with no rest and nobody raised until it is wiped out (or `--cap` fights have passed), and reports how many fights it lasted (`--runs` runs of each team). The scenario is JSON: `{"levels": [5, 20, 40], "difficulty": 0.3, "runs": 20, "teams": {"usual": ["knight", "rogue", "cleric", "warlock"], "same knight": [{"job": "knight", "seed": 7}, "rogue", "cleric", "warlock"]}}`. Only `teams` is needed; `levels`, `difficulty`, `foes`, `fights`, `runs`, `cap` and `seed` are the flags of the same names (a flag on the command line beats the file), and a hero given as `{"job": ..., "seed": ...}` is made from that seed alone, so it has the same stats in every fight. A party at `--difficulty 1` meets encounters as strong as itself, which is a hard fight; try 0.2 to 0.4 for a typical one. It is a tool run on demand: no test plays more than a few fights. It never imports a game by itself, and reads only the seed folder and the rules class it is told about.

**The example game** (`terraforma.example`) is the smallest game that uses all of this: a seed with a small map drawn with a 13-picture tileset (`tiles.png`, made by Mike and converted from QBasic), a cellar, a marsh in the hub where a slime fights the party (the swamp tiles meet monsters), four jobs (Fighter, Scout, Mage and Cleric, each with abilities learned by level), sixteen abilities and five statuses, twenty items (potions, an antidote, weapons with a bow and its arrows, armor for every slot), six monsters with drop tables (a slime in the marsh; bats, goblins, wolves, skeletons and imps in the dark swamp beside it), a personality for each job and each monster with its pictures, and three people to talk to next to where heroes start (Old Tom gives gold, Hana sells the potions, weapons and armor, Bede keeps the inn), a signpost and stairs down to a cellar map (its town is the gate tile where heroes start: a party that steps onto it waits there, and the rest of the meadow is open ground to walk), and a browser module and stylesheet that use the hooks above. `python -m terraforma serve` runs it, and it is the game the browser tests play. A game of your own can start from it. Its pictures are drawn for this repository (the heroes' and monsters' sheets by `utils/example_art.py`, which draws them again the same every time: `PYTHONPATH=src python3 utils/example_art.py`) and a game that wants more bodies draws them with `utils/monster_art.py` (a brute, a mage, a ghost, a robot and a drone, four poses each, drawn the same way: `PYTHONPATH=src python3 utils/monster_art.py --out YOUR/assets --prefix yourgame_`, then recolored by color maps); every asset's source and license are recorded beside it (`assets/ASSETS.md`). The jobs' personalities share the keys of the jobs (`fighter`, `scout`, `mage`, `cleric`) and one pair of hero sheets, told apart by a color map each.

## Running it

Everything runs in Docker.

```sh
cp settings.example.toml settings.toml      # then set session_secret
mkdir -m 700 keys
docker compose run --rm app python -m terraforma keys new   # the encryption key (once)
docker compose up app                       # the engine alone, http://localhost:8000 (Postgres)
docker compose run --rm test                # every test, on SQLite, Postgres and MySQL
docker compose run --rm test -m e2e         # only the browser tests (Chromium plays the example game)
```

The browser tests (`tests/e2e`) serve the example game on a real port and play it in Chromium with Playwright: a test fails on any console error or warning, uncaught error or failed request. In CI they run on SQLite for every pull request; the label `browser-all-databases` on a pull request runs them on Postgres and MySQL too. Outside Docker, `pip install -e ".[dev]"` and `playwright install chromium` set them up.

Settings come from `settings.toml`, not environment variables. The NAS the game runs on may not pass environment variables or Docker secrets into the container. `python -m terraforma check-settings` says what's wrong with the file, if anything.

On start, the container checks the settings, brings the database up to date (`python -m terraforma serve`), then serves. `GET /api/health` answers the container's health check.

## Signing in with an external provider

A game can let players sign in with any OpenID Connect provider (Google, Microsoft and others) instead of, or as well as, a password. Each provider is a `[[external_providers]]` section in `settings.toml` (see `settings.example.toml`): `name` (lowercase letters, digits, `_`, `-`), `label` (the button's words), `issuer`, `client_id`, `client_secret`, and optionally `scopes` (must include `openid` and `email`) and `authorization_endpoint` with `token_endpoint` (both or neither; by default they are read from `<issuer>/.well-known/openid-configuration`). Addresses must be https (http only for localhost). Register `<public_url>/api/external/<name>/callback` as the redirect address at the provider. Microsoft's shared issuer, `https://login.microsoftonline.com/common/v2.0`, is accepted: its `{tenantid}` is read from each token. With no providers listed nothing changes and no button appears.

Two providers are not OpenID Connect and have their own `kind` in the section (`kind = "oidc"` is the default). `kind = "facebook"` needs `client_id` (the app id) and `client_secret`; the server trades the code for an access token at the Graph API and asks it for the person's id and email, signing the call with `appsecret_proof`. Facebook returns an email only when the person has a confirmed one, so a returned address counts as verified; without one the first sign-in is refused like any unverified email. `kind = "steam"` needs nothing else: Steam speaks OpenID 2.0 and has no keys. The server checks that Steam's answer is for this sign-in (its signed `return_to` carries the one-use state), signed the fields that matter and is fresh, then asks Steam to confirm its signature (`check_authentication`). Steam gives no email address, so it can sign in or be linked to a player who already has an account, but a first Steam sign-in with nothing linked ends in `?external=error&reason=no_account` and makes no account. `issuer`, `scopes` and the endpoint settings are only for `oidc`.

A provider that keeps the person's account for several games (the shared account service is one) can also tell this site when the person deletes it. Set `deletion_events = true` in its section (only for `kind = "oidc"`; `jwks_uri` names the provider's signing keys and is read from its published settings when left out, but must be given when `authorization_endpoint` and `token_endpoint` are). The provider then posts `{"token": "<signed message>"}` to `POST /api/external/<name>/events`. The message is a Security Event Token (RFC 8417): a JWT with the header `typ` `secevent+jwt`, signed `ES256` or `RS256` with a key from the provider's key set (found by `kid`), whose `iss` and `aud` are the provider's issuer and this site's `client_id`, with an `exp`, and `events` holding `<issuer>/events/account-deleted` with the person's `sub`. The call has no player login or CSRF token (the signature is the proof; it is rate limited by address), answers the same whether or not the person is known, and ignores any other event (the shared account service also sends `supporter-changed` to the same address; the engine has no use for it yet, so it answers 200 and does nothing; at the service the address is the game's `events_webhook`). The same provider can ask, before the person confirms a deletion, whether they have anything here: `POST /api/external/<name>/account-lookup` with the same `{"token"}` body and checks (the person is the token's `sub` claim) answers `{"exists": true|false}` and, when true, a `summary` such as `an account with 2 teams`; it changes nothing. A deletion removes the link between that person and their account here and ends every login of the account (`session_version` moves on); the account's game data is kept, and an account with a password of its own still works.

The flow is the authorization code flow with PKCE, a `state` and a `nonce`, all kept in the signed session cookie and used once. The server trades the code for the ID token itself, over TLS, and checks the issuer, the audience, the expiry and the nonce; it does not read a signature, which OpenID Connect allows for a token received straight from the token endpoint. Calls: `GET /api/external/providers` (names and labels), `GET /api/external/<name>/start?next=play|profile` (or `?next=oidc&request=<the sign-in provider's signed request>`, which the login page passes on when a site's player came through `/oidc/authorize`: the request is checked, kept in the session, and handed back in the redirect as `next=oidc&request=...` so the page carries on to `/oidc/resume`, also after the first-sign-in and two-factor steps), `GET /api/external/<name>/callback` (always ends in a redirect to `/account/?external=<outcome>`, where `<outcome>` is `done`, `twofa`, `finish`, `linked` or `error` with a `reason`), `GET /api/external/pending`, `POST /api/external/finish`, `POST /api/external/2fa`, `GET /api/external/identities`, `POST /api/external/<name>/link`, `POST /api/external/unlink` and `POST /api/external/password`. Every call that changes an account needs the login and the CSRF token, as the other account calls do.

The rules: every login has a local account. A first sign-in uses the provider's email only when the provider calls it verified; the player then chooses a username and a handle (the handle cannot match the username or the email), and may set a password; the account is made at that step, so abandoning it leaves nothing behind. An email that already has an account never creates or links anything, and the answer does not say how that account signs in. Linking is an explicit action from the account page, needs a current two-factor code when two-factor login is on, and refuses a provider account another player has. Unlinking needs a current two-factor code when it is on and never removes the last way in: a player whose only way in is a provider sets a password first. Two-factor login applies to every way in, a provider sign-in included. A game that wants to hide the buttons leaves the providers out of `settings.toml`.

## Second factors

Two-factor login is on while at least one method counts: an **authenticator app** (TOTP, RFC 6238) or a **security key or passkey** (WebAuthn, FIDO2, through the `webauthn` library). **Recovery codes** (ten, kept only as hashes, each good once) come with the first method and go with the last; they stand in for any method. There is no SMS and no email code, and no way back in by email: a player who loses every method and the recovery codes is reset by an admin.

Calls (all under `/api/2fa`; the ones that change something need the login and the CSRF token): `GET` (state: whether it is on, the app, the keys, the recovery codes left), `POST /challenge` (the options for a key's answer, and which methods count), `POST /setup` and `POST /enable` (the app), `POST /webauthn/options` and `POST /webauthn/register` (a key), `POST /webauthn/remove` and `POST /remove-app` (one method, while another stays), `POST /disable` (all of them), `POST /recovery-codes`, `POST /confirm` (the emailed link), `GET /browsers` and `POST /browsers/forget` (remembered browsers). `POST /api/admin/2fa-reset` is the admin's reset (below).

The rules: every change to two-factor login is confirmed by an emailed link, which works once for an hour, and a newer request replaces the one waiting. Once a method is on, every change needs a live second factor first (an app code, a recovery code or a key's answer) and the call that needs one takes it as `code` or `assertion` (what `navigator.credentials.get` returned, as JSON text), never both: logging in, changing the email address, linking and unlinking a provider, setting a first password and every call above. A key's challenge is made on request (the 202 answer of `/api/login`, `GET /api/external/2fa` and `POST /api/2fa/challenge` carry the options), kept in the signed session cookie and used once, right or wrong. A registered key counts only after its link is followed; a counter that does not go up is refused as a cloned key (0, which passkeys report, is accepted). The relying party is the host of `public_url` and the one origin is `public_url` itself, so `public_url` must be the address players really use, and a browser refuses a key on a bare IP address. No attestation is requested. Every try, by any method, counts against the account's `2fa-code` rate limit.

**Remembered browsers.** A player who proved a second factor may tick "remember this browser" (`remember: true` on the login), which skips it for `SignIn.remember_browser_days` days (30 by default, 0 for never) on that browser, provider sign-ins included. The browser holds a random secret in an `HttpOnly` cookie of its own for each account; the database keeps its hash. A remembered browser stops counting when its time is up, when the account's session version moves on (a password reset or an email change), and whenever two-factor login changes (a method added or removed, new recovery codes, turned off). The player sees their browsers on the account page and can forget one or all. At most ten are kept per account.

**What a game decides**, with `Game(sign_in=...)` (a public interface): subclass `terraforma.accounts.hooks.SignIn` and set `remember_browser_days`, and/or override `single_method_note(account, methods)`, the note shown after login to a player whose second factor is a single method (`methods` is `"app"` and/or `"key"`); the default says to add a second one, and returning None says nothing. The answer of a good login carries it as `note`.

**The admin's reset.** An account with `is_admin` set (by the game's own setup, see Challenge Tokens) calls `POST /api/admin/2fa-reset` with a `username`: that player's methods and recovery codes are removed, every login and remembered browser of theirs ends, and they are told by email. They log in with their password and set it up again. It is rate-limited and logged (the log names account ids, never secrets).

Housekeeping removes expired remembered browsers and keys whose link was never followed (a day).

## Encryption keys

Secrets the engine must read back, such as 2FA secrets, are stored encrypted with a key kept in files beside `settings.toml` (the `key_dir` setting), never in the database. There are two slots: `current.key` encrypts, and `previous.key` still decrypts what the last key made, so a rotation never locks anyone out.

```sh
python -m terraforma keys new       # the first key; refuses to replace one
python -m terraforma keys rotate    # a new key, and everything stored is re-encrypted with it
```

The server won't start without a current key. Back the keys up apart from the database: a database backup is unreadable without them, and both together give everything away. A column that holds encrypted values is registered with `terraforma.keys.encrypted_column`, so rotating finds it.

## Changing the tables

Until the first release there are no migration files: nothing is live, so the tables are built straight from the models (`terraforma/db/schema.py`). Change a model and that is the whole change.

- An empty database gets every table when the server starts (`python -m terraforma serve`, or `python -m terraforma create-tables`), plus a one-row `schema_stamp` that remembers a fingerprint of the models.
- A database made by other models is refused at start with a message instead of failing later on a missing column. Reset it, which **deletes everything in it**: `python -m terraforma reset-database --yes` (or recreate the database or its Docker volume).
- Because there is no history, there are no migration numbers, no `down_revision` and no merge order to keep for the tables.
- Alembic stays installed. `tests/test_baseline_migration.py` generates the baseline Alembic would write for an empty database, runs it on each database, and checks it builds exactly the tables the models describe and undoes cleanly, so the release path keeps working.
- At the first release (Mike cuts it) the baseline is written as migration `0001` (`alembic revision --autogenerate -m baseline`), `serve` runs `upgrade` again, and from then on every change is a numbered migration with its own tests.

## Seed data

A game's starting content is JSON in its `seed/` folder (`Game(seed_dir=...)`): one file per kind of content, each a list of objects. A kind may also be split over several files: put them in a folder named for the kind (`seed/monsters/goblins.json`, `seed/monsters/bosses/dragons.json`; any depth, `.json` files only, names starting with `.` skipped), alone or beside `monsters.json`. The rows are joined, `monsters.json` first and then the folder's files in path order, and the result is checked as if it were one file. A `key` in two files of the same kind stops the server, naming both files. An add-on's seed folder works the same way. These formats are a public interface, so changing one is deliberate and noted here.

| File | A row has |
|---|---|
| `abilities.json` | `key`, `name`, `kind` (`spell` or `skill`), `mp_cost`, `description`, `icon`, `effect`, `presentation` |
| `items.json` | `key`, `name`, `price`, `one_use`, `description`, `icon`, `use_effect`, `equip_slots`, `requires`, `stat_bonus`, `stat_percent`, `attack`, `use_presentation`, `fight_presentation` |
| `jobs.json` | `key`, `name`, `xp_needed`, `stat_growth` (stats per level), `abilities` (each `{"ability": key, "level": n}`, the level a hero gets it at; a bare key means level 1) |
| `job_abilities.json` | `job` (key in `jobs.json`), `ability` (key in `abilities.json`), `level` (default 1): one more ability for a job written elsewhere, so an add-on can teach the game's jobs its own abilities. Joined to the job's `abilities`; a job getting the same ability twice, from its own row and here or from two rows, is refused. An add-on's row is a switchable component (see Add-ons): it goes by the key `job:ability` and may have a `section`. |
| `personalities.json` | `key`, `name`, `fight_art` and `map_art` (each a picture, see Art: a hero's two are separate sheets, a monster needs only `fight_art`), and the older way, an animation for each of `base equip flee hit die attack_close attack_throw attack_shoot skill spell item`, and `overworld` (`stand` and `move`, each facing `up down left right`) |
| `monsters.json` | `key`, `name`, `personality` (key), `xp_reward`, `gold_reward`, `stats`, `abilities`, `items`, `equipment` (keys), `drops` (drop table keys), `ai` |
| `drop_tables.json` | `key`, `name`, `weighted`, `rolls`, `entries` (see Item drops below) |
| `statuses.json` | `key`, `name`, `kind` (`good` or `bad`), `description`, `icon`, `duration`, `intensity`, `ticks`, `modifiers`, `xp_share` (see Statuses below) |
| `maps.json` | `key`, `name`, `wrap_x`, `wrap_y`, `safe_steps`, `tileset`, `tiles`, `zones`, `zone_tiles`, `objects`, `edges` (see Maps below) |
| `dialogs.json` | `key`, `text` (a dialog tree in the dialog language, at most 20000 characters, checked when the seed loads; NPCs, objects, edges and other trees run it with `include,key`: see Dialog trees). A tree the file no longer lists stays where it is. |
| `npcs.json` | `key`, `name`, `map` (a key in `maps.json`, or the default `hub`), `x`, `y`, `dialog` (the dialog language, checked when the seed loads: see NPCs and dialog), `counter` (tiles, `[[x, y], ...]`). The NPC with a key is placed, or moved and rewritten if it exists, each time the content loads; one the file no longer lists stays where it is. |
| `materials.json` | `key`, `name`: a raw material (see Realms and settlements) |
| `realms.json` | `key`, `name`, `kind` (`kingdom`, the default, or `minor`: a lesser power that holds settlements under no kingdom; the engine treats both alike), `strength` (where the realm starts; after that the world moves it and a later load leaves it alone; see Realms and settlements) |
| `settlements.json` | `key`, `name`, `realm` (a key in `realms.json`), `map` (a key in `maps.json`, or the default `hub`), `tier`, `x` and `y` (its entrance tile on the map, both or neither; settlements may share a map, such as the overworld, and are told apart by where they are, so two may not stand on the same tile), `state` (`live` or `dormant`, how it starts; later loads leave the state alone), `supplies` (see Realms and settlements) |

Unlike the other files, a template the file no longer lists is only made inactive, and a template an admin promoted from a generated quest is never touched by the file. |
| `quest_slots.json` | `key`, `name`, `guild`, `rank` (the game's own labels for its dialogs), `min_days`, `max_days` (a period lasts a random whole number of days in this range), `grace_days`, `limit_days`, `obligation` (true for a duty of the guild's members; see Rotating quests below). A slot the file no longer lists is only made inactive. |

- **Keys.** Every row has a `key` (1-64 lowercase letters, digits, `_` or `-`) that the game picks and never reuses. Rows name each other by key. Only `key` and `name` are required; the rest have defaults.
- **Equipment slots.** An item's `equip_slots` lists the slots it takes. The engine's slots are `rhand rammo rarm lhand lammo larm body head back feet`; `hand`, `ammo` and `arm` are *sided* (the player picks left or right when equipping), and a two-handed weapon lists `lhand` and `rhand`. A weapon's `attack.ammo_type` has to match its ammunition's. **A blow that leaves a status.** An item's `attack` may carry `status`, `{"status": "poison", "duration": 3, "chance": 25}`: `status` is a *bad* status of `statuses.json` (the seed is refused for any other), `duration` the rounds it lasts (left out: the status's own) and `chance` the odds out of 100 that a blow that landed leaves it (100 if left out). Ammunition is the usual carrier (a poison arrow); when a weapon is loaded the ammunition's `attribute` and `status` are the ones that count, and a weapon that needs no ammunition may carry its own. The status is placed after the damage (not on a miss, and not on a target the blow felled), by the blow's wielder, as an ability's status is; a chance under 100 draws one roll from the fight's stream (`Rules.attack_status_lands`) and a sure status draws none, so a stored fight replays exactly. It counts toward PXP: the status adds its worth (`STATUS_ROUND_WORTH` for each round it lasts, by the chance) to the wielder's strength in the offence part, as `fights/potential.py` explains. An add-on item's status is a component it needs, as an ability's is. Gear never stacks; ammunition and non-equipment stack to 250, in at most 12 stacks (for now these limits are constants in `heroes/inventory.py`).
- **Who may wear it.** An item's optional `requires` is `{"jobs": [keys], "level": n, "stats": {stat: minimum}}`: the hero's job must be one listed (if any are), the level at least `n`, and the hero's own stats (before any gear, so wearing one thing never decides the next) at least the minimums. Job keys must exist in `jobs.json`. A hero who doesn't qualify gets `{"outcome": "not_allowed", "reason": ...}` (422) from `/equip`, nothing is moved, and the inventory view marks such gear with `refused` (the reason); the same rule holds when changing gear mid-fight. The decision is `Rules.equip_refusal(wearer, item)`, which returns a reason or `None`: a game overrides it for any other restriction (a guild rank, an alignment) and calls `super()` to keep the seed's. A monster's own authored gear isn't checked. The inventory view marks each stack `wearable` (it takes a slot), `sided` (a sided slot, so the call needs a `side`) and `usable` (it has a use effect), and a refused equip or unequip answers with `outcome` and a `detail` in words (the rules' reason where there is one).
- **Stats** are the game's `Rules.stats` (see Fight rules below), by default `HP MP Speed Accuracy Strength Dodge Block Power Resistance Focus`; a stat left out is 0, and any other name is refused.
- **An effect** is `{"effect", "targets", "base", "added", "attribute", "status", "duration"}`: `effect` is one of `none heal hurt revive slay cause_good_status remove_good_status cause_bad_status remove_bad_status restore_mp eject`, `targets` is `individual`, `group`, `party`, `all_parties` (every party, the actor's own included), `all_allies`, `all_enemies`, `all_not_allies` (enemies and neutrals), `all_not_enemies` (allies and neutrals), `random_party` (one whole party, drawn from the fight's own random stream so the fight replays, from the parties `Rules.random_party_pool` names: by default every party with someone alive, the actor's own included; a game narrows it), or a number *n* (the target and *n* neighbours each way along its group, hit less the further they are), and `attribute` is the game's own kind of damage. `revive` gives a fallen target its full life by default; `Rules.revive_fallen(rng, effect, maximum)` decides how much it gives back (0 = it did not take, a `NoEffect` event), so a game can make a revive that succeeds 33% of the time at half life from `base` and `added`. `slay`'s `base` is its chance out of 100. `eject`'s `base` is its chance out of 100 too (see Fleeing); `friendly: true` (for `eject` only) lets it be aimed at the user's own side. `cause_good_status` and `cause_bad_status` need a `status` (a key in `statuses.json` of the matching kind) and may set `duration` (rounds) over the status's own; `remove_good_status` and `remove_bad_status` take off the one `status` names, or every status of their kind if it is left out. `steal_hp` and `steal_mp` are aimed at enemies, can be dodged (a skill) or resisted (a spell) like `hurt`, and give the user what they took: `steal_hp` hurts as `hurt` does and heals the user by the life the target really lost (not more than it had left, not past the user's maximum); `steal_mp` takes `base` plus up to `added` mana from the target (no more than it has) and the user's pool takes what fits. `transfer_hp` and `transfer_mp` are aimed at allies and are never dodged or resisted: the user gives `base` plus up to `added` of its own life or mana, no more than the target has room for, and loses exactly what the target took in. A giver keeps at least 1 life; mana can run to 0. A transfer to a fallen or full target, or from a giver with nothing to spare, does nothing (`NoEffect`). The AI values `steal_hp` like `hurt` and does not use the other three yet.
- **An animation** is `{"animation", "images", "sounds", "times"}`; pictures and sounds are plain file names under the game's assets folder (no absolute paths, no `..`).
- **Checking.** Anything unknown, mistyped or out of range is refused with the file, row and field named, and so is a repeated key or a reference to a key that doesn't exist. All problems are listed at once, and the server won't start on a bad seed.
- **Loading.** On every start the engine makes the database match the seed: new keys are added and known keys updated in place. A key the seed no longer lists is kept but marked inactive, never deleted, because heroes and fight history may still point at it. A file the seed doesn't have leaves its table alone.
- **Monsters an admin writes.** The engine never makes a monster up, but an admin may write one (a boss for a manual quest, a coliseum bout) without touching the seed. `terraforma.content.authoring` and the admin calls `GET /api/admin/monsters` (`authored`, `active`, `after`, `limit`) and `GET .../{key}` (login, admins), `POST /api/admin/monsters` (the monster with its `key`), `PUT .../{key}` (rewrites it whole), `POST .../{key}/retire` and `.../restore` (login and CSRF token, admins only; each its own route and rate-limited) manage them. The monster is checked exactly as a `monsters.json` row is (the game's stats, and its personality, abilities, items, equipment and drop tables must exist and be active); a bad one is refused (422) naming every problem, a used key is a conflict (409). Its row is marked `authored`, so loading the seed never marks it inactive, and every view carries its `pxp` (`Rules.pxp`) to balance it by. It is never deleted, only retired (a retired key stays taken). A monster from the seed can be read but is changed in the seed (409); if the seed later lists the key of an authored monster, the seed row takes it over and the seed owns it from then on.

`terraforma.seed.load_seed` reads the files; `terraforma.content.schema.check_seed` checks them; `terraforma.content.loader.load_content` loads them.

## Statuses

A status is something a fighter can be under, and `statuses.json` is where a game defines them. A fighter under one carries a *token* that records the status, **who placed it** (the *source*), how many rounds have gone by and how long it lasts. A stat is changed by a status and by nothing else (there is no effect that pushes a stat directly). A status lists *ticks* and *modifiers*:
   - A **tick** is `{"when", "action", "every", "amount", "percent", "resource", "attribute", "chance"}`. `when` is `round_start`, `round_end`, `turn_start`, `turn_end` (the start or end of the bearer's own turn), `helped`, `harmed` or `saving_throw` (the bearer makes one). `every` (the four timed moments only) makes it fire on every *n*-th one. `action` is `damage` or `heal` (`amount` plus `percent` of the maximum of `resource`, life if left out; damage of a given `attribute`), `skip_turn` (only at `turn_start`; the turn is lost on a roll up to `chance` out of 100) or `end` (the token goes). Ticks that `damage` or `heal` don't start further `helped` or `harmed` ticks.
   - A **modifier** is `{"kind": "damage_taken" | "damage_dealt", "attribute", "factor"}` (damage of that attribute, or `all`, is multiplied by `factor`) or `{"kind": "stat", "stat", "amount"}` (the stat is raised or lowered while the token lasts). A stat that is not a resource has no current value of its own: it is its base, the worn gear and the bearer's tokens added up, and `Rules.stat_value(stat, geared, bonus)` sums and clamps them (never below zero, by default). Only the resources (HP and MP) keep a current value.
   - `duration` is in rounds (none: until something removes it) and `intensity` is `{"shape": "flat" | "rising" | "falling", "high", "low"}`, how strong the token is over its life: `flat` is always `high`; `falling` starts at `high` and reaches `low` on the last round; `rising` the other way. Everything a token does is scaled by its intensity (a modifier's factor eases towards 1). A status with no duration is flat.
   - A status placed again by the *same* source refreshes that source's token; a different source's token is its own.

**Who earns from a status.** A token's source is the actor behind everything the token does. Damage and healing from its ticks go through the usual path with the source as the actor, so `Rules.gauge_moved` sees the source earning it, at the intensity the token had. A tick that moves no gauge (a lost turn, say) is reported to `Rules.status_acted(fight, source, target, status, intensity, ratio)`, where `ratio` is the status's `xp_share` times the intensity: the share of the bearer's PXP (its potential experience, DragonStar's measure of what a character is worth) that the source is credited. By default the bearer owes the source that share of its PXP as an `XpDebt` (harm for a bad status, help for a good one), paid out with the rest of the experience when the fight ends.

Events: `StatusApplied`, `StatusTick`, `StatusRemoved` (with the reason: `expired`, `removed`, `ended` or `died`), `TurnSkipped` and `RoundEnd` (a round has gone by for the tokens; logged only when some fighter carries one). `fights.replay.apply_events` follows them, so tokens survive replays and spectators see them. A fight starts with the statuses it knows (`build_fight(layout, statuses)`; `fights.content.status_spec` makes one from a content row), and its snapshot carries them with every fighter's tokens.

## Standing statuses

A fight's tokens last rounds and go when the fight does. A *standing status* is a long-term one that lives between fights: a dialog places it with `add_status,target,status,seconds,locked|removable,label` on the talking hero, their team or their party (`hero`, `team`, `party`; a hero with no team or party takes the label branch). The dialog gives a number of seconds and the engine turns it into a wall-clock end time (`terraforma.wallclock`); 0 seconds lasts until removed, and placing the same status again renews it. `has_status,target,status,has|lacks,label` tests for one. A status that has ended is gone at once for every read, and the `ended_standing_statuses` housekeeping job deletes the rows. `GET /api/heroes/{id}/statuses` lists what a hero is under (its own, its team's and its party's, with the seconds left).

When a fight starts, each hero's live standing statuses go on its fighter as ordinary tokens (its own source, no round limit, for the whole fight), so ticks and modifiers work as for any token. A `locked` status is *unremovable*: `remove_good_status` and `remove_bad_status` skip its token. Deleting a hero, a team or a party deletes its statuses. A *guest pass* is a team's standing status with an end time that also sends the team out of its party when it ends (`standing.place(..., ends_party=True)`; the guild gives one, see below): the housekeeping sweep takes the team out of the party and its town visit, tries again on the next pass if a hero of it is in a running fight, and a team that leaves early takes the pass with it.

## Teams and their heroes

A hero never exists without a team. A team is made first, by its name, in the game client's Teams panel (`POST /api/teams`: `name`, and optionally `heroes`, each a `name` and a `job`); the player is taken to the team's own page (`/team/{id}`), where its heroes are made. A player has at most `Rules.max_teams` teams, and a team at most `Rules.team_max` heroes (the engine's screens draw at most 5, whatever `team_max` says). A team with fewer than `Rules.team_min` heroes is incomplete: it says so, and cannot play until its empty places are filled. The engine's defaults are 1, 4 and 8; the example game sets 3 teams. The calls under a team: `POST /api/teams/{id}/heroes` makes a hero in its first empty place while it has room, `.../heroes/{hero_id}/delete` removes one, `.../heroes/{hero_id}/replace` removes one and makes another in the same place, `POST /api/heroes/{id}/move` (`team_id`) moves one to another of the player's teams and `POST /api/heroes/swap` (`hero_id`, `with_hero_id`) exchanges two. Deleting a team (`POST /api/teams/{id}/delete`) deletes its heroes.

What may change once a team is saved is the game's to decide, with `Game(roster=...)` (a public interface): subclass `terraforma.heroes.hooks.Roster` and override `may_remove` (removing or replacing a hero), `may_move` (a move, and each hero of an exchange) and `may_disband` (deleting a team). Each returns None to allow the change, or why not (shown to the player as it is). The defaults refuse removing, replacing and moving, and allow disbanding. A game that sells a change (Vanguard Tavern: a Challenge Token purchase) charges in the rule, which runs in the call's transaction, so a change that fails afterwards is not charged; a game can instead call the engine's functions (`terraforma.heroes.service.replace_hero`, `move_hero`, `swap_heroes`, `remove_hero`) from an item's use effect. A game that wants them as ordinary play returns None, as the example game does for removing and replacing.

Where a new team starts is the game's too, with `Game(start=...)` (a public interface): subclass `terraforma.heroes.hooks.Start` and override `places(session, account)` to return `StartPlace(key, title, map, x, y)` entries (the capitals, say), where `map` is the map's name in the engine's world. By default none are offered and every new hero starts on the hub. `GET /api/start-places` lists the choices for the browser; `start` (a key) in the body of `POST /api/teams` picks one (the first place offered if none is sent; an unknown key, or any key when the game offers none, is refused with 422), and the same field on `POST /api/teams/{id}/heroes` places the first hero of a team that has none yet. The browser shows the picker in the add-a-hero form of a team that has no hero yet (a team is made with its name alone, and its first hero is what stands somewhere). A hero added to a team that has heroes stands where the team does, and a replacement stands where the hero it replaces did.

## Parties

A party is a collection of *whole teams* (`terraforma.parties.service`). A team joins whole and leaves whole, never split; a team is in at most one party; the smallest party is one team; and parties merge (all of the second party's teams join the first, in their order, only if they fit together). Teams from different accounts can share a party. A party stands on a map like everything else (where its first team's first hero stands; the hub for an empty team).

A party has a **leader**, a player (account), not a team: the player who founded it (`Party.leader_account_id`), then whoever accepts another party into theirs. `join_party` and `merge_parties` take `accepted_by`, the account of the accepting player, who must have a team in the receiving party; without it the leader stays. When the leader's last team leaves, the owner of the party's first team leads (`parties.service.leader_account` settles it), and a team in no party is led by its owner. A leader hands out the party's `assign` drops (see Held drops), opens or closes the party to asks and answers them at the guild (see The adventurers guild), and may treat the party at an inn when the game allows it (see Inns); a game can use `is_leader` for more.

How many heroes a party holds is the game's rule: `Rules.party_size`, 20 by default, and `Rules.group_size`, 5 by default, the size of the groups a fight's side is laid out in (four groups of five). A team joins only if there is a place for every one of its heroes, and a hero added to a team that is in a party needs a place too (the add-hero call follows the game's `party_size`). Deleting a team takes it out of its party, and an empty party goes with its last team.

Joining and merging are service functions, not server calls of their own: they take ids, and whoever calls them decides who may. The calls that reach them are a team's `play` (below) and the guild's (see The adventurers guild); the map will add its own interactions. A party becomes one side of a fight with `fights.build.party_side(session, party_id, rules)`: its heroes team by team, in the order the teams joined, in groups of `group_size` (`build_fight({0: await party_side(...), 1: ...})`).

A team enters the game when its player selects it to play: `POST /api/teams/{id}/play` (login and CSRF token; safe to repeat; refused with 409 for a team with no heroes) makes its party, a party of just that team, where its first hero stands. After that a team is never in no party; teams meet by joining and merging parties on the map. In a town the real party and its formation are kept, and each group of teams there acts as an *ethereal* party: `towns.service.acting_party(session, team_id)` says which party a team acts in right now (the whole real party, or in a town only the team's group, `ethereal=True`, never stored and gone when the real party is put back together).

## Art

A picture in a seed file (a tile's `art`) is a file name under the game's assets folder, drawn as one image, or a sheet reference `{"sheet": "knight", "frame": 3, "colors": "red_team", "animations": "knight"}` (a public format: the license exception covers it). Names are written without the extension, `frame` is which picture of the sheet (0, the first, if left out; then left to right and down: a tile kind of a map picks its own, so one sheet can be a whole tileset), and `colors` and `animations` are optional:

- `knight.png` is the indexed-color sheet, `knight.alpha.png` its transparency (an 8-bit gray image of the same size) and `knight.sheet.json` describes it: `frame` (`[w, h]`), `grid` (`[columns, rows]`), `frames`, `palette` (hex colors) and `alpha` (`false` for a sheet with no alpha file). The browser combines the two images on a canvas when it loads the sheet.
- `red_team.colors.json` is a color map, `{"#3050a0": "#a03030"}`. Each pixel is snapped to the nearest palette color, then swapped if the map lists it; colors the map leaves out stay. Colors are `#rrggbb` (the `#` may be left out, capitals are fine, and a color listed twice is an error). `python -m terraforma.tools.colormap` makes, checks, joins and previews maps (see Making color maps). One sheet serves many recolors, and each sheet-and-map pair is combined once and cached.
- `knight.anim.json` is the sheet's animations (the sections below say what it holds). One file belongs to one sheet, so a hero's fight art and map art, which are separate sheets, each have their own.

In the browser a game calls `shell.art.load(reference)`, which resolves to `{source, frame, grid, frames, palette, animations}`; `source` goes straight to `drawImage`, and `animations` is the animation set (or `null` when the reference names no animation file). `drawFrame(context, loaded, index, x, y, width, height, ops)` from `art.js` draws a frame of a sheet, changed by the transforms an animation asks for.

### Animations

`knight.anim.json` holds the sheet's named animations and aliases (a public format; the license exception covers it). The server checks every `*.anim.json` in the game's assets folder when it starts (against the frame count of the sheet with the same name, if there is one) and refuses to start on a bad one; it never plays them.

```json
{
 "animations": {
  "stand_right": {"frames": [0, {"frame": 1, "ms": 250, "rotate": 10}], "ms": 100, "loop": true, "sync": "shared"},
  "move_right": {"frames": [2, 3, 4, 5], "ms": 80}
 },
 "aliases": {
  "stand_left": {"of": "stand_right", "flip_x": true},
  "stand_up": {"of": "stand_left", "scale": 1.5, "pivot": [8, 16]}
 }
}
```

- An **animation** has `frames`: each a number (a frame of the sheet, counting as for `frame` above) or `{"frame", "ms", ...}` with its own time and transform. `ms` is how long each frame shows unless it says (100 by default), `loop` is on by default (off: it holds its last frame) and `sync` is `shared` (the default: everything playing it is in step, counting from the same clock) or `random` (each starts at a random moment of it).
- An **alias** is another name for an animation or another alias (`of`), with a transform of its own. A loop of aliases, an alias of nothing, a name that is both an animation and an alias, or a frame the sheet doesn't have is an error. Names are lowercase letters, digits and `_`, starting with a letter.
- A **transform** is `flip_x`, `flip_y`, `scale` (above 0, at most 16), `rotate` (degrees clockwise, -360 to 360) and optionally `pivot` (`[x, y]` in pixels of the frame; the frame's center if left out), allowed on a frame and on an alias. Within one transform the order is flip, then scale, then rotate. A frame's own transform comes first, then the aliases it was reached through, the one nearest the animation first.
- **Names.** Fight art (its own sheet) uses `base`, `equip`, `hit`, `die`, `flee`, `attack_close`, `attack_throw`, `attack_shoot`, `skill`, `spell` and `item`. Map art uses `stand_<dir>` and `move_<dir>` (`up`, `down`, `left`, `right`), and the map versions of actions that can also happen there, such as `cast` and `equip`, each with an optional `_<dir>`. A game may add names of its own and play them through its client code.
- **Back and front.** A fight shows each side from one view, with the direction suffix of the map names: the viewer's own side (the left) from behind, `_up`, and the other side from the front, `_down`. A fight sheet gives a view its own animation, `base_up`, `hit_up`, `attack_close_up`, and `base_down` or the bare name for the front; a name with no `_up` plays the bare name (the front), so a sheet drawn only from the front still works (monsters need no back view). Both views live in the same sheet and animation file; the fight card carries `data-view` (`up` or `down`). **Player heroes need a back view:** a personality with a job's key (the one a hero is drawn with) that has a `fight_art` must name an animation file that has `base_up`, as an animation or an alias, or the server refuses to start, naming the personality (`terraforma.animations.check_hero_back_views`). A personality with no `fight_art` stays a plain card.
- **Fallbacks.** The client plays the first of these that the file has: the name asked for, then `stand`, then `base`, each as `NAME_<dir>`, `NAME` and `NAME_down` (a missing direction becomes down). So a fight sheet's missing `hit` plays `base`, and a map sheet's `move_left` that is missing plays `move_down`, or `stand_left` if there is no `move` at all. A file with none of them plays nothing (the picture stays as drawn).
- **Playing.** `loaded.animations.play(name, {direction})` gives a player (or `null`); `player.frameAt()` says which frame to draw and which transforms to apply. All players share one clock (`Clock`, in `animation.js`, one `requestAnimationFrame` loop for everything that subscribes), so animations that are `shared` stay in step; a player who asks for less motion (`prefers-reduced-motion`) sees the first frame of each animation and the clock runs no loop. The server never depends on a frame.
- The map scene plays `base` for a tile kind whose `art` names an `animations` file (the example's cellar has a crystal), and sets the stage's `data-animated` to how many tile kinds do. A personality carries two pictures, `fight_art` (the fight sheet, with the fight names above) and `map_art` (the map sheet, with `stand_<dir>` and `move_<dir>`), each a sheet reference of its own, so one hero body can serve every job with a color map each. The server stores them (`personalities.fight_art`, `personalities.map_art`); the fight scene draws `fight_art` (below, under The browser client); the map scene draws `map_art` (below, under The browser client). A monster is drawn with its `personality`'s `fight_art`; a hero has no personality of its own yet, so it is drawn with the personality that has its job's key (the example's four jobs and four personalities), and with a plain card if there is none.
- **In a fight** the scene plays `base` for each fighter, and one-shots for what happens: `attack_close` when it attacks (the log does not say how far the blow reaches, so `attack_throw` and `attack_shoot` are for a game's own client hooks), `skill`, `spell` or `item` when it uses one, `hit` when it takes damage, `flee` when it flees and `die` when it dies (the last frame is held, and a fighter who is revived goes back to `base`). Each plays once, in the fighter's view (`_up` or `_down`), then the picture is back on `base`; a sheet without the name keeps playing `base` (the fallbacks above do not apply to these: a missing `hit` does not play `base` again from the start). Reduced motion, and Skip, play none of them. The fighter's card says which one is playing in `data-cue`.


## Maps

A map (`maps.json`; `terraforma.maps`) is a grid of tiles with a second grid of zones over it. Both are public formats (the license exception covers them). Walking, encounters, objects, doors and edge events are described below; the nearby list is under Reach.

- **Tiles.** `tileset` lists the kinds of tile: `name`, `passable` (default true), `poison` (default false; what it does is the game's rule), `encounter_rate` (out of 10000: the chance a step ending on it meets monsters) and `art` (a picture: a file name under the game's assets folder, or a sheet reference, see Art below). `tiles` is the grid, rows top to bottom, each tile a place in `tileset` (up to 512 by 512; every row the same length).
- **Zones.** `zones` lists the kinds of area: `name`, `encounters` (groups of `monsters`, keys in `monsters.json`, each with a `weight` against the others), `drops` (drop table keys, the area's own, see Item drops), `pvp` (whether parties may fight each other there) and `can_flee` (whether a fighter may flee from a fight there; on by default). `zone_tiles` is their grid, the same size as `tiles`; left out, the whole map is the first zone (which defaults to a plain one).
- **Edges.** `wrap_x` and `wrap_y` make walking off the left or right, top or bottom edge come out on the other side (a wrapped edge is no edge, and fires no edge event). `safe_steps` is how many steps a party takes on the map, from entering it and again after each fight, before it can meet monsters (`Party.steps` counts them; any fight, walking or not, starts it over).
- **Keys.** A map's `key` is its name everywhere else (`Position.map`, a hero's place); `name` is what players read. Maps are checked with the rest of the seed (monsters and drop tables named by a zone must exist). The default hub is a map without a grid (open ground, one plain zone); a `maps.json` row with the key `hub` draws it.
- **Loading.** Maps load into the engine's world on every start. A new key is added, a known one rewritten, and a map the seed no longer lists is kept (things may stand on it). `Map.revision` starts at 1 and goes up whenever a load changes anything about the map, so a client holding an older one can tell.
- **Asking a map.** `Map.normalize(x, y)` (wrapped, or None off the map), `Map.tile(x, y)` and `Map.zone(x, y)` give the tile kind and the zone at a place; off a grid they give open ground and a plain zone.
- **Walking.** The page proposes, the server decides. `GET /api/maps/{name}` gives a page what it draws (size, wrap flags, `revision`, tile and zone kinds and grids, never encounter rates, encounter tables or drops). The party's leader calls `POST /api/parties/{id}/route` with either `{"path": [{x, y}, ...]}` (tiles to pass, in order) or `{"destination": {x, y}}`; the server checks every tile is on the map and passable, fills the gaps between tiles that aren't neighbours with the shortest way (steps go up, down, left or right, through a wrapped edge as an ordinary step; at most `Rules.route_limit`, 100, steps in all) and answers `{map, revision, x, y, route, at}`: the route it will confirm, the tile the party stands on first. The page walks it and calls `POST /api/parties/{id}/route/step` with `{x, y}` as it arrives on each tile. The server confirms the next tile of the route (`confirmed: true`, the party moves there) or, if it can't (not the next tile, the map's `revision` changed, a party in the way, the party in a fight or apart in a town), answers `confirmed: false` with where the party really stands and ends the route, so the page goes back to that tile. `GET /api/parties/{id}/route` shows the route and position again, for a page that reloaded. Only the party's leader walks it.
- **Monsters on the way.** Each confirmed step ends with a roll: once the party has taken more than the map's `safe_steps`, the tile's `encounter_rate` (out of 10000) is rolled on a `WorldRng` stream for that party and that step, and a hit picks one of the zone's `encounters` by `weight` (those that fit `Rules.party_size`), starts the fight where the party stands and ends the route; the step's answer carries `fight` and `monsters`. Any fight started at a spot takes the zone's `drops` as its area drops unless the caller gives its own.
- **Objects.** A map's `objects` are the things a hero uses: chests, doors, signs, whatever the game draws. Each has a `key` (unique on its map), `name`, `kind` (the game's word, `chest` by default; the engine treats all kinds alike and the page may draw them differently), `action` (the kind of reach it takes: `open` by default, `search`, or a game's own), a tile `x`/`y` and a `script`: dialog text, the same language as an NPC's (see NPCs and dialog), so plain text is said, a `question` asks, and `add_item`, `have_item`, quest and status tags work as they do there. A hero uses an object with `POST /api/heroes/{hero_id}/objects/{object_id}/use` (login and CSRF token; no body). It is refused with 409 unless the hero is in reach of it (`Reach.map_object`, see Reach and the nearby list; by default within one tile) and out of a fight, and 404 for something that isn't there. The answer is the first step of the script as a conversation frame, `{"object": {id, key, name, kind}, "events", "prompt", "ended", "window"}`: `window` is true only when the script asked something of the hero (a question, an ack, an activity), which is when the page opens its dialog window; whatever else the script says is in `events`, to show without one. A script that asks goes on through the NPC calls (`GET /dialog`, `POST /dialog/next`, `POST /dialog/leave`), and the conversation ends if the hero leaves reach.
- **Doors and warps.** `warp,map,x,y,label` is a dialog tag the engine runs: it moves the party the hero acts in (and every hero of it) to that tile of that map, drops its route, starts its safe steps over, and *leaves the dialog* (the hero is somewhere else now). The label is where the script goes if the party can't go now (apart in a town, a hero of it in a fight). A door is an object whose script asks and then warps. The seed is checked: the map must be in `maps.json` (or be `hub`), and the tile on it and passable. `warp_visited,map,x,y,label` is the same, but only when every team of the party has been to a town on that map (else the label). **Visited towns:** each team keeps a list of the towns it has been to, one per map, written when a party it is in comes into a town (`towns.service.enter_town`; the spot is where it first arrived). A town stays on the list while its team does; whether it is still a town (the map is there and `Towns.is_town` still says yes) is asked when the list is read: `towns.service.visited_towns(session, towns, team_ids)` gives the towns *all* the given teams have been to (two teams: the places both may go to), and `GET /api/teams/{id}/town/visited` gives a team's own list. `warp_visited` only checks the map was visited; the tile is the one the script names.
- **Edge events.** `edges` gives a script for any of `north`, `south`, `east` and `west` (not for a wrapped axis: a wrapped edge is no edge). A route may end by stepping off such an edge, onto the tile just beyond the map; any other tile off the map is refused. The step is checked in like the rest, but the party stays on its last tile, the route is over, and the script runs for the leader's first hero in the party. The step's answer is `{confirmed: true, done: true, edge, x, y, dialog}` where `dialog` is the first frame of the script (`window` as above). The page learns which edges have events from `GET /api/maps/{name}` (`edges`, and `objects` with `key`, `name`, `kind`, `action` and tile; never their scripts).
- **Revision.** Adding, moving, renaming or removing an object, or adding or removing an edge event, raises `Map.revision` (a page can see them); changing a script does not.
- **Heroes follow the party.** A party's tile is the one that moves, and its heroes' tiles follow it (on every step and every warp), so what a hero can reach is measured from where the party is.
- **Parties in the way.** `Rules.party_blocks(mover, other)` says whether a party standing on a tile keeps another off it. By default none does. It is checked when a route is made (routes go round blocking parties) and at each step. A public interface (the license exception covers it).
- **PvP.** The engine's default `PvpZones.allows_pvp` now reads the zone's `pvp` flag (a map with no zones allows it nowhere, as before); a game's own `Game(pvp=...)` still overrides it.

## Fights between parties (PvP)

Where a party may pick a fight with another party is a rule, in two parts. The place: `Game(pvp=...)` (`terraforma.pvp.hooks.PvpZones`) says whether a spot allows PvP, `allows_pvp(session, map_id, x, y)`; the engine's default follows the map's zone flag (see Maps), so nowhere on a map with no zones. The range window: `Rules.may_start_pvp(attacker_pxp, target_pxp, allowed)` returns None if the fight may start, otherwise why not. By default it refuses where PvP is off, and where it is on it allows a target whose party PXP is at least `Rules.pvp_window` (0.85) of the attacker's, and always a stronger one. A party's PXP is the sum of its fighters' (`terraforma.pvp.service.party_pxp`), and `terraforma.pvp.service.refusal` runs both checks. These are public interfaces (the license exception covers them).

This is the step where a player who has met an enemy party on the map confirms they want to fight it: the game asks first, then makes the call. To pick a fight, a team's owner calls `POST /api/pvp/fights` with `team_id` (their own team; its party picks the fight) and `party_id` (the party to fight), with login and CSRF token. The fight starts with the caller's party as party 0 and the other as party 1, and each player commands their own heroes. It is refused with a 409 and the reason unless the other party is in reach for a fight (the game's `Reach.party` rule for the `fight` action: by default on the same map and within one tile, and in the same instance), neither is in a town or in a fight, the place allows PvP (on the tile of each party, when they stand apart) and the other party is inside the window. A team not in a party, or not the caller's, is refused too (404 for a team that is not theirs). The fight is where the caller's party stands. The nearby list (see Reach and the nearby list) shows the parties within reach, and a game that wants fights from farther away widens `Reach.party` (and `Reach.party_window` for the list). What a PvP fight pays out is the engine's ordinary result (experience, no gold or drops unless the game's Rules say so).

Vanguard Tavern's setup: towns are PvE only (unless lawless), everywhere else, dungeons and shared instances included, is PvP

        class Zones(PvpZones):

## NPCs and dialog

An NPC (`terraforma.npcs`) stands on a map at a tile, like a hero, and *dialog is how a hero uses a place*: a store, an inn or a church is a tag in what an NPC says, not a separate thing to walk up to. A game stands NPCs on its maps with `npcs.service.place_npc(session, key, name, map_id, x, y, dialog, counter)` (safe to run again: the NPC with that key is moved and rewritten; the dialog is checked, and a wrong one is refused with where it went wrong). `counter` is the NPC's row of counter tiles, `[(x, y), ...]`.

A hero talks from a tile on or next to one of the counter tiles (any of the eight around it) that the NPC is also next to; an NPC with no counter is talked to from the tiles around it. Who may talk to whom, and from where, is the game's rule of reach (see Reach and the nearby list): `Game(reach=...)`, `terraforma.reach.hooks.Reach.npc(session, action, hero, npc)` returns None or the reason not (a level, a quest, a time of day), and the default is that counter rule. What an NPC's dialog does with the tags the engine leaves to the game is `Game(npcs=...)` (`Npcs.tag`). A hero in a fight that is still running can't talk, and a conversation ends when the hero is no longer where they can talk.

The calls, each its own route under `/api/heroes/{hero_id}` (writes need login and CSRF token): `GET /npcs` (who this hero can talk to from here), `POST /npcs/{npc_id}/talk` (start; a hero is in one conversation at a time), `GET /dialog` (the conversation they are in and what it last asked), `POST /dialog/next` with `{"choice": n}` or `{}` (Next, or the index of an answer; null cancels), `POST /dialog/leave`. The server runs the dialog and decides everything; each answer is `{"npc", "events", "prompt", "ended"}`: `events` are what to show and play in order (`text`, and the cues `sound`, `music`, `mute`, `pause`), `prompt` is what the hero is asked, with `accepts` listing exactly what the server will take next (`choice`: the option indexes, `next`, `cancel`; anything else is refused with 409 and the conversation stays where it was) (`{"type": "ack"}` for Next, `{"type": "choice", "kind": "question|switch|inn", "options": [{"text"}]}`, or `{"type": "activity", "command", "parts"}`) or null once it ended. Where an answer leads is never sent to the browser.

The dialog language is DragonStar's, run on the server (the full list is at the top of `npcs/script.py`). A tag is quoted in backticks (two backticks show one); text outside tags is said; a text block ends at a line break or a tag. Flow tags the engine runs itself: `label`, `jump`, `team` and `party` (text for a player's teams or party, others jump), `question` and `switch` (asked after the text that follows; an answer jumps to its label, and cancelling goes to the question's own cancel label or on with the text), `inn` (Yes or No), `ack`, `end` (leave the dialog there) and the cues. The rest are the game's: `services`, `heal`, `recharge`, `select_team`, `resurrect`, `cure`, `uncurse` and the Yes of an `inn` (which the engine does itself when this returns None, see Inns) go to `Npcs.tag(session, hero, command, parts)`, which returns a label to go to, `""` to go on, or None for not handled; a tag it does not handle reaches the browser as an *activity* to run (the shop's calls, say), and the browser finishes it with `next`. The engine also runs the tags that read or change the game's state. `have_item,item,qty,scope,label` jumps to the label unless the party has at least `qty` of the item in one hero's pack; `add_item,item,qty,label` puts `qty` in the talking hero's pack (all or nothing: it jumps if they do not all fit); `remove_item,item,qty,label` takes them from the talking hero (it jumps if they do not have that many). `quests,category,level,op,n,scope,label` compares the quests a team completed (`level` a whole number or `any`) with `n`, `quest_marker,quest,op,value,scope,label` compares a team's marker for a quest in progress with `value` (no marker is 0), and `set_quest_marker,quest,value` sets the talking hero's team's marker (0 clears it). `op` is `eq`, `ne`, `lt`, `le`, `gt` or `ge`; `scope` is `any` (any team of the party, for items any hero), `lead` (the party's leading team: the leader's first team in the formation) or `each` (every team, for items a hero of every team). The party is the one the team acts in right now (`towns.service.acting_party`), so in a town a team speaks only for its own group. Quests belong to the *team*: `terraforma.quests.service.complete(session, team_id, category, level)` adds to its permanent record (the engine awards nothing itself; a game calls it), and markers are whole numbers up to 1000000. `warp,map,x,y,label` moves the party to a tile of another map and leaves the dialog (see Maps, Doors and warps). The engine also runs the Challenge Token and gold tags, which is how a perk is sold (a perk is a dialog, not a table): `have_tokens,amount,label` jumps unless the talking hero's account holds that many Challenge Tokens, `spend_tokens,amount,label` takes them (one ledger entry, reason `spend`; it jumps if the account holds fewer, taking nothing) and `add_tokens,amount,label` pays them as a quest reward (reason `quest`, cut to the room `Rules.challenge_purse_cap` leaves; the daily cap, which is for fights, does not apply; it jumps to the label for an admin's account, who earns tokens only fighting as a player, or when no room is left) and `add_gold,amount,label` pays gold into the talking hero's purse, wherever the game's economy keeps it. Each step of a conversation runs in a savepoint: if one fails (a status that does not exist, say), whatever the step had already done, items, tokens and gold, is undone. Two differences from DragonStar, both stricter: a label that is neither defined nor `end` is refused when the dialog is placed (DragonStar silently leaves), and a choice at the very end of a text is still asked. The shops are *activities* the engine runs from the conversation (next section); the inn is described after them.

**Dialog trees.** A dialog is limited to 20000 characters, so a long one (a guild's quest board, say) is split into *trees*, rows of the `dialogs` table with a `key` (`dialogs.json` in the seed, or `npcs.service.place_dialog(session, key, text)`). `include,key` runs the tree with that key from its start, like a subroutine, and it works in an NPC's dialog, a map object's script, an edge event and another tree. The tree's own ending decides what happens next: `end_return` goes back to just after the `include` that entered it, and `end_complete` ends the whole dialog however deep it stands (`end` is `end_complete`). A tree that simply runs out of text goes back too, and so does a jump to the `end` label, which is the end of the tree it is in; at the top (the NPC's or object's own text) running out, `end` and `end_return` all end the dialog. Labels belong to their own tree: the same name may be used in two trees, and a jump never leaves its tree, so a tree gives its caller back what it asked (a `question`'s cancel label `end` is a way back to the board). A conversation that is waiting in an included tree (a question, a Next, a shop) is kept with its way back (`npc_talks.tree` and `stack`; the browser sees none of it), and trees may include trees up to 8 deep. The seed is refused if an `include` names a key `dialogs.json` doesn't have or if trees include themselves in a circle; a game that places trees from code finds the ones never placed with `npcs.service.missing_includes(session)`, and a tree that is missing when a dialog reaches it ends that conversation with the reason. A quest board is then a short tree that checks the team's standing and includes one tree per quest it offers, each ending in `end_return`.

## Reach and the nearby list

This is an MMO: a hero is rarely on the same tile as what they want, and parties move. So interaction is by *proximity*, and what counts as in range is the game's rule (`Game(reach=...)`, `terraforma.reach.hooks.Reach`; a public interface, the license exception covers it). An *action* is a string: the engine's are `talk`, `invite`, `open`, `search`, `fight` and `help`, and a game may add its own. There is one rule per kind of target, so a game can set them apart:

- `Reach.npc(session, action, hero, npc)`: whether the hero is in range of the NPC for the action, None or the reason not. By default a `talk` is the counter rule (see NPCs), and any other action is from the tiles around the NPC.
- `Reach.map_object(session, action, hero, obj)`: the same for a chest, door or other map object (see Maps), for the object's own action. By default within one tile, on its map.
- `Reach.party(session, action, actor, party)`: the same for another party, where the actor is a hero or a party. By default within one tile, on the party's map. `Reach.party_window` (1) is how far, in tiles, a party can be and still be asked about; the engine only asks the rule about parties inside it, so a game whose rule reaches farther raises it (or sets None to ask about every party on the map).
- `Reach.lists_parties(session, action, hero)`: whether the nearby list for the action shows parties after the NPCs (by default for `talk` and `invite`, not for the rest).
- `Reach.valid_for(action)`: how many seconds the browser may show a list before asking again (`valid_seconds`: 60 for `talk` and 300 for `invite`, `default_valid` for the rest). Every call that acts asks the rule again when it runs, so a stale list is refused cleanly rather than trusted.

Distances count a diagonal step as one tile and go round a wrapped edge of a map (`terraforma.reach.hooks.distance`). `Npcs.can_talk` is gone: the NPC calls ask `Reach.npc` with `talk`.

`GET /api/heroes/{hero_id}/nearby/{action}` (login; the hero must be the caller's; `action` is lowercase letters and underscores, up to 32) answers `{"action", "valid_for", "nearby"}`. `nearby` lists the NPCs first, then the map objects whose `action` it is, then the parties, each group nearest first and ties by name and id, at most `Rules.nearby_limit` (20) in all so a crowd does not flood it. An NPC is `{"kind": "npc", "id", "key", "name", "distance"}`; an object is `{"kind": "object", "id", "key", "name", "object": <its kind>, "distance"}`; a party is `{"kind": "party", "id", "teams": [{"id", "name"}], "distance"}`, naming only the teams their players made visible (a hidden team is just part of the party). The hero's own party and parties in a town are left out. `GET /api/heroes/{hero_id}/npcs` still lists only the NPCs the hero can talk to.

Helping a party with an item is built (see Using items in the field). Fighting a party from range is built (see Fights between parties). Helping a party with an ability is built too (see Using items in the field, "Abilities in the field").

**Talking to a party.** `GET /api/heroes/{hero_id}/talk/party/{party_id}` (login; the hero must be the caller's; a read, so no CSRF token) says what the hero's side could do with another party it can reach for a `talk`: `party_id`, `teams` (only the teams their players made visible), `stance` (what `Rules.party_stance` makes of the hero's team's view of the party's teams: `ally`, `enemy` or `neutral`) and `options`, two entries `{"action", "available", "reason"}`. `fight` is the PvP the game asks about first; it is on offer unless `Rules.may_challenge(stance)` refuses (by default allies are not offered a fight) or `pvp.service.check_fight` does (the same checks `POST /api/pvp/fights` runs: reach for a `fight`, the place's flag on both tiles, the range window, a town, a fight, a pending join offer), and the player answers it with that call. `help` is using an item on one of its heroes (see Using items in the field): on offer unless `Reach.party` for `help` or `Rules.may_help(stance)` refuses. So an enemy party offers a fight, a friendly one help, and a mixed one (teams of both stances) both. Talking changes nothing: a pair of teams that never met is read at `Relations.initial` and no relationship is formed. It is refused with a 409 and the reason when the party is out of reach for a talk, is the hero's own, or the hero is on no team, and with a 404 for a party that does not exist. `Rules.may_challenge` only shapes this menu, so a game that has allies fight on purpose (a contract for fair PvP) still can through the PvP call.

## Shops

A shop is an NPC's dialog waiting on a `vend`, `hawk` or `shop` tag; there is no shop table. A hero shops from their conversation, so the NPC's reach rules apply (walking away ends it) and the browser never names a price. The calls, each its own route: `GET /api/heroes/{hero_id}/dialog/shop` shows the wares with prices, what the hero could sell and for how much, and their gold; `POST .../dialog/shop/buy` (`item`, `qty`) and `POST .../dialog/shop/sell` (`position`, `qty`) need the CSRF token and are limited like trades; `POST .../dialog/next` leaves the shop and goes on with the text. A hero in a fight that is still running cannot talk, so cannot shop. In the browser the shop is part of the Talk panel: a ware the server marks `stacks: false` (equipment) is bought one at a time with no quantity box, and a purchase says how many did not fit in the pack. There is no player-to-player market: an auction house is not planned, so the shop is the whole of the market on screen.

- `vend,item1,price1,item2,price2,...[,cancel]` sells exactly the listed items at the listed prices, as in DragonStar. It never buys.
- `hawk,margin,item1,price1,...[,cancel]` buys: a listed item at its listed price, any other item at its own price times `margin` percent (rounded half up). It never sells.
- `shop,key[,cancel]` sells and buys by the game's rules: `Game(market=...)` takes a `Market` that says what the shop with that key sells and for how much: `level(session, rules, shop, hero, party)` (by default the total PXP of the heroes of the teams acting with the hero's), `stock(session, shop, level)` (by default every active item with a price, priced at or under the level, cheapest first), `price(shop, item)` and `sell_percent(shop, item)` (75 by default, which a game can raise or lower for one item, so a quest such as "the area needs healing herbs" makes the economy the reward). Stock is a function of the economy level, the same thing as how hard the region is, so a shop has no seed. This is a public interface (the license exception covers it).

Gold moves through the game's economy (`Game.economy`: the team's purse by default). A purchase puts what fits in the pack and charges only for that (equipment is bought one at a time; nothing fitting is refused), and a sale that would pay nothing is refused, so nothing is thrown away for no gold. A worn item is taken off when it is sold.

## Inns

`inn,price,label` asks Yes or No (No goes to the label). When the game's `Npcs.tag` leaves the Yes to the engine (it returns None, the default), the engine rests the party: the price is taken once per team from the talking hero's purse through the game's economy, and every hero of each team that paid rests through `Rules.rest` (full HP and MP by default, the dead revived as the game decides). By default each team pays its own: the talking hero's team rests and pays. `Game(inn=...)` takes an `Inn` whose `leader_pays(session, hero, price)` (False by default) lets the leading team treat the teams acting with it: when the leading team's player talks, its purse pays for its own team first and then the others in formation order, as many as it can afford. Teams that were not paid for do not rest. If no team can pay, the answer is refused with 409 ("not enough gold") and the conversation stays where it is, so the player can answer No. A hero on no team rests alone and pays their own gold. `Inn.price(session, hero, team_id, price)` (the tag's price, unchanged, by default; never below zero) is asked for each team that rests, so a game can charge teams differently (a guild member's discount); when the leader treats the party, each team's price is still its own. A game that wants something else (a room that is full) answers the Yes in `Npcs.tag` itself. This is a public interface (the license exception covers it).

## The adventurers guild

A game's guild (the Vanguard Tavern, say) is an NPC whose dialog uses the guild's tags. Three are *activities* (the browser calls the guild's routes, and the dialog waits on the tag): `add_team` lets the player add one of their own teams to the party their hero is in, `find_party` lists open parties on the hero's map and lets the hero's team ask one to take it, and `party_requests` lets the party's leader accept or decline the asks. A price is whatever the dialog charges before the tag: adding a team and asking a party each finish the activity and go on with the dialog, so one payment buys one use. For adding a team a Challenge Token price can instead go in the tag, `add_team,tokens`: the tokens are taken in the same change that adds the team, so a team that can't be added (or an account that can't pay) costs nothing. `open_party,on|off,label` (a tag the engine runs itself) opens or closes the hero's party to asks; only the leader may, anyone else goes to the label.

The calls, under the conversation like the shop's: `GET /api/heroes/{hero_id}/dialog/guild` shows what the tag allows now (own teams that could be added; open parties, with places left and the names of visible teams only; the requests to the hero's party, for its leader), `POST .../add-team` (`team_id`), `POST .../ask` (`party_id`) and `POST .../answer` (`request_id`, `accept`). The writes need the CSRF token and are limited like trades. A team can be added if it is the player's own, has heroes, is not in the party, and is in no party or in a party of just itself (which it leaves, so that party is gone). Its heroes then stand where the talking hero does. Accepting an ask brings the asking team into the party (it leaves its own), and the leader who accepted it leads. Teams join whole and only where the party has room for all of them. In the browser each tag is a screen in the Talk panel: a list of the teams that could be added, the open parties (a team that keeps its name private is shown as such), or the requests with Accept and Decline (which stay on the screen and refresh it); a refusal shows in the server's own words.

Parties normally refuse changes while apart in a town; the guild is in a town, so its joins are allowed there. The joining team becomes a group of the town visit of its own, not waiting, so the party leaves only once it is ready as well. `Game(guild=...)` takes a `Guild` whose `may_ask(session, team_id, party_id)` says whether a team may ask a party (None if so, otherwise why not); by default the team must be an ally: in an alliance with one of the party's teams, or the same player's. `Guild.guest_pass(session, team_id)` returns a `GuestPass(status, seconds)` (default None) for a team a player adds with `add_team`: the team gets that standing status as a guest pass and leaves the party when the time runs out (the status can be a plain one with no effects). These are public interfaces (the license exception covers them). Requests are removed with their party or team.

## Weekly quests

Each team may be offered one quest a week (weeks run Monday 00:00 UTC to the next Monday), meant as a one-shot: failing it loses it for the week. The quest comes from a *template* that fits the team, or is *generated*. The engine does the plumbing and keeps the contents the game's: a quest is a name, a level and a `spec` dictionary of the game's own (goals, reward, which dungeon), which the engine stores and hands back without reading it.

- **The draw.** `POST /api/teams/{team_id}/weekly-quest/offer` gives the team its quest for this week (the same one if asked again; `quest` is null when the game makes none for it) and `GET /api/teams/{team_id}/weekly-quest` reads it. The draw uses a stream of the world's seed named for the team and the week, so it replays. The quest's level is the team's level plus its relative difficulty. Among the active templates whose `min_level`..`max_level` holds that level one is drawn by `weight`; the quest is then `WeeklyQuests.scale(template, level)`. Otherwise (or when `use_template` says so) `WeeklyQuests.generate(rng, team_id, level)` makes one up.
- **The game's hooks.** `Game(weekly_quests=...)` takes a `WeeklyQuests` (a public interface: the license exception covers it): `level(session, team_id)` (default: the average hero level), `difficulty(session, team_id)` (default 0: levels harder or easier than the team), `use_template(rng, fitting)` (default: a template whenever one fits), `scale(template, level)` (default: a copy of the template's spec) and `generate(rng, team_id, level)` (default None: the game makes none, so a team no template fits has no quest that week). Draw only from the `rng` handed in.
- **Playing it.** The game's dungeon and dialog call `quests.weekly.start(session, quest_id)` (this week's quest only) and `finish(session, quest_id, won)`; there is no player call for either. A won quest is added to the team's quest record (`quests.complete`, category `weekly`, at the quest's level); a quest started in time may finish after the week turns, but not after its own deadline. Instancing (a private dungeon per team) is its own slice.
- **The time limit and the penalty.** A quest taken has a wall-clock limit: `WeeklyQuests.limit_seconds(level)` (a day by default) after `start`, kept as the quest's `started` and `deadline` (seconds since 1970; the player's view shows them and `failure`). Nothing runs on a timer: a started quest past its deadline fails with `timeout` the next time anything touches the team (`offer`, `start`, `finish`, `active`), and a win reported late is that same timeout, not a win. A loss reported in time fails with `poor_performance` (`finish(session, hooks, quest_id, won, reason)`; `reason` may also be `timeout`). Either failure calls `WeeklyQuests.penalty(session, team_id, quest, reason)` once, which does nothing by default: the game decides what failing costs (the rotating quest slots have the same hook). A team takes one weekly quest at a time, so `start` is refused while last week's is still in time. `start`, `finish` and `active` now take the game's `WeeklyQuests` as their second argument.
- **The dialog tag.** `weekly_quest,offer|start|finish_win|finish_lose,label` acts on the talking hero's own team's quest: `offer` gives this week's (made if need be; the label if the game makes none or the team already finished it), `start` takes the offered quest (the label unless one is offered), and `finish_win` / `finish_lose` end the active one (the label if none is active; a quest started last week can still be finished). A board offers it and the dungeon's exit finishes it. The tag reads the game's `WeeklyQuests` through the request's database session.
- **Generated quests are kept.** Every generated quest stays as a row (a deleted team leaves them behind, owned by nobody) so it can become a template. An admin lists them with `GET /api/admin/weekly-quests` (`promoted=true|false`, `after`, `limit`) and promotes one with `POST /api/admin/weekly-quests/{id}/promote` (`key`, and optionally `name`, `min_level`, `max_level`, `weight`, `spec`). Without tweaks the template keeps the quest's name and spec and fits teams at exactly its level; each generated quest can be promoted once.
- **Templates by hand** are `quest_templates.json` in the seed (see Seed data).

### Ranks and gates

A team has **points** and a **rank** with each guild, kept per team like quests (`guild_standing`). A guild is just a name the game picks in its dialog text (`vanguard`, `crown`); the engine knows no guilds. A rank is a whole number, 0 the lowest and 99 the highest; the game names its own (Vanguard Tavern: E is 0, D 1, C 2, B 3, A 4, S 5). Points only grow, and a rank changes only when the dialog sets it, so a promotion quest is a dialog that checks the points, runs the quest and then sets the rank. Seven dialog tags (see Dialog text in `npcs/script.py`) are the whole interface:

| Tag | Does |
|---|---|
| `add_guild_points,guild,n` | the talking hero's team earns n points (1 or more) |
| `set_guild_rank,guild,rank` | the team now holds that rank |
| `guild_points,guild,op,n,scope,label` | the label unless the team's points compare true with n |
| `guild_rank,guild,op,n,scope,label` | the label unless the team's rank compares true with n |
| `guild_rank_any,scope,label,guild,min,...` | the label unless the team holds at least `min` with at least one of the guilds listed (up to 8 pairs) |
| `party_gate,guild,average,lowest,highest,pxp_min,pxp_max,label` | the label unless the party passes the gate |

`scope` and `op` are those of `quests`. **`party_gate`** is a quest's entry rule for the party the hero acts in: the teams' ranks average at least `average` (a number such as 1.5), every team has at least `lowest`, the best team has at least `highest`, and the party's strength (`Rules.pxp` added up over the heroes of its teams) is at least `pxp_min` and at most `pxp_max` (0 for no ceiling). A D average with at least one B is `party_gate,vanguard,1,0,3,0,0,no`. A gate that asks for strength needs the game's `Rules`, which the dialog routes pass in. **Standing elsewhere.** Every guild tag takes any guild's name, so a guild can gate on a team's standing with a different one: `guild_rank,aldermere,ge,3,any,no` asks for rank 3 with Aldermere's guild. Guilds do not share a rank scale (Vanguard's lowest rank is about a B or an A elsewhere, depending on the guild), so the game writes the rank each guild's door asks for. **`guild_rank_any`** takes several, and passes a team that meets one: `guild_rank_any,any,no,aldermere,3,sunvale,3,ironhand,4` lets in a team with rank 3 in either kingdom or rank 4 with the company. The scope is that of `guild_rank` (`each` needs every team of the party to meet one). A game's own code asks the same with `terraforma.guild.ranks.meets_any(session, team_id, [(guild, lowest), ...])`. A team that is deleted takes its standing with it.

## Rotating quests

A slot is a place where one quest at a time is offered and the quest changes now and then: a guild's rank S promotion that changes every few months, say. The engine knows no guilds and no ranks: a slot has a `key` and the game's own `guild` and `rank` labels, which its dialogs use. Weekly quests (above) are one per team per week; a slot's quest is the same for every team and lasts a whole period.

- **The schedule.** A period lasts a random whole number of days from the slot's `min_days` to `max_days`, drawn from a stream of the world's seed named for the slot and the period, so a schedule replays. A higher tier simply gets a longer range, because it takes far more preparation. A slot's first period begins when the slot first reaches the database; changing a slot in the seed later does not start it over or change the periods already made. Nothing runs on a timer: a period's row is made the first time anyone asks during it (a period nobody asked about leaves no row), so any server of a cluster gives the same answer.
- **Which quest.** The templates tagged for the slot (`slot` in `quest_templates.json`, the slot's key) are drawn by `weight`, never the one the slot held just before when another fits. With no active template for the slot, `RotatingQuests.generate(rng, slot, seq)` makes one up (`Game(rotating_quests=...)`, a public interface: the license exception covers it); with that returning None (the default) the slot offers nothing for the period. A slot's templates are never dealt as weekly quests, and their levels mean nothing. A quest's `spec` is the game's own and the engine never reads it.
- **Taking it.** `POST /api/teams/{team_id}/slot-quests/{slot}/offer` gives the team its hold on the slot's quest of the moment (the same one if asked again) and `GET /api/teams/{team_id}/slot-quests` shows what the slots hold and the team's standing with each (it makes nothing: a slot nobody asked about this period is left out). The game's dialog and dungeon take and finish the quest, with the `slot_quest,slot,offer|start|finish_win|finish_lose,label` dialog tag or `quests.rotation.start` and `finish`. `slot_template,slot,template,label` goes to its label unless the quest the slot holds now was drawn from that template (never for a quest the game generated), which is how one dialog sends a team to the dungeon of whichever quest the slot is offering. A team takes one quest of a slot at a time, and has one try per period. A won quest is added to the team's quest record (`quests.complete`, the category is the slot's key, the level its rank).
- **Obligations (a guild's "F" rank).** A slot with `obligation: true` is a duty of the guild's members instead of a step up: no rank is needed to take it, and a team with a standing in the slot's `guild` (it has earned points there; `GuildStanding.joined_at` says since when) owes the quest of every period that began after it joined. A period's quest the team never took, or took the offer of and let lapse, calls `RotatingQuests.penalty` with the reason `ignored`, once per period (recorded as a lapsed row, so any server gives the same answer), the next time anything touches the team, for at most the last 12 periods (`rotation.MAX_OWED`); a period nobody asked about has no quest and owes nothing, and one the world ended early owes nothing. Doing it needs no engine support beyond the quest record: a completed duty is recorded in the category of the slot's key, so a promotion board can ask for it with the `quests` dialog tag. A duty taken and failed (timeout or poor performance) is penalized as any quest is.
- **Time limits.** Every quest has a wall-clock limit: `limit_days` after the team took it, and never later than `grace_days` after the quest rotated out of the slot (the area may be gone by then). A quest not taken before the rotation lapses (nothing lost). A team past its deadline has failed with the reason `timeout`, whatever it would have done: this is settled the next time anything touches the team, not on a timer.
- **Failing costs what the game says.** `RotatingQuests.penalty(session, team_id, slot, reason)` is called when a team fails, with `timeout` or `poor_performance` (the reason a dialog's `finish_lose` or a dungeon gives); it does nothing by default. It is never called when the world ended the quest.
- **The world ends a quest.** `POST /api/admin/quest-slots/{slot}/end` (an admin only) or `quests.rotation.end_early` ends the slot's quest now, because the world changed under it: every team that held it is done with it (status `ended`, no penalty) and the next ask starts a new period with a fresh draw.

## The quests the world needs

A rotating slot (above) only helps a player if its quest suits them. `terraforma.quests.needs` finds the strengths of party nobody has anything to do for and makes a quest for them from the monsters the world already has. It generates no monsters: it *promotes* an existing one to a boss (or a gang), scaling its stats up. The game lists the strengths to watch with `Game(needs=...)` (`quests.hooks.Needs`, a public interface: the license exception covers it); the default lists none, so nothing happens.

- **Bands.** `Needs.bands()` returns `Band(key, slot, pxp_min, pxp_max, stall_seconds, min_teams)`: a range of party strength (`Rules.pxp` added up over a team's heroes, the same measure a `party_gate` uses) and the rotating slot that should serve it. A band is judged only while at least `min_teams` teams stand in it (`pxp_max` 0 is no ceiling).
- **A gap** is either of: no active template of the band's slot says it is meant for strength overlapping the band (`pxp_min` and `pxp_max` on `quest_templates.json`; a template that says nothing about strength could be meant for anyone and does not count), or, with `stall_seconds` above 0, no team in the band has completed a quest for that long (the team's creation time stands in for one it never did).
- **The boss.** `Needs.target(band)` is the strength to aim for (the ceiling, else half as much again as the floor). `Needs.gang_size(rng, band)` says how many monsters share it. The candidates are active monsters worth between an eighth of their share and all of it; one is drawn by strength from the world's `WorldRng` (`quest-need` streams, so a replay gives the same pick), or the game picks with `Needs.pick(rng, band, candidates)`. Its stats are multiplied (never more than 60 times) until it reaches the share, and `Needs.extras(rng, band, monster)` may add abilities or anything else the game keeps. With no fitting monster, nothing is proposed (a warning is logged).
- **The proposal.** A `QuestProposal` records the band, the reason (`no_fit` or `stalled`), a `name` (`Needs.name`) and a `spec` holding the bosses (monster, scale, resulting PXP, extras). A band has one open proposal at a time (the database enforces it), so a second server or a repeat run makes nothing. `Needs.needs_approval(band)` says whether it waits (`proposed`) or goes live at once; approving makes a template `need-<id>` for the band's slot, with the band's strength window, which the slot offers from its next period (an admin who wants it now ends the slot's quest). `GET /api/admin/quest-proposals` (login; admins), `POST .../{id}/approve`, `.../reject` and `.../retire` (the template goes inactive) and `POST /api/admin/quest-needs/run` (all admins only; login and CSRF token; each its own route and rate-limited) are the portal's calls.
- **The boss fight.** A live proposal's quest holds its bosses in `spec["bosses"]`, and the dialog tag `slot_boss,slot,fight|won|lost,label` plays them (`terraforma.quests.bossfight`). `fight` starts an ordinary fight (`fights.live.start_party_fight`, which now also takes ready-made `foes`) between the whole party the hero acts in and the bosses as promoted (`quests.bosses.fighters`: the monster's stats times its scale, plus the game's extra abilities), and leaves the dialog. It goes to its label when the team took no quest of the slot, the quest has no bosses (a hand-made or generated one), or the party cannot fight (apart in a town, a hero already in a fight). Every team of the party that took the same quest is tied to the fight (`QuestBossFight`; swept with the fight). Nothing in the fight code knows about quests: the quest is settled when a dialog asks, so a boss's fight ends like any other. `won` finishes the team's quest as won when the team won the fight (the fight's own scoring: a hero stands and every enemy has gone); `lost` finishes it as failed with `poor_performance` (so the game's penalty applies) when the fight ended and the team did not win, fled included. Each goes to its label while there is no fight, it is still running, or it ended the other way, so a dungeon's last room asks `won`, then `lost`. A game that wants a second try, or a different way to judge, uses `fight` and the quest calls (`slot_quest,...,finish_win`) and never `lost`.
- **Supply quests.** The same run looks at the living world's settlement supplies (see Realms). `Needs.supply_floor(settlement, material)` is the whole percent of capacity a live settlement's supply may fall to before the world needs help (0, the default, asks for nothing, so a game names a floor for the materials it cares about) and `Needs.supply_slot(settlement, material)` the rotating slot the quest goes in (empty makes no quest). Below the floor, a `QuestProposal` with the reason `supply` is made, with the `spec` `{"supply": {"settlement", "material", "amount"}, "band", "reason"}`; `Needs.supply_amount` (by default what fills the supply to half its capacity), `Needs.supply_name` and `Needs.needs_approval` (given a `Band` keyed `supply-<settlement id>-<material id>`) work as for bands. `Needs.supply_reward(rng, settlement, material, amount)` (nothing by default) names what the players are given for the goods, a small JSON object of the game's own (the item a town's crafter makes from a rare material, gold, guild points) that the quest carries as `spec["reward"]` for the game's dialog to hand out; the engine only carries it, and `rng` is the quest's own stream so a replayed world picks the same one. A settlement and material have one open proposal at a time. The level is read at the world clock and not changed by the run. When the gap closes (the supply recovered, or the settlement fell to ruins) the open proposal is taken back: rejected while it waits, retired when live (the game's `dungeon_gone` is not involved, since a supply quest has no dungeon unless the game's own dialog makes one). The game's dialog, when the players finish, calls `terraforma.quests.needs.deliver(session, spec, amount=None)`, which adds the goods to the settlement (up to its capacity, returning what fitted; nothing for a settlement no longer live). Like the rest of `Needs`, these hooks are a public interface (the license exception covers them).
- **When it runs.** The housekeeping job `quest_needs` (once a pass, on any server). - **The dungeon is the game's.** When the engine proposes a quest it calls `Needs.dungeon(session, rng, band, bosses)` (async, in the same transaction as the proposal). The game builds whatever place holds the fight (a map in the database, a pick from maps it has, or nothing: None, the default) and returns a JSON object of its own, kept in the quest's `spec["dungeon"]` and copied to its template, which the game's dialog reads (`slot_template` picks the dungeon of whichever quest the slot offers). `rng` is the stream the bosses came from, so a replayed world builds the same dungeon. If the hook raises, or returns more than a spec may hold, that band is skipped for the run (logged) and tried again at the next one. `Needs.dungeon_gone(session, proposal_id, dungeon)` is called when an admin rejects or retires the quest, so the game may take the place down (teams that took the quest keep it, so wait until they are done). The game puts a `slot_boss` object in the dungeon's last room.

## Maps kept for reuse

The engine generates no maps; a game does (a dungeon for a quest, a cellar, an instance). `terraforma.maps.library` is the memory it can use so the same kind of place is not generated again and again. `library.save(session, game_map, key, replace=False)` keeps a copy of a map under the game's own `key` (up to 64 characters; a key already saved is refused unless `replace`), `library.instantiate(session, saved, name, title=None)` makes a new map called `name` (a free map name) from it, and `library.reuse_or_make(session, world_id, key, name, make, title=None, review=True)` does both: a copy when an approved map is saved under the key, else it calls the game's async `make()` (which builds a map called `name`), returns it, and, when nothing is saved under the key yet, keeps a copy of it. `find`, `listing` and `forget` read and drop the saved copies (maps made from one stay). A copy holds the map's grids and flags and its object and edge rows with their scripts, and nothing that happens on the map: NPCs belong to the seed, and parties, fights and instances are never copied. A copy is a map of its own, so changing one changes neither the saved copy nor another copy. **Review.** Nobody has looked at a generated map, so a saved map starts `proposed` and is not copied until an admin approves it (`library.review(session, id, approve)`; a rejected map is never copied; a map decided already is refused). Until then every place that wants one still gets a map from the game's `make()`, and the proposed copy is neither used nor replaced. A game that trusts its generator passes `review=False` to `save` or `reuse_or_make` and its maps are approved at once. Saving over a key with `replace=True` needs a new review. The admin's calls (login; admins only; the three that change something need the CSRF token and are rate-limited; each its own route): `GET /api/admin/saved-maps` (key, title, size, number of objects, status, uses), `POST /api/admin/saved-maps/{id}/approve`, `.../reject` and `.../forget` (drops it; maps made from it stay, and the game may propose the key again). The admin page's Saved maps section uses them. The rule for what shares a key is the game's (a dungeon style and size, say): a `Needs.dungeon` that builds its dungeon with `reuse_or_make` gets one generated map per key and a copy for every later quest. `SavedMap` rows are per world, and `uses` counts the copies made. This is a public interface (the license exception covers it).

## Planned and live state

What an admin authors as settings is a *settings document*, kept twice: the **live** state (the latest committed snapshot, which the running game reads) and the **planned** state (one editable draft). Every admin edit touches the draft only; nothing is live until it is committed. `terraforma.gamestate` holds the machinery.

- **The document** is `{"format": 1, "sections": {name: {...}}}`. A game lists its sections in `Game(state_sections=...)` (a public interface: the license exception covers it). A `Section` has a `name`, a `default()` (the empty section), a `check(value, document)` that returns what is wrong, as sentences, and an `async apply(db, value)` that makes the database match the live value (called inside a commit's transaction and at every start of a server that lists add-ons; it must give the same result however often it runs; nothing by default). Names must be distinct. The engine's own section `components` is always there (see Add-ons).
- **The hash** is SHA-256 of the canonical JSON (sorted keys, no spaces), so equal states have equal hashes. A snapshot is stored as `ExactJSON`, never changed, and carries who committed it, when, and an optional note. A fight stores the hash of the snapshot that was live when it began (`fights.state_hash`; none: no snapshot had been made yet, which is the game on its defaults), so a recording can be checked against the add-ons and rules it ran under.
- **Check** finds every problem: wrong format, a section the game doesn't have or one that is missing, a section that is not an object, and each section's own checks. **Commit** needs the draft's hash (the one the admin read, so a draft edited since is refused with 409), runs the check, refuses an unchanged draft, and moves the one live pointer to a new snapshot. **Revert** replaces the draft with the live document. Concurrent edits are caught by a revision number on the draft.
- **Frozen** is set only by an import (slice 2; `service.freeze`, no route) and cleared by any edit, revert or commit. Staged maintenance will need a frozen plan.
- **The first state** (every section at its default) is made the first time anything looks at the state, by any server.
- **No process state.** The live snapshot's id sits in one row; a server compares it and reloads on change.
- **The calls** (admins; each its own route; the writes need the login and CSRF token and are rate-limited): `GET /api/admin/state`, `GET .../live`, `GET .../planned`, `GET .../history`, `POST .../check`, `PUT .../planned/sections/{name}`, `POST .../revert`, `POST .../commit`.
- **Export and import.** `GET /api/admin/state/export` (`?source=live` for the live state) returns a file: `{"export_format": 1, "kind": "planned-state", "source", "hash", "modules", "document"}`. `modules` lists the add-ons installed, in layer order; `hash` is the document's. `POST /api/admin/state/import` (the same file as the body) puts the document in the **draft**, frozen, and never touches live: commit it as usual. An import is refused, with every problem named and nothing changed, if the file is not a good export, its hash does not match its document, it was made with other add-ons (the same list in the same order is required), or the document does not check out against this game's sections. Player saves are not part of it. The command line does the same: `python -m terraforma export-state FILE [--live] [GAME_APP]` and `python -m terraforma import-state FILE [GAME_APP]`.
- **Not yet.** Seeds in the file, moving monsters, events and quest slots, and the maintenance-mode requirement come with the later slices (the draft is the only thing an import changes today).

## Manual quests (events)

An admin can write a quest by hand: an alliance competition, a coliseum tournament, a one-off hunt. `terraforma.quests.manual` keeps it as an *event*; the engine does the plumbing and the game keeps the meaning. An event has a `key`, a `name`, a `kind` (the game's own label: `alliance`, `coliseum`), a `description`, a `spec` (the game's own description, stored and handed back, never read), and, like anything that exists somewhere, an optional place (`map_id`, `x`, `y`). It uses monsters the world already has: an admin does not make monsters here.

- **Drafts and publishing.** An event starts as a draft that only admins see and may rewrite (`PATCH`). `publish` shows it to the teams; a published event is never rewritten under them: cancel it and write another. `cancel` calls it off: the teams still in it are done with it (status `ended`, no penalty, the game's `penalty` is not called) and a result already given stands.
- **Times.** `opens_at` <= teams may enter < `closes_at` <= `ends_at`, in seconds since 1970 (the world clock). Entering starts the team's clock: it has `limit_seconds` (0: until the event is over) and never longer than `ends_at`. `max_entries` limits how many teams may enter (0: any number). Nothing runs on a timer: an entry past its deadline fails with `timeout` the next time anything touches the team or the event, so any server gives the same answer.
- **Finishing.** The game's dungeon calls `quests.manual.finish(session, hooks, entry_id, won, score=None, reason=...)`, or an admin judges a contest by hand. A won entry is added to the team's quest record twice, in the category `event` and in the category named by the event's `key` (both at level 0), so a dialog can ask either with the `quests` tag. A lost entry calls the game's penalty. `score` (0 to 1,000,000,000) ranks a competition: best first, then who finished earliest.
- **Dialog tag.** `manual_quest,event,enter|finish_win|finish_lose,label` acts for the talking hero's team: `enter` takes the published event with that key (the label if it is not open, is full or the game turns the team away), `finish_win` / `finish_lose` end the entry still running (the label if there is none or its time ran out).
- **The game's hooks.** `Game(manual_quests=...)` takes a `ManualQuests` (a public interface: the license exception covers it): `may_enter(session, team_id, quest)` returns None or the reason a team may not enter (anyone may by default; an alliance competition checks membership here) and `penalty(session, team_id, quest, reason)` (`timeout` or `poor_performance`; nothing by default).
- **The portal's calls** (admins; each its own route and rate-limited; the writes need the login and CSRF token): `GET /api/admin/manual-quests` (`status`, `after`, `limit`), `GET /api/admin/manual-quests/{id}` (with every entry), `POST /api/admin/manual-quests`, `PATCH /api/admin/manual-quests/{id}` (a draft), `POST .../{id}/publish`, `POST .../{id}/cancel` and `POST .../{id}/entries/{entry_id}/result` (`won`, `score`). **Players** (login; the writes with the CSRF token): `GET /api/teams/{team_id}/manual-quests` (the published events not yet over, with the team's entry), `POST /api/teams/{team_id}/manual-quests/{id}/enter` and `GET /api/manual-quests/{id}/standings` (rank, team name, score, status: no accounts or heroes).

## Towns

In a *town* a party comes apart. The game says which places are towns (`Game(towns=...)`, `terraforma.towns.hooks.Towns`: `is_town(session, map_id, x, y)`, nowhere by default; the map will ask it as a party moves), and `terraforma.towns.service.enter_town` suspends a party there: it is split into groups of its teams (`Towns.groups`: by default one team each; a game can keep a player's own teams together, for example because the player paid for it), and each team shops and rests on its own. The party can't be joined, merged or have a team leave while it is apart (`parties.service` refuses), with one exception: the guild adds teams in town (see The adventurers guild). **Several towns on one map.** The overworld is one big map, so the visited list keeps a town for each team, map and *town*: `Towns.town_key(session, map_id, x, y)` names the town a party that comes in at a place is in (up to 64 characters). By default it is the key of the settlement (`terraforma.realms`) placed on exactly that tile, and "" when there is none, which keeps the old rule of one town for a map. A game whose towns cover many tiles overrides it to give the same key for each tile. The visited list (`GET /api/teams/{id}/town/visited`) now carries `town` in each entry, ordered by map and town, and a settlement that falls takes only the entries that name it (when no live settlement is left on its map, the map's other entries go too). `towns.service.record_visit` takes the game's `Towns` as an optional last argument. This is a public interface (the license exception covers it).

To leave, a team (with the teams in its group) says it is ready (`ready`; `Towns.may_wait` can refuse, for a team in a fight; a hero that fled from it is free) and waits in a holding queue. Every other team of the party is *told* (a notice: `view` lists who is ready) and can follow, which is the same call. A waiting team can `come_back` into the town, or `leave_party` for good (it is not waited for any more). When every team left is waiting, the party is put back as one unit, in the formation it had (its teams' order), and every hero of it is placed at the party's spot on the map (`reform`). `is_town` is true for the hub by default, and `settle` suspends a party that stands in a town. **Leave Town** is the `ready` call: when the last team presses it and the party is whole, the party's fight starts at once, against the monsters `Towns.encounter` picks (by default random active monsters while their PXP stays within the party's, at least one; a game overrides it, and none means no fight; the response's `fight` is the new fight's id or null). On a small chance (`Rules.join_chance`, 3% by default) the hub offers the party a running fight to join instead, and no fight starts until its leader answers (the response's `offer` is true; see Joining a running fight). A team with a hero in a running fight can't press it (`Towns.may_wait`), unless that hero fled from it (see Fleeing). Entering a town and putting a party back are service functions the map drives; a team's own owner calls `GET /api/teams/{id}/town` and `POST .../town/ready`, `.../town/come-back` and `.../town/leave-party` (login and CSRF token; each its own route), and the join-offer calls (see Joining a running fight). These are public interfaces (the license exception covers them).

## Realms and settlements

The living world's towns are records (`terraforma.realms`), so they can be founded and can fall while the game runs. A *realm* (a kingdom, or a minor power that holds settlements under no kingdom: its `kind`) has a `strength` number; a *settlement* belongs to a realm, stands on a map and is `live`, `dormant` (authored, not yet founded) or `ruins` (fell, kept so it can be founded again). `realms.service` creates them and moves a settlement between states: `found` wakes a dormant settlement or founds ruins again, `fall` turns a live one into ruins and deletes the map's rows from every team's visited list (unless another live settlement stands on the same map). The seed's `realms.json` and `settlements.json` make them (rows are only added or renamed on a later load: a realm's strength and a settlement's state belong to the world once they exist). An admin (all with a login, and a CSRF token for the three that change something) uses `GET /api/admin/realms` (every realm and settlement), `POST /api/admin/realms/{id}/strength` (`{"strength": n}`), `POST /api/admin/settlements/{id}/fall` and `POST /api/admin/settlements/{id}/found`. 
**Supply.** A settlement keeps a level of each material (`materials.json`, and `supplies` on a settlement row: `material`, `capacity`, `rate`, `drain`, `level`). Time is the world clock (`World.tick`): from the last time it was read, each tick adds `rate` (its own sources) cut by the settlement's `cut` percent (an event such as a raid) and takes away `drain` (what its crafters and people use), between 0 and `capacity`. Nothing steps it: `realms.supply` works the level out when it is read or changed (`supply_of`, `set_cut`, `take` for a crafter, `add` for a delivery), so every server agrees. `GET /api/admin/settlements/{id}/supply` reads it and `POST /api/admin/settlements/{id}/supply/{material}/cut` (`{"cut": 0-100}`) cuts or restores the sources. A later seed load changes capacity, rate and drain but leaves the level and the cut. Shops read it (see below); the planned slices after that (supply quests, strength drift) are in the project's living-world design.

**Shops and supply.** A game ties a shop's item to a settlement's supply by overriding `Market.supplied(session, shop, item)` (`terraforma.market.hooks`), which returns `Supplied(settlement_key, material_key)` or `None` (the default: nothing is tied, so a game that does not use supply sees no change). For a tied item the shop works out how full the supply is, in whole percent of its capacity, and asks `Market.price_percent(shop, item, fullness)`: the price in percent of `Market.price`, or `None` for sold out (the item is then not for sale and `buy` refuses it). The default line charges the normal price from `dear_below` (50) percent full up, rises to `dearest_percent` (200) at `sold_out_below` (10) percent, and sells out below that; a game changes the three numbers or overrides `price_percent` for its own curve per item. A tied item whose settlement or material does not exist counts as empty (sold out), so a typo in the game shows at once. What the shop pays when the player sells an item back is unchanged: it follows the item's own price, not the supply. Buying from a shop does not use up supply (only a crafter's `take` does). These hooks are public interfaces (the license exception covers them).

**Strength over time.** A game decides how a realm's strength moves and when its towns fall or rise by handing `Game(realms=...)` a subclass of `terraforma.realms.hooks.Realms` (a public interface; the license exception covers it). By default nothing moves. `target(realm, fullness)` is the strength the realm heads for, given how full each supply of each of its live settlements is (whole percent of capacity), or `None` for no drift; `step` is the most it moves in one tick of the world clock; `falls(realm, settlement)` says a live settlement falls now, and `founds(realm, settlement)` says a dormant one (before any in ruins) is founded, or raised again: at most one settlement per realm each pass, and one the world refuses to found is skipped. Like a supply, strength is not stepped by a job: `realms.strength.drift` brings it up to the world clock (`Realm.as_of_tick`) when it is looked at, reading the target once for the whole time that passed. The housekeeping job `realm_strength` runs `realms.strength.judge` (drift, falls, at most one founding) for every realm and returns how many settlements fell or were founded. Not built yet: strength moving with quest outcomes. The engine has no cap on realms, settlements or settlements per map (all of that is game content); its only limit is whether it can keep up with the backend work.

**Supply in dialogs.** A game writes its supply quests and its crafters as dialog (see The dialog language), with three tags that name a settlement's key (`settlements.json`) and a material's key. `supply_level,settlement,material,op,percent,label` jumps to the label unless how full the supply is (whole percent of its capacity) compares true with `percent` (0 to 100; `op` is `eq ne lt le gt ge`), so a quest board offers a fetch quest only while a supply is low. `supply_add,settlement,material,amount,label` is a delivery: it brings up to `amount` into the supply, as much as fits under the capacity, and jumps to the label if none fits; it takes nothing from the hero (a dialog takes the goods itself, with `remove_item`; a jump to a label does not undo what came before it, so a dialog checks that the hero has the goods (`have_item`) and that the supply has room (`supply_level`) before it takes the goods and delivers them). `supply_take,settlement,material,amount,label` is a crafter at work: it uses `amount` up, all or nothing, and jumps to the label (taking nothing) if the settlement keeps less. A dialog that names a settlement or supply the world does not have fails with a message that says which; the seed check refuses one that names a settlement or supply `settlements.json` does not have, in an NPC, a map object or edge, or a dialog tree. Not built yet: quests the engine makes itself for low supplies (the quest generator), and rare-material quests with craftable rewards.

**Realm strength in dialogs.** Quest outcomes move a realm's strength through two more tags that name a realm's key (`realms.json`). `realm_strength,realm,op,value,label` jumps to the label unless the realm's strength (a whole number, which may be negative) compares true with `value`, so a board offers a rescue quest only while a realm is weak. `realm_nudge,realm,delta` moves the strength by `delta` (a whole number that is not 0 and may be negative; the strength stays within 1000000 of zero, as the admin call does), so a dialog that finishes a quest can make its realm stronger or weaker. A nudge is added to the stored strength without first bringing it up to the world clock (that needs the game's `Realms` hook), so the drift carries on from the nudged value. A dialog that names a realm the world does not have fails with a message that says which, and the seed check refuses one that names a realm `realms.json` does not have.

## Joining a running fight

When a party that is whole again is about to fight at the hub (Leave Town), the hub may offer it a running fight to join instead (`terraforma.fights.joining`). The chance is `Rules.join_chance` (0.03), rolled once from a stream of the world (`WorldRng`, never the `random` module, so a test fixes `World.seed` or sets the chance to 0 or 1). If the roll hits, the hub looks at up to `Rules.join_looked_at` (10) running fights picked at random and offers the first that suits the party: it has room (`Rules.max_fight_parties`, 4: the parties that joined count) and it is in range (`Rules.may_join_fight(joiner_pxp, fight_pxps)`, which by default is the PvP window: the fight's strongest party is at least `pvp_window` of the joiner's strength, and a stronger fight is always fine). The players are never told what the fight is. The offer waits for the party's leader, and until then the party can't walk or pick a PvP fight.

- `GET /api/teams/{id}/town/join-offer` (login) says `{"offer": true|false}` for the team's party.
- `POST /api/teams/{id}/town/join-offer/accept` (login and CSRF token, the party's leader only) makes the party the next party of that fight (`joined: true`, `fight`); if the fight can't take it any more (over, full, out of range now) the party's own fight starts instead (`joined: false`).
- `POST /api/teams/{id}/town/join-offer/decline` (same) starts the party's own fight as usual.

Joining adds a party between two rounds. The `PartyJoined` event (the new party as `state.dehydrate_party` writes it, and how the other parties now count each other) is kept with the fight and written first into the next round that plays (`store.add_party`, `store.pending_joins`), so the log still replays, `store.verify(deep=True)` checks it and the hash chain covers it. The joiners act in that round (it waits for them like for any player), their heroes can be commanded and watched at once, and every watcher is sent `{"type": "party_joined", "fight": id}`. Parties never merge. The joiners earn experience only for what they do after joining, because the experience tree reads the debts the fight collects as it goes. The fight's round clock is the one fixed when it started.

How the parties stand to each other is settled as the party joins. Every pair of teams (one of the joiner's, one of a party already there) with no relationship yet gets one in both directions, neutral (`Relations.initial`). A team's view counts at face value (`Relations.stance(score)`: by default friendly and close are allies, wary and enemy are enemies, neutral is neutral), and `Rules.party_stance(stances)` makes a party's stance toward another party of the stances of its teams' pairs: allies and no enemies, ally; enemies and no allies, enemy; both, neutral; none at all, as for strangers and for monsters (who have no teams), enemy. It is one way: the joiner may count a party as an ally while that party counts the joiner as an enemy. The result is written into each party's `allies` and `enemies` (a party in neither is neutral to it). `Rules.fight_is_over` now also ends a fight whose parties that are left count none of the others as enemies, so neutral parties do not fight on forever. `Rules.join_chance`, `join_looked_at`, `max_fight_parties`, `may_join_fight`, `party_stance`, `Relations.stance` and the `PartyJoined` event are public interfaces (the license exception covers them).

## Monster-party play

A player can volunteer to command the monsters of a new fight instead of a hero party (`terraforma.monsterplay`). Volunteers wait in a queue, longest first. When the server *creates* a fight that allows it, it seats the longest-waiting volunteer the game accepts as the controller of the monster party (`MonsterSeat`); with nobody queued, or nobody accepted, the AI plays as always. A volunteer is never seated into a running fight, and a fight never waits for one. The seat is recorded (the fight view says `monsters_played`) and the player commands the monsters, is rewarded and may be locked out (below), and a game may let people who are not logged in play too (guests, below).

- **Which fights.** `FightRecord.monster_play`: on for random encounters on the map and the hub's Leave Town fight, off for any other fight (`live.start_team_fight` and `start_party_fight` take `monster_play=False`; a scripted fight leaves it off unless a game asks), and never for PvP or coliseum fights. A fight another party joins keeps its volunteer.
- **The calls.** `GET /api/monsters/queue` (login) says whether the caller waits and where (`position`, 1 is next), the `seat` they hold (the fight and party), a `locked_until`, why they may not volunteer (`refusal`) and how often to check in. `POST .../join`, `.../leave` and `.../check-in` (login and CSRF token; each its own route, rate-limited) volunteer, leave and say "still here". A volunteer who has not checked in for `Rules.monster_checkin_seconds` (60) is no longer waiting: the next seating drops them, and joining again puts them at the back.
- **The rules.** `Rules.may_queue_monsters(volunteer)` says who may wait (None, or the reason): by default a logged-in account with a team, no unfinished fight (as a hero or as a monster player) and no running lockout (admins are exempt from a lockout). It is given a `Volunteer` whose `account_id` may be None: a guest (below), who has a `guest_id` instead. `Rules.may_play_monsters(volunteer, seating)` says who may take the seat of a particular new fight: by default not an account with a hero in it, not one with *any* team that counts a team of the heroes as an ally (`Relations.stance`, judged across all its teams), and not one in another fight. A volunteer the rules refuse stays queued for the next fight. `Volunteer` and `Seating` are in `terraforma.monsterplay.facts`. These are public interfaces (the license exception covers them).
- **Commanding.** The player who holds a fight's seat is, for every fighter of the monster party, what a hero's owner is for theirs: `GET /api/fights/{id}` shows the fight to them (their fighters are `yours`; a `seat` key tells them `{party, absent, admin}`), `GET /api/fights` lists it (`monsters: true`), the fight socket lets them listen, and `POST /api/fights/{id}/commands` takes their commands. The heroes' pending commands are never shown to anyone (only who has committed). Rounds wait for them like for any player. The monsters never flee unless the game lets them (`Rules.monster_flee_allowed(fight, address)`, on top of `flee_allowed`).
- **Absence.** A round in which the player gave *none* of their fighters a command is *missed*: it is counted (`MonsterSeat.missed`, kept for the rewards), their monsters repeat the commands they had last round (the AI chooses when there were none, or the old command no longer makes sense: its target is down, say), and `Rules.monster_absent(missed)` says whether the monsters now go to the AI (by default after the first miss, DragonStar's way). While absent the AI plays the monsters and the round does not wait for them. The player returns by commanding a monster again or by `POST /api/fights/{id}/monsters/back` (login and CSRF token; the page calls it when it loads the fight); the count stays.
- **Admin takeover.** `POST /api/fights/{id}/monsters/take-over` (login and CSRF token, admins only) sits an admin in a *running* fight that allows monster play, in an empty seat or one whose player is absent (never over a player who is commanding), and not if the admin has a hero in it. The round's end is pushed back by a whole round (never made earlier) so they can finish the playback and decide, and the fight's watchers get a `deadline` message. The seat is marked `admin`: it earns nothing, whatever the rules pay.
- **When the fight ends.** The seat is settled once (`monsterplay.service.settle`, called from `store.apply_results`). It is given a `SeatResult` (`played_through`: no round missed; `won`: the monster party was still standing; `absent`: the AI was playing when it ended; `rounds_missed`; `admin`). `Rules.monster_challenge_earned(result)` says how many Challenge Tokens it earns, **none by default**; DragonStar's way is `int(result.played_through) + int(result.won and not result.absent)`. They are paid through the daily and purse caps (`challenge_daily_cap`, `challenge_purse_cap`) like any fight's. `Rules.monster_lockout_seconds(result)` says how long the player may not volunteer again: by default `Rules.monster_lockout_default` (an hour) for one who missed rounds, was not back in control at the end and whose monsters lost. A longer lockout already running is kept. A seat an admin took pays nothing and locks nobody out, whatever the rules say, and an admin account is never locked out. Monster players earn no gold, experience or drops.
- **The heroes' bonus.** The heroes of a party still standing get extra experience for beating monsters a player commanded at any point of the fight, even briefly: `Rules.monster_player_bonus(fight, party, overkill, monster_hp)` gives the share of what each hero earned, by default the overkill they dealt those monsters (damage past the last hit point, from the log's `Died` events) as a share of the monsters' total hit points, up to `Rules.monster_bonus_cap` (0.15, DragonStar's). It is a second `XpEarned` event for the hero, so the log shows it and it replays. A game turns it off with a cap of 0.
- **Guests.** The engine's rules refuse people who are not logged in (`may_queue_monsters` says "Log in to play monsters."), so the calls below answer 409 until a game accepts them (a `Volunteer` with a `guest_id`; it has no teams, is never an admin and is never locked out). A guest is a random token (`MonsterGuest`; only its SHA-256 hash is stored), not an account. `POST /api/monsters/guest/join` makes one, queues it and answers with `token`, shown once; the page keeps it and sends it as `Authorization: Bearer <token>` on `GET /api/monsters/guest` (where it stands, the `seat`), `POST .../check-in`, `.../leave`, `GET .../fights/{id}` (the fight as the volunteer sees it), `POST .../fights/{id}/commands` (the same body as the heroes' call) and `POST .../fights/{id}/back`. The guest lapses `Rules.monster_guest_seconds` (4 hours) after it was last heard from, and a lapsed guest that sits in no fight is cleared (with its queue place) when the next guest joins. A guest earns no Challenge Tokens and has no lockout, whatever `monster_challenge_earned` and `monster_lockout_seconds` say; the heroes still get the bonus for beating its monsters. Nothing rides along with a guest's request by itself (no cookie), so there is no CSRF token; instead the calls that change something must carry this site's `Origin` header (403 otherwise), every call counts against the caller's address (`MONSTER_GUEST_BY_ADDRESS`, and making guests apart: `MONSTER_GUEST_JOIN_BY_ADDRESS`), and a guest reaches only the fight whose monsters it commands. A guest listens to its fight on its own socket, `/ws/monsters/guest/fights/{id}`: the browser cannot put a header on a WebSocket and a token in the address would be logged, so the page offers the token as the second subprotocol (`new WebSocket(url, ["terraforma.guest", token])`; the server answers with the first only). The server checks this site's `Origin`, the rate limit, the token and that the guest commands that fight before it accepts, and then pushes what the players' socket pushes; the socket only listens (commands are calls). `/monsters/` is the page that uses it. Inside the fight, a guest is the negative of its id where an account id would stand (`MonsterSeat.holder`), so it never meets an account.
- **Tables.** `monster_volunteers` (one place per account or guest), `monster_guests`, `monster_lockouts` and `monster_seats`. None stands on a map: a volunteer waits for any fight, and a seat belongs to its fight.

## Item drops

A drop table (`drop_tables.json`) says what a monster, or an area, leaves behind. A monster names the tables it rolls when it dies (`drops`); a fight may carry *area* tables of its own (`live.start_team_fight(..., area_drops=[keys])`; the map's, once there are maps).

- **A plain table** rolls every entry on its own: an entry is `{"item", "chance", "min", "max", "for"}`. `chance` is out of `Rules.drop_chance_scale` (10000 by default, so 10000 is a sure thing and 1 is one in ten thousand); `min` and `max` (default 1) say how many. **A weighted table** (`"weighted": true`) instead picks an entry by `weight`, `rolls` times; an entry with no `item` means nothing drops.
- **Who gets it.** An entry's `for` is `one` (one person, the default), `each_team` (one in each team of the winning side) or `each_member` (every hero of the winning party). Who that person is, is the game's rule: `Rules.drop_recipients(fight, party, monsters, share, rng)`. The default picks one at random among the heroes who *contributed*, which it reads off the experience debts the fight keeps: whoever harmed a monster that died (a hit, or through a status, or by placing a bad status on it) and whoever placed a good status on one of those. Healing does not count. Everyone in the pool has the same chance, and a hit for 1 HP counts the same as any other. A game overrides it for a leader's choice, the last strike, round robin, a team chest and so on (choices that need players to answer later are *held*: see **Held drops** below).
- **When.** `Rules.roll_drops` runs when a fight ends, after the experience and the gold, for each party of players that won: the tables of every monster that died, and the area's tables once for the fight (`Rules.map_drops_once_per_fight`, on by default; off rolls them for every monster instead). The dice are the fight's own stream, so a fight replays exactly.
- **What lands.** A `Drop` event, and the item goes into the hero's inventory in the fight; what does not fit (twelve stacks, 250 to a stack, gear never stacking: `Rules.inventory_stacks` and `stack_size`) is a `DropLost` event, never lost silently. `store.apply_results` puts the dropped items in the heroes' inventories, once.
- **Held drops.** `Rules.drop_mode(fight, party, monsters, share, rng)` says how one drop is given out: `"auto"` (the default, `drop_recipients` at once), `"need_want"` or `"assign"`. A held drop is a `DropHeld` event `[party, item, quantity, mode]`, nobody is given it, and `store.apply_results` makes a row of it in `pending_drops` (once, however often it is saved) standing where the fight did. A *need/want* drop waits until every hero of the party that fought has said `need`, `want` or `pass` (changing their mind is fine until the last one answers); then those who needed (or, if none did, wanted) roll 1 to 100 from a stream of the fight's own (`"drop", n`), the highest wins and a tie goes to the lower hero id. If all pass it is `unclaimed`. An *assign* drop is given to a hero of the party by whoever `Rules.may_assign_drop(hero_ids, hero_id, is_leader)` allows: by default the hero's player, if they lead the party (see Parties), and nobody else; a game overrides it to say otherwise. (`is_leader` is a new third parameter: an override written with two parameters needs it added.) What does not fit the winner's pack is counted in `lost`, not lost silently. Calls (each its own route, login and CSRF token on the writes): `GET /api/heroes/{id}/pending-drops`, `POST .../{drop_id}/choose` (`{"choice"}`) and `POST .../{drop_id}/assign` (`{"to_hero_id"}`). Others' answers stay hidden until the drop is settled.
- **Checks.** The seed refuses a table that names an unknown item, a chance outside 1 to the scale, a minimum above its maximum, an empty table, a plain entry with no item or a weight, a weighted one with no weight or a chance, and a monster that names an unknown table.

## Gold and the economy

Where gold lives is the game's decision, so the engine asks `Game(economy=...)` (`terraforma.economy.Economy`). `TeamGold`, the default, is DragonStar's way: a hero on a team spends and earns from the team's gold (`Team.gold`), and a hero on no team has gold of their own (`Hero.gold`). `HeroGold` keeps every hero's gold on the hero and splits what a team earns between its heroes, the first by slot getting the odd coins. A game subclasses `Economy` for anything else, overriding `purse(session, hero)` (the row whose `gold` is the hero's money) and `credit_team(session, team_id, amount)` (what a team earns).

`balance`, `credit` and `debit` work on the hero's purse; a debit that would take more than is there raises `NotEnoughGold` and takes nothing. Gold moves with single statements, so two calls at the same instant never lose a coin. The inventory call shows the hero's purse in the game's economy. A fight's gold is paid by `economy.credit_fight_gold(session, economy, fight_record, [(team_id, amount), ...])`: once per fight (the fight records that it has paid), however often it is called. `fights.store.apply_results` does it from the fight's `Gold` events, through the game's economy. These are public interfaces (the license exception covers them).

## Trading

Heroes give each other gold and items, if the game's economy allows it. Who may trade with whom is `Economy.can_trade(session, giver, receiver, what)`, which asks the economy's `trade_policy` (`terraforma.trading.policy`). The stock policies are `NoOne`, `Anyone`, `WithinTeam` (the default: heroes on the same team), `WithinParty` (the same team, or teams in the same party), `Related` (whatever the economy's `related(session, giver, receiver)` says, the hook a game fills in for its own relationships; nobody until it does) and `AnyOf(...)` to combine them. A game sets one on its economy (`trade_policy = AnyOf(WithinTeam(), Related())`) or subclasses `TradePolicy` and writes `allows(economy, session, giver, receiver)`. These are public interfaces (the license exception covers them).

The calls, each its own route, for the hero's owner and with the CSRF token: `POST /api/heroes/{id}/give-gold` (`to_hero_id`, `amount`) and `POST /api/heroes/{id}/give-item` (`to_hero_id`, `position`, `qty`), and `GET /api/heroes/{id}/trades` for the hero's ledger. They are limited to 120 gifts an hour per account. An item moves only if it is not worn and all of it fits in the other pack; gold moves between the two heroes' purses in the game's economy, so heroes who share a purse (teammates under `TeamGold`) have nothing to give each other. Whether the other hero does not exist or may not be traded with, the answer is the same (404, "you can't trade with that hero"), so the calls cannot be used to find heroes. Every gift is a line in the ledger (`TradeRecord`), which keeps the heroes' ids and names so the history outlives a deleted hero.

## Guild fees

What a guild charges a team for a service (a contract, a marketplace listing, a delivery) goes through one hook, `Game(fees=...)`. `Fees.quote(session, team_id, guild, base, kind="")` returns the price for that team and guild; the default charges the base price. `RankFees(rank_discounts, merchant_guilds)` is the engine's rank rule: `rank_discounts[rank]` is the percentage off at each guild rank (the last entry holds for higher ranks), and `merchant_guilds` maps a guild key to an extra percentage off. Both discounts apply, and the price rounds up to a whole coin. A game that wants something else subclasses `Fees` and may price by `kind`. Changing the `Game.fees` field is a change to what the license exception covers.

## Storage

Whether items can be kept beside the heroes' packs is the game's decision, so the engine asks `Game(storage=...)` (`terraforma.storage.hooks.Storage`). `NoStorage` is the default: no storage. `TeamStorage` gives each team one store shared by its heroes (Vanguard Tavern's way; a hero on no team has none), and `AccountStorage` gives each account one store shared by all its heroes. A game subclasses `Storage` for anything else: `owner(session, hero)` (an `Owner(kind, id)` or None), `capacity` (stacks; 24 by default), and the rules `reachable` (where a hero can get at it: a town, say), `may_put`, `may_take` and `may_use`, each returning None to allow or why not, shown to the player as it is. Using an item straight from storage is refused by default ("take it out of storage first"); a game that allows it returns None from `may_use`. Storage is used outside fights only: a hero in a running fight cannot put, take or use, whatever the rules say. Using it in a fight is not built. These are public interfaces (the license exception covers them). The Pack panel of the browser client shows it when the game keeps storage (`enabled`): a Store button on each pack stack, and Take and Use on each stored one, with a refusal from the rules shown as the server words it; a game with none shows nothing.

Stacks work as in a pack: equipment never stacks, the rest stack up to the pack's limit, positions have no gaps. A move is all or nothing: what does not fit stays where it was, and a worn item must be taken off first. The calls, each its own route, for the hero's owner (`GET` needs only a login, the others the CSRF token too): `GET /api/heroes/{id}/storage` (`enabled`, `owner`, `capacity`, `items`; `enabled` is false when the game has none), `POST /api/heroes/{id}/storage/put` and `/take` (`position`, `qty`: the pack's position going in, storage's coming out) and `POST /api/heroes/{id}/storage/use` (`position`, optional `target_hero_id`, answered like `use-item`). Refusals from the rules are 409.

A delivery (a store's purchase, a reward) goes through `terraforma.storage.service.deliver(session, storage, hero, item_key, qty)`: into storage first, then into the packs of `Storage.sharers(session, hero)` in order (the hero's teammates by slot, or the hero alone), the next after each is full. It returns a `Delivery` (`stored`, `packed` by hero id, `left`) and raises nothing for a full house, so the caller decides what to do with the rest. Deleting a team deletes its storage with it, as it does the team's gold.

## Delivery

Goods can be on their way to a team at a guild (`terraforma.delivery`). A hero sends a parcel with `delivery.service.send(session, economy, hero, to_team_id, guild, purpose, ref, delay, gold, items)`: gold from the hero's purse and `items`, a list of (pack position, quantity), from their pack, for their team to send, all or nothing. The game sends goods it makes (a quest giver's reward) with `send_goods(session, to_team_id, guild, purpose, ref, delay, gold, items)`, where items are (item key, quantity) and nothing is taken from anyone. A parcel names the guild it is delivered to, the receiving team and `delay`, the seconds it takes by the wall clock; it is in transit until then. `parcels` lists those in transit, narrowed by team, guild, purpose and ref, and by whether they have `arrived`.

A hero on the receiving team collects an arrived parcel with `collect(session, economy, storage, hero, shipment_id)`: gold goes to the team (`Economy.credit_team`) and items through the game's storage (`storage.service.deliver`), all or nothing; a team with no room for every item leaves the parcel waiting, and a parcel pays once. A refusal for another team's parcel reads the same as for one that does not exist. `cancel(session, economy, storage, shipment_id)` calls a parcel back before anyone collects it: it goes back to its sender, or vanishes if the game made it. A game that wants a reward to reach its recipient on time whatever the questing party does sends it with `send_goods` and cancels it if the party delivers first. Where a hero must stand to collect (at that guild) and what a parcel costs to send are the game's: it calls these from its dialogs and rules. No call a player can make, no schema file. These are public interfaces (the license exception covers them).

## Contracts

Two teams can bind each other with a contract at a guild (`terraforma.contracts`), secured by breach escrow. Side `a` offers (`contracts.service.offer(session, economy, fees, contracts, hero, guild, to_team_id, my_terms, their_terms, my_escrow, their_escrow, duration)`): each side lists the terms it is bound to, each a kind and its params, and the gold it will put down as breach escrow. The offering side pays the guild's fee and puts its escrow down at once; the other side answers with `accept` (their fee and escrow, and the contract runs `duration` seconds) or `decline`, `a` can `withdraw`, and `expire_offers` clears offers nobody answered. Fees are the game's base amount put through `Game(fees=...)`, each side at its own rank.

Side `a` may also set a *payment* (`payment_gold` in `offer`, `payment` in the offer call): a fee for side `b` that is taken from `a` with the offer, held in a deposit of its own, and paid to `b` when the contract ends with none of b's terms broken (even if `a` broke one of its own). It goes back to `a` if `b` broke a term, or if the offer is declined, withdrawn or expires. This is how a contract pays for a job done (the assassination, escort and bounty contracts build on it).

A side's escrow has a floor: at least `Contracts.minimum_percent(guild)` (half, by default) of the other side's total at stake, which is the worth of their terms plus their escrow. Below 100 percent, both floors can be met at once. `judge(session, economy, storage, contracts, contract_id)` asks the game about each pending term. A broken term ends the contract `breached`: the breaking side's escrow goes to the other side and the other's comes back (if both broke, each goes to the other). A term still pending when time is up counts as broken. Every term met, or time up with nothing broken, ends it `fulfilled` and both escrows come back. A contract is settled once. Contracts never move items between teams; a term that needs goods to change hands uses delivery.

**Bounties** (`terraforma.contracts.bounties`) are contracts with nobody to accept them. A team posts one at a guild with `POST /api/heroes/{id}/bounties` (`guild`, `target_team_id`, `scope` `team` or `hero` with `hero_id`, `reward` gold, `lifetime` seconds; login and CSRF token), or posts it in an alliance's name (`alliance_id`) by the same permission as spending its treasury (`alliances.service.commit_gold`; a spend that needs a vote is refused). The reward is held from the posting (the team's purse, or the treasury) and paid once: when the target (the whole team, or the one hero) has fallen in fights that began after the posting, the housekeeping job `standing_bounties` (`bounties.judge`) splits it evenly between the teams whose heroes were on the other side of those fights; a fall to monsters earns nothing. If nobody earns it before `lifetime` runs out, or the poster withdraws it (`POST .../bounties/{bounty_id}/withdraw`), the reward goes back (to the alliance's treasury, or to the posting team if the alliance is gone). `GET /api/heroes/{id}/bounties` lists the standing ones (optionally by `guild`).

`Game(contracts=...)` is a `terraforma.contracts.hooks.Contracts`: `kinds()`, `validate(kind, params)`, `check_offer(session, a_team_id, b_team_id, my_terms, their_terms)` (why an offer cannot be made, from what only the database knows; None by default), `value(kind, params)` (the gold a term is worth), `check(session, contract, term, ended)` (met, broken or pending), `minimum_percent`, `base_fee` and `offer_lifetime`. `StandardTerms` (`terraforma.contracts.terms`) is the default and ships the kinds the engine can judge from its own records. `truce`: the bound side does not pick a fight with the other; any fight that began after the contract started in which the bound side's heroes attacked (party 0) the other side's breaks it, and it is met when time runs out. `parcel`: the bound side sends the other goods by delivery with purpose `contract` and the contract's id as the reference; it is met once parcels not called back hold the gold and items asked (`gold`, `items` as `[item key, quantity]`), and broken if time runs out first. `assassinate`: the bound side kills a third team that need not know or agree (`target_team_id`, `scope` `team` for every hero of it or `hero` with a `hero_id` on it); it is met once those heroes have each fallen (a `Died` event) in fights that began after the contract started and had a hero of the bound side and one of the target on opposite sides, and broken if time runs out first. The target may not be either side of the contract. `kill_boss`: the bound side kills a boss (`monster`, a monster key) inside the other side's run of a quest. `POST /api/heroes/{id}/contracts/{contract_id}/enter-instance` (login and CSRF token) lets the hired side's party into the instance the other side's party is in (`instances.service.admit`: an invitation, whatever the capacity or joining time; both teams must be in parties); the term records the map it entered, and is met once a fight on that map that began after the contract started, with a hero of the hired side in it, has a `Died` event for that monster. It is broken if the party never went in or the boss stands when time runs out. Who gets the drops is the contract's to settle (a `parcel` term can send them on). `escort_to`: the bound side (the escort) takes the other team (the escorted) to a place and keeps it alive: `to_map`, optional `x`/`y` (a tile), `dungeon` (go into the instance on that map and be brought back to where the escort began), `scope`/`hero_id` (who must not fall) and `value`. `accept` takes a `party_size` (the route passes `Rules.party_size`): the escort team must own a party with room, and the escorted team joins it (a team already in a party must leave it first). While the contract runs neither team can leave the party (`PartyError`), a party with both warps only to places every team in it has visited (`warp` behaves as `warp_visited`), and every step or warp is noted (`contracts.escort.note`) so arrival is recorded on the term; it is met when the party has arrived (and, for a dungeon, come back), and broken if one of the escorted falls in a fight after the contract started or time runs out. A game that already has its own term kind called `escort` is unaffected (the engine's is `escort_to`). Both take a `value` (the gold the term is worth, for the escrow floor). A game adds its own kinds (killing a target for a quest, say) by subclassing `StandardTerms` and extending `kinds`, `validate`, `value` and `check`. Changing the `Game.contracts` field is a change to what the license exception covers. The calls a player makes are routes, added with the first kinds of term.

**Open contracts.** The guild itself can post a contract (`contracts.service.post_open(session, contracts, guild, terms, escrow_gold, reward_gold, duration)`, the game's call, not a player's): it binds only the team that takes it, to the guild. The first team to `accept` holds it (a second finds it gone), paying its fee and putting the escrow down, and is paid `reward_gold` when every term is met; if it breaks one, the guild keeps the escrow (`escrow.keep`, so that gold leaves the economy). An untaken one expires like any offer. Its terms must be kinds from `Contracts.open_kinds()` (none, by default: the standard kinds describe another team), which the game judges in `check`. Adding `open_kinds` to `Contracts` is a change to what the license exception covers. `GET /api/heroes/{id}/open-contracts` (`guild`, `limit`) lists the ones waiting, and taking one is the same `accept` call.

The calls, each its own route with a strict body (the ones that change something with the CSRF token, limited to 120 an hour per account; a contract is visible only to its two teams, anyone else gets a 404): `POST /api/heroes/{id}/contracts` (`guild`, `to_team_id`, `my_terms` and `their_terms` as `kind` and `params`, `my_escrow`, `their_escrow`, `duration`), `POST .../contracts/{contract_id}/accept`, `.../decline` and `.../withdraw`, `GET /api/heroes/{id}/contracts` (the team's, newest first) and `GET .../contracts/{contract_id}`. Housekeeping settles contracts by itself: `unanswered_contract_offers` expires offers nobody answered and `running_contracts` judges active contracts (`judge`, `expire_offers`), using the game's `Contracts` and `Economy` hooks.

## Escrow

A guild can hold a team's gold, Challenge Tokens and items until the game settles them (`terraforma.escrow`). `escrow.service.hold(session, economy, hero, guild, purpose, ref, gold, tokens, items)` takes the deposit from a hero for their team: gold from the hero's purse (`Economy.debit`), tokens from the account's balance and `items`, a list of (pack position, quantity), from the hero's pack, all or nothing. `guild` names the hall that holds it, `purpose` is the game's word for why (a breach, a listing, a delivery) and `ref` whatever it wants to find the deposit by (`escrow.service.held` narrows by team, guild, purpose and ref; `contents` lists what a deposit holds).

A deposit is settled once, all or nothing: `refund(session, economy, storage, escrow_id)` gives it back to the depositing team and `forfeit(session, economy, storage, escrow_id, to_team_id)` gives it to another team. Gold goes to the team (`Economy.credit_team`), tokens to the team's account (whatever the purse cap says) and items through the game's storage (`storage.service.deliver`, into the team's first hero); a team with no hero or no room for every item gets nothing and the deposit stays held. Settling is not a call a player can make: what a deposit secures and when it is released is the game's, so these are functions for its dialogs and rules. They are public interfaces (the license exception covers them).

## The marketplace

Goods are listed at a guild for a fixed price in gold, Challenge Tokens or both (`terraforma.marketplace`). A hero posts a listing with `marketplace.service.post(session, economy, fees, marketplace, hero, guild, items, price_gold, price_tokens)`: the goods leave their pack for an escrow deposit, the posting fee leaves their purse and the listing is open until the game's `Marketplace.lifetime` (a week, by default). `search(session, guild, text, max_gold, limit, offset)` finds open listings at one guild or, with no guild, at all of them. `buy(session, economy, fees, marketplace, hero, listing_id, to_guild)` is made by another team: the price goes to the seller's team and the goods are never handed over, they go to the buyer's team as a parcel (`terraforma.delivery`) at the guild they name, after the route's delay and for its fee. A listing is sold once; two buyers at the same instant never both get it. The seller takes an open listing back with `cancel` (the posting fee is not returned) and `expire_due(session, economy, storage)` returns the goods of listings that ran out of time; the housekeeping job `ended_listings` calls it (and closes ended auctions) with the game's `Economy`, `Storage` and `Marketplace`. `housekeeping.run` now takes the `game` as a last argument for this.

`Game(marketplace=...)` is a `terraforma.marketplace.hooks.Marketplace`: `lifetime(guild)`, `listing_fee(guild, price_gold, price_tokens)` and `delivery(from_guild, to_guild)` (a `Route` with a fee and a delay) give the base amounts, which the game's fee rule (`Game(fees=...)`, "Guild fees") puts through a team's rank in the guild. Changing the `Game.marketplace` field is a change to what the license exception covers. Fixed prices in gold and tokens come first; barter is a later piece.

**Barter.** A listing may also ask for items, alone or besides gold or tokens (`post(..., asks=[(item key, qty), ...])`, at most 8 kinds). The buyer names which of their stacks to give (`buy(..., pay_items=[(position, qty), ...])`); they must add up to exactly the items asked. Nothing is handed over: the buyer's items are held in escrow, then go to the seller's team as a parcel at the listing's guild (purpose `barter`, free and at once), while the goods go to the buyer as usual. A wrong payment changes nothing. In the calls, `POST .../listings` takes `asks` (`item`, `qty`) and `.../buy` takes `pay_items` (`position`, `qty`), and search rows show `asks`.

**Auctions.** `service.post(..., price_gold, auction=True)` lists goods as an auction: the price is the starting bid, in gold only, and it runs `Marketplace.auction_lifetime` (two days, by default). `service.bid(session, economy, fees, marketplace, storage, hero, listing_id, amount, to_guild)` holds the bid plus the delivery fee for the route to `to_guild` in escrow; a bid must be at least the starting bid, or the highest bid plus `Marketplace.increment(guild, current_bid)` (a twentieth, by default). The team outbid gets everything back at once, a team can raise its own bid, and nobody bids on their own auction. A fixed-price `buy` refuses an auction, and an auction with a bid can't be cancelled. When time is up `expire_due(session, economy, storage, limit, marketplace)` sells an auction that has a bid (the seller's team gets the bid, the delivery fee goes to the guild and the goods go to the winner as a parcel) and returns the goods of one that has none. `Marketplace.auction_lifetime` and `increment` are added public hooks (the license exception covers them).

The calls, each its own route with a strict body (the ones that change something with the CSRF token, limited to 120 an hour per account; the engine does not know where guilds stand, so a game that wants a hero to be at the guild to trade there checks that itself): `GET /api/market/listings` (login; `guild`, `text`, `max_gold`, `limit`, `offset`; cheapest first), `POST /api/heroes/{id}/listings` (`guild`, `items` as `position` and `qty`, `price_gold`, `price_tokens`), `POST /api/heroes/{id}/listings/{listing_id}/buy` (`to_guild`) and `.../cancel`, `POST /api/heroes/{id}/auctions` (`guild`, `items`, `start_gold`), `POST .../listings/{listing_id}/bid` (`amount`, `to_guild`), `GET /api/heroes/{id}/parcels` (what is on its way to the hero's team) and `POST /api/heroes/{id}/parcels/{parcel_id}/collect` (once it has arrived; the goods go through the game's storage).

The browser client has a **Market** panel for these calls: search the open listings (item, guild, most gold), buy a fixed-price listing, bid on an auction, take back the hero's own team's listing, and list and collect the team's parcels. Goods are delivered to the guild typed in "Deliver to guild", or the listing's own guild when it is empty. Posting a listing and paying a barter listing in items are not in the browser yet (a barter listing shows what it asks and has no Buy button).

The **Quests** panel shows the team's quest of the week (name, level, status, when it ends, and the time limits and failure once taken) and the quest each guild slot holds now with the team's hold on it. "Ask for it" calls the offer routes (`POST /api/teams/{id}/weekly-quest/offer`, `POST /api/teams/{id}/slot-quests/{slot}/offer`); taking and finishing a quest stay with the game's dungeons and dialog. A quest's `spec` is the game's own, so the panel never shows it.

## Relationships

A team has a relationship with another team: how it feels about it, as a score from -100 to 100 and a short private note. It is *directed* (Aria's view of Bram and Bram's view of Aria are separate rows) and private: only the team's owner reads it, and the other side never sees a score or a note. Scores have named *bands* (`enemy`, `wary`, `neutral`, `friendly`, `close` by default). Alliances are the same kind of side (see Alliances).

The game has the say, through `Game(relations=...)` (`terraforma.relations.hooks.Relations`). A fight can move them too, only if the game says so: when a fighter moves the gauge of one on another team whose party is not its enemy (an ally, a neutral or a partymate), `Rules.relation_moved(fight, actor, target, resource, before, after, maximum)` returns how much the actor's team's view of the target's team changes (the default is 0, so nothing moves). The rule may instead return `AskPlayer(delta, reason)` (from `terraforma.fights.rules`) to let the player decide: the log gets a `RelationPrompt` event (team, other team, suggested change, reason) for the owner of the actor's team to be asked about, and nothing moves until they answer (the engine's way to ask and record the answer is the after-fight rating prompt, below). A non-zero number is a `RelationChange` event (team, other team, change) in the fight's log, and `fights.store.apply_results` applies what the log holds, added up per pair, through `Game(relations=...)` once (the fight records that it has: a change the game's rules refuse, or for a team that has gone, is dropped). The engine never changes a score on its own; every change goes through `Relations.resolve(session, subject, object, current, change)`, which by default gives what was asked, within the scale. A game also sets `bands`, says where a new relationship starts (`initial`) and who may form one at all (`may_form`), and moves scores from its own rules by calling `terraforma.relations.service.apply(session, relations, Change(subject, object, delta=-5, by="game", reason=...))`. A `Change` says who asked (`by` is `"player"` for the owner in a call, `"game"` for the rules). These are public interfaces (the license exception covers them).

The calls, each its own route, for the team's owner (the ones that change something with the CSRF token, limited to 120 an hour per account): `GET /api/teams/{id}/relationships` (the bands, and this team's own views by name), `POST .../relationships/set` (`id` of the other team, and a `score`, a `note`, or both) and `POST .../relationships/forget` (`id`). A team's relationships go when it is deleted. A team's own page (`/team/{id}`) has a card for them: the team's views by name with their band and note, a form to set a score and a note for another team or alliance by its number, and Forget; the alliance page's card is the same one.

## Alliances

An alliance is a formal power structure of teams: a name, member teams in roles, and invitations. Roles come in three tiers. The **commander** (one team) may do every action. **Subcommanders** may do every action except one that applies to the commander, and may fill the commander's seat when it is empty. Every other role is of **tier 3**: no rank among them, each a set of actions the alliance chooses (like roles in an access list), and it acts on teams of tier 3 only and gives only tier-3 roles. A new alliance starts with the game's `starting_roles`: `treasurer` (the purse), `quartermaster` (the alliance's items), `diplomat` (contracts, and speaking for the alliance) and `recruiter` (invite, withdraw), with `member` the role a team joins as; the `edit_roles` action defines, changes and removes them. The actions are `invite`, `withdraw`, `remove`, `appoint` (give a role), `revoke` (take a role away: the team is a plain member again), `hand_over` (the commander only: the seat goes to another team and the commander becomes a subcommander), `disband`, `speak`, `open_ballot`, `close_ballot`, `vote` and `edit_roles`; `deposit`, `spend`, `set_fight_tax`, `set_sales_tax`, `inventory` and `contract` are named already and nothing uses them yet. The game shapes this through `Game(alliances=...)` (`terraforma.alliances.hooks.Alliances`): `commander_role`, `subcommander_role`, `default_role`, `starting_roles`, `max_members` (counting invited teams), `max_per_team` and `max_roles`, and the hooks `may_found`, `may_join` and `allowed`, the one place to say otherwise (by default the tiers decide, and no team acts on itself). These are public interfaces (the license exception covers them). A game that wants a team in only one alliance sets `max_per_team = 1`.

A team's owner acts for it. A team founds an alliance and is its commander; a role that may invite invites a team, whose owner accepts or declines (it joins in the default role); a team leaves, or is removed; the commander can't leave while others remain and hands the seat over first; the last team out, or a disband by a role that may, takes the alliance with it. A team that is deleted leaves its alliances; if it was the commander and a subcommander is there, the seat stays empty for a subcommander to fill, and otherwise the longest-standing team takes it. Someone with no team in an alliance cannot tell that it exists (404).

The calls, each its own route (the ones that change something with the CSRF token, limited to 120 an hour per account): `GET /api/alliances` (your teams' alliances and the invitations waiting), `POST /api/alliances` (`team_id`, `name`), `GET /api/alliances/{id}` (`?team_id=` reads it as that one of your member teams), `GET /api/alliances/{id}/roster` (members: each team by name and role, with the token of its page only while it is visible and its player's handle and page token only if the player is in the directory), `POST /api/alliances/{id}/invite|withdraw|remove|revoke|hand-over` (`team_id` of the acting team and `target_team_id`), `.../appoint` (also `role`), `.../roles` (`team_id`, `name` and `actions`: makes a role of tier 3 or changes its actions) and `.../roles/delete` (`team_id`, `name`; its holders become members), the alliance view carrying `roles`, `role_actions`, `can` and `appointable`, `.../leave` and `.../disband` (`team_id`), `GET /api/team-directory?prefix=` finds a team to invite (see Following, bans and the directory), `GET /api/teams/{id}/invitations` and `POST /api/teams/{id}/invitations/accept|decline` (`alliance_id`).

**Ballots** put a question to the alliance. A role that may `open_ballot` gives a title (and `kind` and `payload` for the game's own use, which the engine keeps and never reads), two to ten options, whether it is `secret`, and when it closes; each team whose role may `vote` votes once, weighted as `Alliances.vote_weight` says (1 each by default). A ballot closes when its time is up, when everyone who could vote has (`close_when_all_voted`), or when a role that may `close_ballot` closes it; the game decides who wins (`Alliances.decide`, most weight by default, a tie decides nothing) and acts on it in `Alliances.on_ballot_closed`. Nothing waits on a timer: a ballot is closed, if its time is up, the next time anyone looks at it or votes, and `ballots.close_due` closes every due ballot for a game to call on its own schedule. A *public* ballot shows who voted for what, and a team may change its vote until it closes; a *secret* ballot keeps who voted apart from what was voted (the stored vote has no team on it), shows only the turnout until it closes and the totals after, and its votes are final. The calls: `GET /api/alliances/{id}/ballots` and `.../ballots/{ballot_id}` (members read; `?team_id=` picks which of your teams you read as), `POST .../ballots` (`team_id`, `title`, `options`, `kind`, `payload`, `secret`, `closes_in_hours`), `POST .../ballots/{ballot_id}/vote` (`team_id`, `option`) and `.../close` (`team_id`).

**Voting on actions.** An alliance can ask for a vote before an action is done. A *rule* (`AllianceRule`) says that when a team in a role (or any role) does an action, `percent` of the alliance's *active* teams must vote yes (at least that many); no rule, no vote. A team is active if it was selected to play within `Alliances.active_within` (a week of wall-clock time; the engine records it on `Team.last_played_at` when a team plays). The actions a rule can name are `GOVERNED`: invite, withdraw, remove, appoint, revoke, hand_over, disband, edit_roles, set_rules and the ones reserved for the treasury and taxes. Changing the rules is one of them (`set_rules`), so an alliance can make that need a vote too; a new alliance has no rules and its commander and subcommanders do everything without a vote. Any role that may do an action can also put it to a vote on purpose (`vote`: true), which asks `voluntary_percent` (50). A ballot that carries an action (kind `action`; `payload` says which and with what) is voted on by every team whose role may vote, the proposer's yes included, and closes when the yes has its percent of the active teams (or when its time is up, `action_ballot_seconds`, 72 hours unless the caller gives `closes_in_hours`); if it passed, the engine does the action as the team that put it, which must still be allowed to, and the ballot's result says `passed`, `executed` and, if it could not be done, `error`. The action is tried first and taken back, so one that could not be done is refused before the vote opens. A service function called directly for an action that needs a vote raises `NeedsVote`; `ballots.perform` does it or opens the ballot. Three actions are always votes of the members themselves: a team of tier 3 may put it to **all the members** (`elect_subcommander`, `dismiss_subcommander`, `Alliances.subcommander_percent`, 60) to make a team a subcommander or take that away, and a team so elected is safe from `remove`, `revoke` and `appoint` for `subcommander_protection` (a week; only a vote of the members dismisses it sooner); and a subcommander may put it to the **subcommanders alone** (`remove_commander`, all of the active ones) to remove the commander, leaving the seat empty for a subcommander to fill. The calls take `vote` and `closes_in_hours` besides what they did: `POST /api/alliances/{id}/invite|withdraw|remove|appoint|revoke|hand-over|disband|roles|roles/delete`, and the new `.../rules` (`team_id`, `action`, `role`, `percent`; null drops it), `.../elect-subcommander`, `.../dismiss-subcommander` (`target_team_id`) and `.../remove-commander`. They answer with the alliance as before, or `{"ballot": ...}` when a ballot was opened (`{"disbanded": true}` when the alliance went). The alliance view lists its `rules`.

**The treasury.** An alliance holds gold (`Alliance.gold`, in its view). A team gives some with `POST /api/alliances/{id}/deposit` (`amount`), taken from the team's first hero, and a deposit is a gift: it belongs to the treasury, and leaving or being removed returns nothing. A role that holds `spend` pays gold to a member team with `.../spend` (`to_team_id`, `amount`). Both are actions like the others, so a rule can ask for a vote first; a plain member holds `deposit` by default. Where the gold comes from and goes to is the `Alliances.economy` hook, which `create_app` binds to the game's `economy` unless the game's `Alliances` chose its own. When an alliance is dissolved (disbanded, or its last team leaves) the treasury is split by shares among every team that was ever in it, including those who left or were removed (`AllianceAlumnus`): a team that played within `share_month` (30 days) has `max_shares` (12), one fewer for each further month since it last played, and none after a year. Coins that don't divide go to the heaviest shares first; gold nobody holds a share of leaves the economy.

**Taxes.** An alliance keeps a share of what its own member teams earn. It sets two rates, each a whole percent up to `Alliances.max_tax_percent` (50): `fight_tax` on gold earned from fights and `sales_tax` on gold earned selling on the marketplace (fixed prices and won auctions; `POST /api/alliances/{id}/fight-tax` and `.../sales-tax` with `percent`, the actions `set_fight_tax` and `set_sales_tax`, which a rule can ask a vote for and the Treasurer holds by default). The tax is taken as the earnings are paid and goes to the treasury, rounded down, so a small earning can owe nothing. A team that left or was removed is not taxed, and a team in several alliances pays each, never more than it earned. The tax comes out through `Economy.credit_earnings`, which asks the economy's `taxman` (`create_app` sets it to the alliances' collector on the game's economy) before `credit_team` pays the rest; a game that earns gold some other way calls `credit_earnings` with `FIGHT` or `SALES` to have it taxed too. Selling to an NPC shop (`market`) is not taxed.

Alliances are sides in relationships too (see Relationships): a team can have a view of an alliance (`kind: "alliance"`), and an alliance has views of teams and of other alliances, read by its members and set by a role that may `speak` (`GET`/`POST /api/alliances/{id}/relationships`, `.../set`, `.../forget`).

**Rating after a fight.** When a fight between player teams ends, a team that was helped or harmed by another player team (read off the experience debts the fight kept: a hit, a heal, a status) and has no opinion of it is asked to rate it (`terraforma.relations.ratings`): a question kept until the player answers or dismisses it. Nothing changes by itself: an answer is an ordinary change to the relationship, so the game's `Relations.resolve` still decides the score that results, and `Relations.ask_after_fight(session, subject, object, interaction, score)` decides whom to ask at all (by default: only a team in the neutral band, `interaction` being `helped`, `harmed` or `both`). Monsters and a team's own side are never asked about. A game's own rule can ask too: a `RelationPrompt` event in the log (from `Rules.relation_moved` returning `AskPlayer`) always raises a question (the game said so), which carries the suggested change and the reason and can be accepted as it stands. The calls (each its own route, a login; the two that change something with the CSRF token, in the same 120 an hour): `GET /api/ratings` (the bands and the open questions, with the teams' names, the fight's public name and any suggestion), `POST /api/ratings/{id}/answer` (a `score`, -100 to 100, or `accept: true` for the suggestion) and `POST /api/ratings/{id}/dismiss`. A team's questions go when it is deleted. The browser client has a **Ratings** panel for them: each open question says who helped or harmed which of the player's teams (or the game's reason, when its rule asked), with a score box (-100 to 100) and Rate, an Accept button with the suggested change when the game made one, and Dismiss; the answer is shown as the server gives it (the other team's name, band and score).

## Using items in the field

A potion, an ether or a revive can be used outside a fight: `POST /api/heroes/{id}/use-item` (login and CSRF token; a strict body: the item's `position` and an optional `target_hero_id`, the user's own hero when left out) spends one of the item on one of the *caller's own* heroes (`terraforma.heroes.field.use_item`). What it does is `Rules.field_use(rng, effect, vitals, maximums)`: by default the item's own `use_effect` as in a fight (heal and restore mana for the living, revive for the dead; anything else is for fights only), and a game overrides it to allow more or less. The new HP and MP are kept on the hero (`Hero.vitals`). A hero in a fight that is still running can neither use nor receive an item (the fight has its own item command), and a use that would change nothing is refused and costs nothing. The roll comes from the world's stream for that hero, item and stack size, so it never uses the `random` module.

**Helping another party.** `POST /api/heroes/{id}/help/use-item` (login and CSRF token, limited to 120 an hour per account; a strict body: `position`, the item's place in the hero's pack, `party_id`, and `member`, the place of the target in that party's heroes, counting from 0 team by team) spends the item on a hero of a party in reach, the same field use as above (`terraforma.reach.helping`). The target is named by its place so a player never learns the id of a hero in a team they cannot see, and the answer carries `party_id`, `member`, `before`, `after` and `used_up` but no hero id. The party must be in range for the `help` action (`Reach.party`, one tile by default, and the nearby list for `help` shows parties), and the hero's team must not count it as an enemy: `Rules.may_help(stance)` gets the stance `Rules.party_stance` gives (ally, neutral or enemy; teams that never met count as enemies, as in any fight) and returns None or why not, and by default refuses only an enemy. A party's own members need no stance. The other player is not asked, since helping only gives. Only items so far; abilities used on a friendly party come later.

**Abilities in the field.** A hero casts an ability it knows outside a fight with `POST /api/heroes/{id}/use-ability` (login and CSRF token; a strict body: the ability's `ability` key and an optional `target_hero_id` of one of the caller's own heroes, the caster when left out) and, as help, with `POST /api/heroes/{id}/help/use-ability` (limited like the item help; a strict body: `ability`, `party_id` and `member`), under the same reach (`help`) and `Rules.may_help` rules as an item. What the cast does is `Rules.field_use`, the rule items use (by default heal, restore mana and revive; anything else "can only be used in a fight"), so a game changes both at once; what it costs is `Rules.ability_cost` (mana, `mp_cost`, by default), taken from the caster's stored resources. The caster must know the ability and be alive and able to pay; a cast that is refused, or would change nothing, costs nothing. The field always has one target, so an ability's wider `targets` are ignored there. The roll comes from the world's `field-ability` stream (the caster, target, ability and the caster's resource), never the `random` module. The answer carries the target's resources before and after, the `cost` and the `ability`.

## Chat

Players talk in *channels*. A channel is a kind and a key (`("party", "12")`), and every kind answers the same few questions (`terraforma.chat.hooks.ChannelKind`): how a key the player gave becomes the stored one (`resolve`), who is in the channel (`member`, which means read and speak), which channels a player is in now (`channels`), and who hears a message said from a place (`hears`). The calls know nothing about any one kind, so a game adds a channel (a guild, a dungeon run) by writing a `ChannelKind` and listing it in `Chat.kinds`, and drops one by leaving it out. The engine has six: `party` (players with a team in the party; key: the party id), `alliance` (players with a team in the alliance; key: the alliance id), `nearby` (the map the player stands on, heard within `NearbyChat(range=10)` tiles; key: the map id), `town` (whoever stands where `Towns.is_town` says; key: the map id), `global` (every player; key `all`) and `whisper` (two players; the key is the other player's handle, or the pair as the channel list gives it). A team's chat is not a kind: a team belongs to one player.

A game hands `Game(chat=...)` a subclass of `Chat` to set `kinds`, `body_max` (500), `history` (50), `flag_reasons` (`tou`, `spam`, `harassment`, `other`), `clean` (how the text is kept; a place to filter words) and `may_speak(session, speaker, kind, key, body)` (a reason a player may not say this now, or None). This is a public interface (the license exception covers it).

Messages are saved with the place the speaker stood, and fetched, not pushed: a page asks for the lines after the last one it holds, so any server can answer. A player needs a handle to chat, and only the handle is ever shown. The calls (each its own route, a login; those that change something with the CSRF token): `GET /api/chat/channels`, `GET /api/chat/messages?kind=&key=&after=&limit=` (latest lines, or the lines after `after`, oldest first; lines from muted players and ones out of hearing are left out), `POST /api/chat/say` (`kind`, `key`, `body`; 600 an hour), `GET /api/chat/mutes`, `POST /api/chat/mute` and `/unmute` (by handle; a mute follows the player into every channel and hides their whispers too), `GET /api/chat/reasons` and `POST /api/chat/flag` (`message_id`, `reason`, `note`; the player must be able to see the message, and flagging twice is one flag). For admins: `GET /api/chat/admin/flags?state=open` (each flag with the message and the five lines before it) and `POST /api/chat/admin/settle` (`flag_id`, `state` `actioned` or `dismissed`; what acting on a flag means is the game's own). The Chat panel (`chat.js`, one of the engine's panels) lists the player's channels, polls the open channel every three seconds for the lines after the last one it holds, and has a send box, a whisper box (by handle), a mute list, a Flag button on every line that is not the player's own, and, for an admin (`admin` in the channel list), the flags to settle. An admin can bar a player from speaking (`POST /api/chat/admin/ban`: `handle`, `hours` or none for good, `reason`; they can still read; `GET /api/chat/admin/bans`, `POST /api/chat/admin/unban`; an admin can't be barred, and one ban per player, a new one replacing the old). Settling a flag as `actioned` calls `Chat.actioned(session, admin, sender_id, message, reason)`, the game's place for its own consequence (a warning, `chat.service.ban`); the engine does nothing more by itself. The Chat panel shows the bans to an admin, with a Ban 24 hours button on every flag and a Lift button. Housekeeping removes messages older than `chat_retention_days` (settings, 7 by default, 0 keeps them for good), except those with a flag no admin has settled.

## Voice

The engine does not carry audio. A voice *provider* outside it makes the rooms, and the engine gives a member a link to one (`terraforma.voice`). Discord is the provider the engine ships; it is optional and off unless `settings.toml` sets both `discord_bot_token` and `discord_guild_id` (the id of the Discord server the bot may make voice channels in; the bot needs Manage Channels and Create Instant Invite there). A room belongs to a chat channel (see Chat): `Voice.kinds` says which kinds have one (`party` and `alliance` by default), `Voice.room_name(kind, key)` what it is called, and `Game(voice=...)` hands a game's subclass in. The membership is the chat channel's own, so whoever is in the party or alliance may join its room and nobody else gets a link.

The calls (each its own route, a login; the second with the CSRF token, 60 an hour): `GET /api/voice` (`enabled` and the `kinds` that have rooms; the Chat panel shows a Join voice button for those) and `POST /api/voice/join` (`kind`, `key`; the answer is `url` and `seconds`). The first member to ask makes the room (`voice_rooms`, one per channel, kept so two servers share it: a room made twice is closed again), and every member gets a fresh single-use invite that lasts five minutes. Housekeeping (`old_voice_rooms`) closes a room at Discord `voice_room_hours` (24) after it was made; one Discord will not close is tried again at the next pass. Discord's REST API is called over the standard library, so there is no new dependency, and the bot token is never logged. A refusal or an unreachable Discord is a readable 502.

What it cannot do: Discord voice cannot be embedded in the browser, so players need the Discord app or site and an account, and an invite lets whoever holds it join the Discord server. The rooms are visible to everyone in that server (names like `party-12`, never a player), so use a Discord server meant for the game. Making a room private to its members needs each player's Discord account linked (OAuth) and a permission per member: not built yet. Built-in browser voice (WebRTC) is a later option behind the same `VoiceProvider` interface (`open_room`, `invite`, `close_room`).

## Profiles

A player, a team and an alliance can each have a public page, reached by a **random token** (22 characters, from `secrets`) rather than a name or number, so a page can't be guessed. The owner can replace the token at any time; the old one stops working at once. A page shows only what its owner chose, and never an account id, username or email.

- **Visibility** is set per team, and it is the real switch: a team is *hidden* until its player makes it *visible* (`PUT /api/profile/team-visible`, `team_id` and `visible`; the player can hide any or all of their teams). A visible team's page can be reached from the player's page and from the pages of the alliances it is in; a hidden team has no link or page (404), though its name still shows on its alliance's page. The *directory* is a separate opt-in (`PUT /api/profile/directory`, `enabled`, off by default): while a player is in it, their handle appears next to their visible teams in an alliance's roster, and alliance members can go from a team's page to the player's page.
- **The player's page** (`GET /api/p/{token}`, no login): the player's public handle (`null` if none is set), a short bio of up to 500 characters, and the player's visible teams, each named with the token of its page. It is always public to anyone holding the link. The owner makes it with `POST /api/profile/token` (which also replaces it), reads it with `GET /api/profile` (the teams with their `visible` flags, and `directory`), sets `PUT /api/profile/bio` (`bio`) and replaces a team's address with `POST /api/profile/team-token` (`team_id`).
- **A team's page** (`GET /api/p/team/{token}`): the team's name and the alliances it is in (each with its page token once the alliance has one), and the player's handle only if the player is in the directory. It exists only while the team is visible (otherwise 404).
- **An alliance's page** (`GET /api/p/alliance/{token}`): its name, a short description and *every* team in it by name and role, so anyone can see which teams belong (never their members). Only a *visible* team also has its page token, and its player's handle if the player is in the directory; a hidden team shows its name alone (`page` is null). Members read the alliance's own profile with `GET /api/alliances/{id}/profile`; a team whose role may `speak` makes and replaces it with `POST .../profile/token` and writes it with `PUT .../profile/bio`. Members of an alliance open a visible member team's page with `GET /api/alliances/{id}/teams/{team_id}/profile` (a login; 404 to anyone else, or for a hidden team), which also carries `player`, the token of the player's page, when the player is in the directory. The directory's listing of players, where others find a page, comes later; this opt-in is what it will read.

The owner's calls need a login and, to change anything, the CSRF token, and are limited to 60 an hour per account. The public pages need neither, and are limited per address (120 per 15 minutes) so a token can't be hunted for. Deleting a team or disbanding an alliance deletes its page. These routes and their response shapes are public interfaces (the license exception covers them).

## Challenge Tokens

Challenge Tokens are a special currency: one balance per account (`ChallengeBalance`), with a ledger of every change (`ChallengeEntry`: who, how many, why, which fight or purchase) so a balance can always be re-derived (`challenge.service.audit`). The game decides what they are worth and what limits them; the engine keeps the books.

- **Earning.** `Rules.challenge_earned(fight, address)` says what a hero's fighter earns when a fight ends (this is where a game sets its earning rates); it pays nothing by default, so a game opts in. `fights.store.apply_results` pays it, once per account per fight (the ledger holds a unique fight and account pair, so saving the result again pays nothing more). Tokens are only ever paid to the account that owns a hero in the fight, so an admin (`Account.is_admin`) earns only when fighting as a player, never for a monster or a fight they watched. No call sets `is_admin`: a game's own setup does, with `challenge.service.set_admin`.
- **Limits** (both default to none; the game decides). `Rules.challenge_daily_cap(account_id)` is the most an account may *earn from fights* in a UTC day: what would go over is not paid. `Rules.challenge_purse_cap(account_id)` is the most an account may hold: earnings are cut to fit, and a purchase that would not fit is refused whole (nobody pays for tokens that are thrown away). The daily cap does not limit purchases or spending, and neither cap ever takes tokens away (a purse over a lowered cap keeps what it has and earns nothing until it is under). A fight whose pay was cut to nothing is still recorded as paid, so it does not pay again the next day. The daily total is read before it is paid, so two fights that end at the same instant for one account can overshoot the day's cap slightly; the purse cap is exact.
- **Spending.** A game spends through `challenge.service.change(session, account_id, -amount, reason)`, which refuses to take the balance below zero (`NotEnoughTokens`).
- **Buying.** A game that sells tokens sets `challenge_purchase_secret` in `settings.toml` (at least 32 characters; empty, the default, turns the call off and it answers 404). Its own backend (a shop or payment service, never a browser) then credits a purchase with `POST /api/server/challenge/purchase`, sending `Authorization: Bearer <secret>` and `{"account_id": 7, "amount": 50, "key": "order-1234"}`. There is no login, cookie or CSRF token for this call; the secret takes their place. `key` is the caller's idempotency key (8 to 64 letters, digits and `_.:-`): sending the same key again with the same account and amount (a retry) credits once and answers the same with `"duplicate": true`. The answer is `{"credited": 50, "balance": 120, "duplicate": false}`. 401: wrong or missing secret. 404: the call is off, or no such account. 409: the key was used for a different purchase, or the purse cap would be passed (nothing is credited). Every attempt counts against the caller's address (600 per 15 minutes), the secret is compared in constant time and logs scrub the header. The game's backend does the charging and credits only what was paid; the engine takes no payment.

- **The store's grant.** A game whose store grants (or takes) tokens and items sets `store_grant_secret` in `settings.toml` (at least 32 characters; empty, the default, turns the call off and it answers 404; it is a different secret from the purchase one). The store's backend then calls `POST /api/server/store/grant` with `Authorization: Bearer <secret>` and `{"subject": "<the player's sign-in subject id>", "tokens": 50, "items": {"potion": 3}, "message": "Order #1234 arrived.", "email": true, "key": "order-1234"}`. `tokens` is added (negative takes tokens back, a spend; it never takes the balance below zero), `items` maps a content key to a quantity of at least 1, and `message` is the transaction note: the engine emails it to the player (`email` defaults to true), so the store never learns the player's address; nothing is mailed to an account with no confirmed address, and a mail that fails does not undo the grant. A grant changes tokens or gives items, at least one. Like the purchase call there is no login, cookie or CSRF token, and `key` is the store's idempotency key (8 to 58 letters, digits and `_.:-`): the same key with the same grant again changes nothing, mails nothing again and answers `"duplicate": true`. The answer is `{"balance": 120, "duplicate": false, "emailed": true}`. 401: wrong or missing secret. 404: the call is off, or no such player (subject) or active item. 409: the key was used for a different grant, the balance would go below zero, the purse cap would be passed, or an item would pass 1,000,000 in the parcel (nothing changes). 422: the game's rule refused (its reason is in `detail`) or the grant does nothing. The ledger stays in the engine (`reason` is `store`, key `store:<key>`), and the daily cap does not apply. **The game's rule has the final say:** `Rules.store_grant(account_id, tokens, items, message)` (the game still sees the account) runs before anything changes and returns None to grant it (the default) or why not; the store is shown the reason. Granted items land in the account's parcel (`Parcel`, read with `storegrant.service.parcel`), a holding place: the player moves them to a hero's side with `POST /api/heroes/{id}/parcel/collect` (login and CSRF token, rate-limited; a strict body: the item's `item` key and a `qty`, 1 by default), which hands them to the game's storage (`storage.service.deliver`: storage first, then the packs the storage shares with), so the game's storage rule decides where they land; what fits is taken and the rest stays in the parcel, and the answer is `{"taken", "waiting", "stored", "packed"}` (422 when the parcel holds none of the item or the hero is in a running fight). `GET /api/parcel` (login) says what waits. The store names the player by the opaque `subject` id the closed sign-in provider (X2) gave it as `sub`, never by an account number; a subject that no player has is a 404. Every attempt counts against the caller's address (600 per 15 minutes).

`Rules.challenge_earned`, `challenge_daily_cap`, `challenge_purse_cap`, `Rules.store_grant`, the `challenge.service` and `storegrant.service` functions, the purchase call and the store's grant call are public interfaces (the license exception covers them). They replace `Rules.tokens_earned` and `terraforma.tokens` of the admin tokens: a game that overrode `tokens_earned` renames it to `challenge_earned`, and the balances and ledger are in the new tables from the start (no data had to move).

A game's own rules set the limits and rates. Example for Vanguard Tavern, which adopts DragonStar's numbers (from DragonStar's `MonsterToken`: in DragonStar tokens are earned by playing the monsters in a fight, 1 for playing it through and 1 more for winning it, with at most 3 earned in any 24 hours and no limit on how many are held):

```python
class VanguardRules(Rules):
    def challenge_earned(self, fight, address):
        return 1  # DragonStar: 1 for playing a fight through (a win earns 1 more: see the note below)

    def challenge_daily_cap(self, account_id):
        return 3  # DragonStar: at most 3 earned a day

    def challenge_purse_cap(self, account_id):
        return None  # DragonStar has no limit on what is held
```

The engine differs from DragonStar in three ways, so the example is close, not identical. (1) The engine pays the heroes' owners, as `challenge_earned` is called for hero fighters only; paying a player who controls the monsters, as DragonStar does, is for the game's own code (``challenge.service.change`` with `reason` ``fight``, which the daily cap counts) until the engine has a monster side. (2) The engine's day is the UTC day; DragonStar's is a rolling 24 hours. (3) DragonStar pays a fight's whole award to a player still under the limit when it ends (so a winning fight can carry them to 4); the engine cuts the award to fit the cap (to 3). A game that wants DragonStar's exact behaviour, a win's extra token included, would need hooks for these; say so and they can be added.

## The engine as a sign-in provider

A game's store (or any other site the game maker owns) can sign players in with their game account, so the player has one login. The engine is a **closed OpenID Connect provider**: only the sites listed in `settings.toml` can use it, each with its own secret and its exact redirect addresses. With none listed (the default) every address below answers 404 and nothing is exposed.

```toml
[[oidc_clients]]
client_id = "store"
client_secret = "at least 32 random characters"
redirect_uris = ["https://store.example.com/callback"]   # compared exactly: no patterns, no prefixes
name = "The store"                                       # a note for you; players are not shown it
```

`redirect_uris` must be `https://` addresses with no `#fragment` or user name (plain `http://` only for `localhost`, `127.0.0.1` and `[::1]`, for development). Each `client_id` appears once. The issuer is `public_url`.

- **The flow.** Authorization code with PKCE, and nothing else: the site sends the player's browser to `GET /oidc/authorize` with `response_type=code`, `client_id`, `redirect_uri`, `scope`, `state`, `nonce` (optional) and `code_challenge` with `code_challenge_method=S256` (PKCE is required; `plain` is refused). A player who is signed in goes straight back to the site with `code`, `state` and `iss` in the address; one who is not goes to the login page and then back (`prompt=login` makes a signed-in player log in again, `prompt=none` answers `login_required` rather than showing a login). There is no consent screen, since the sites are the game maker's own. The site's **server** then calls `POST /oidc/token` (a form: `grant_type=authorization_code`, `code`, `redirect_uri`, `code_verifier`; sign in with `client_secret_basic` or `client_secret_post`) and receives `access_token`, an ES256-signed `id_token` and `expires_in`. Discovery is at `/.well-known/openid-configuration` and the public keys at `/oidc/jwks`, so any OpenID Connect library can be pointed at the issuer.
- **What the site learns.** The ID token has `iss`, `sub`, `aud`, `iat`, `exp` (ten minutes), `nonce` and, with the `profile` scope, `preferred_username`: the player's **public handle**. `GET` or `POST /oidc/userinfo` with `Authorization: Bearer <access_token>` (an hour) answers `sub` and the handle too. `sub` is an opaque random id, **different for each site** (two sites cannot tell they have the same player) and stable for a player at one site. The site never receives the username or the email address. Scopes the engine does not offer (`email`, `offline_access`) are ignored; there are no refresh tokens, so a site signs the player in again when the access token runs out.
- **What is refused.** An unknown `client_id` or a `redirect_uri` not listed for it is shown as an error and the browser is **not** redirected. Other mistakes go back to the site with the standard's `error` (`invalid_request`, `invalid_scope`, `unsupported_response_type`, `login_required`, `access_denied` for a player who has not yet chosen a public handle). A code works once, for a minute, only for the site and `redirect_uri` it was made for and only with the matching `code_verifier`; showing a code a second time revokes the tokens it made. A password reset or any other end of all logins (`session_version`) also ends the codes and access tokens made before it.
- **Keys.** ID tokens are signed with a key derived (HKDF) from the engine's encryption key of the same slot, so nothing more is stored or backed up and `python -m terraforma keys rotate` rotates the signing key too. The key set lists the current key and the previous one, so a token signed just before a rotation still checks out until the next. The `kid` is the key's RFC 7638 thumbprint. The algorithm is ES256 (P-256); RS256, the standard's default, is not offered.
- **Limits and logs.** The browser's steps and the site's calls have no login or CSRF token (a site's server has neither): the secret and the access token take their place, and each call is rate limited by the caller's address (`authorize` and `resume` 120 and `token` 300 per 15 minutes, `userinfo` 600; a store's server shares one address across all its players). Logs are scrubbed of codes, verifiers, secrets and tokens, and only the SHA-256 of a code or token is stored. Housekeeping removes the ones that have run out.

The `[[oidc_clients]]` settings, these addresses and the claims are public interfaces (the license exception covers them).

## Fight rules

A fight is DragonStar's process: every fighter has chosen a command (attack with the left or right hand, use an item, change gear, use a skill, cast a spell, defend, run), then the round resolves in one pass and returns *events* (`Turn`, `Attack`, `Damage`, `Miss`, `Died`, ...) that say what happened. The fight's state after the round is what you get by applying its events in order (`terraforma.fights.replay.apply_events`), so a stored fight can be replayed and shown to spectators.

- **The rules** are the class `terraforma.fights.rules.Rules`, and `Game(rules=...)` hands the engine yours. `Rules()` is DragonStar's, unchanged: speed (the fighter's Speed spread by 15%, a caster slowed by the spell's cost against their Focus, multi-strike weapons acting several times, ties shuffled), the hit roll (always out of 100: it hits on a roll up to Accuracy ÷ (Accuracy + Dodge) as a percentage, so a critical, a roll of 1 that doubles Strength, is one hit in a hundred whatever the stats are), damage (Strength against Block, scaled by how cleanly the roll hit, from half at the edge of the hit chance to full at a 1, halved when defending, never under 1), the saving throw (Power against Resistance: none, half or all of a harmful spell gets through), and what each effect does. A game overrides any of them:

  ```python
  class MyRules(Rules):
      stats = (*Rules.stats, "Luck")

      def chance_to_hit(self, rng, accuracy, dodge):
          ...
  ```

  This is a public interface (the license exception covers it): the method names and signatures are what games build on.
- **Stats and resources.** `Rules.stats` is the list seeds are checked against. A *resource* is a stat that is a pool: its base is the maximum and its current value what's left. `Rules.resources` lists them (HP, which is life, and MP by default); a game adds its own (rage, technique points) and fills and drains them from the hooks `ability_cost`, `gauge_moved` (called whenever one fighter moves another's resource) and `after_event` (called for every event, and may add more).
- **Statuses and stat values.** `Rules.stat_value(stat, geared, bonus)` sums a stat's geared base and its statuses' bonus and clamps it; `Rules.slay_chance(rng, effect)` decides a slay; `Rules.status_acted(...)` is the hook for a token's source earning from it (see Statuses).
- **Allies, enemies and neutrals.** How parties stand to each other is `Rules.alignment(fight, party)`, returning that party's (allies, enemies); a party in neither is neutral to it. A party is always its own ally. Each `Party` may carry its own `allies` and `enemies` sets; with neither set, as in DragonStar, each party is for itself and every other party is an enemy. The seed's `all_allies`, `all_enemies`, `all_not_allies` and `all_not_enemies` targets follow it, and a game can override `alignment` for alliances and factions.
- **Fleeing.** The `flee` command is a try: it rolls against `Rules.flee_chance(fight, address)` (the fighter's Speed against the Speed of every enemy still in the fight, added up: `100 * mine / (mine + theirs)`) with `Rules.flee_succeeds(rng, chance)`, a `Run` event and then `Fled` or `FleeFailed`. A try that fails costs only the fighter's turn. When it works, `Rules.flee_party(fight, address)` says who leaves: by default the whole party (every fighter of it still standing, one `Fled` event each); a game that wants only the fighter returns `[address]` (Vanguard Tavern's way: the fighter comes back to its party's place when the fight is over). A fighter that fled stays in the fight's layout, so its address and earnings are kept, but it has left: it takes no turn, can't be aimed at (an attack at its place lands on a neighbour who stayed), its statuses don't tick, and its party counts as gone once no one of it is left (`Combatant.present`, `Party.dead`; a fighter that fled is still `alive`). `Rules.flee_allowed(fight, address)` says whether it may be tried at all: the fight's `can_flee` flag, which the map's zone sets (`can_flee`, on by default) or a scripted fight turns off (`live.start_team_fight(..., can_flee=False)`); where it is off the live fight refuses the command (409) and a `Run` in a replay comes to nothing. Monsters never flee by their own choice (the AI does not pick it). **Eject** is an ability (`"effect": "eject"`) that forces its target out the same way: its `base` is the chance out of 100, moved by the user's Power against the target's Resistance to between half and double of it (`Rules.eject_chance`, never over 100); a success is a flee for the target (so `flee_party` and `flee_allowed` apply), it refuses the user's own side unless the effect is `friendly`, and one that does not work says `NoEffect`. **What it pays.** A fighter that fled still earns what it did (half of its own credit) but loses its share of its party's and its team's pools, which are worked out for those left as if it had stayed (they claim the share its work earned). Gold and drops go only to a team with a hero alive at the end (one that fled counts; the gold is split between those teams), and a monster that was ejected is not dead, so it leaves no gold or drops. A party of players that stayed to the end and is all down has suffered a loss: a `PartyLost` event, and `Rules.party_lost(fight, party)` for the game's own rule (where it wakes up, what it pays; nothing by default). A party that all fled has lost nothing; a game decides other outcomes by how many fled in `Rules.fight_is_over` and `party_lost`. A hero that fled is free of the fight (`FightParticipant.fled`) while the others play on: it can walk, leave a town or start another fight, its HP and MP are saved as they stood when it left, and when the fight ends what the end of it paid the hero (experience, level-ups) is *added* to the hero, once, rather than written over what it has become since. These are public interfaces (the license exception covers them).
- **What PXP counts.** A fighter's PXP (`Rules.pxp`, `fights.potential`) rates its defence, its weapons and what it can cast or do, with gear counted. *Being under a status changes nothing*; *being able to cause or remove one does*: a status effect is worth `base * added` plus 10 for each round it lasts (`STATUS_ROUND_WORTH`; the ability's `duration`, else 3 rounds, at most 10), by the usual reach rating (one target 1, a group 3, a party 9), and `steal_mp`, `transfer_hp` and `transfer_mp` are rated like `steal_hp` and `heal` (`base` plus half of `added`). The status's own definition is not read, so an ability rates the same for a hero and a monster whatever the fight knows. A game with other ideas overrides `Rules.pxp`. (Mike, 2026-10-16.)
- **Experience, gold and advancement.** Whenever one fighter moves another's life or mana, `Rules.gauge_moved` makes the target *owe* the actor experience (an `XpDebt` event: the share of the gauge that moved, at the target's `Rules.pxp`, DragonStar's potential experience). When `Rules.fight_is_over` first holds (one party left, or only allies), `Rules.on_fight_end` pays the debts out with DragonStar's experience tree (`fights.experience`): half to whoever earned it, 20% pooled across its party and 30% across its team, for harm done to non-allies and help given to non-enemies; only fighters on a team (`Party.teams`) earn, monsters and NPCs only dilute the pools. Dead enemies' gold is split between each party's teams (`Gold` events), and `Rules.advance` levels up whoever has the experience (`LevelUp`: each stat grows 75 to 100% of the job's growth, from the fight's stream, up to `Rules.max_level`; `Rules.experience_needed` says how much each level takes). Override `on_fight_end` or `advance` for other rewards. Once the payout is made the fight is *over* (a `FightOver` event, and `Fight.over`): it plays no more rounds, so nothing is paid twice, and `fights.store.play_round` raises `FightOver` if asked for another. `fights.store.apply_results` then saves each hero's experience, level and stats to the database and teaches it the abilities its job grants at its new level (it sets rather than adds, so calling it again is harmless). It also saves what each hero's resources (HP, MP, ...) stand at in `Hero.vitals`, and `fights.build.hero_fighter` brings a hero into its next fight with them (never above the maximum in `Hero.stats`; a hero that has never fought, or been rested, is full). A hero that ended a fight at zero HP starts the next one dead. The engine never regenerates heroes between fights: a game calls `heroes.service.rest_hero(hero, rules)` from its inn, potion, camp or level rest, and `Rules.rest(vitals, maximums)` decides what that does, for the living and the dead alike. The default fills everything and revives the dead in full; a game overrides `rest` to bring them back at 1 HP, at half, or to heal only a part (a game that wants regeneration over time calls `rest_hero` itself). A team's heroes reach a fight with `fights.build.team_party`, which also gives the `Party.teams` the experience tree needs.
- **Monster AI.** `fights.ai.choose_command(rules, fight, address, rng)` picks a fighter's command from its four numbers (a monster's `ai` block: `action`, `goal`, `target`, `experience`; DragonStar's meanings, in `fights.ai`): what kind of player it is, what it wants, how well it judges its target, and how much it misjudges stats. `profile_for_level` gives a hero on autopilot its numbers. It draws only from the stream it is given, so fights replay. The engine adds what DragonStar left as notes: what statuses and stat changes are worth to the AI (`Rules.status_worth`, reckoned in hit points by `fights.ai_status`; override it for your own way) and its own play for the Protector (heals, cleanses and buffs the weak and afflicted), Hinderer (bad statuses first), Smart (weighs every command and takes the best) and Omnipotent (as Smart, seeing every stat exactly) actions. It departs from DragonStar in three places, each noted in `fights/ai.py`: stats are read skewed by the fighter's experience percent (DragonStar's formula reads them as a hundredth), a command that reaches neighbours adds up the neighbours' values, and the Fighter and Mage actions keep the better half of their targets, not the first half.
- **Dice.** Never the `random` module: every roll comes from a `WorldRng` stream, one per fight under its map (`fight_stream(world_rng, map_name, fight_id)`), drawn in a fixed order, so the same fight replays exactly.
- **Storing a fight** (`terraforma.fights.store`): a fight is its *initial state*, written once when it starts (`fights.state.dehydrate` turns a `Fight` into plain JSON and `hydrate` back), plus an append-only log of rounds. Each round records the commands that led to it, the events it produced, and a hash of the round before (the first chains from a hash of the initial state), so a changed or missing round shows. `load_state` rebuilds the fight now by replaying the log; `verify` checks the chain, and with `deep=True` plays every round again from its commands and its own dice (`fight_stream(world_rng, map, fight_id, round)`) and expects the same events. Anyone not given a command in a round defends. Heroes and monsters become fighters with `fights.build.hero_fighter` (with the HP and MP the hero has kept, see Experience above) and `monster_fighter`.
- **Pure.** `terraforma.fights` (apart from `store` and `build`) has no database or web code. Heroes and monsters become fighters through `terraforma.fights.content`.

## Live fights

A fight waits for its round (`terraforma.fights.live`). **Starting** one is the server's business: a player has no call to start a fight against monsters. `live.start_team_fight(session, team, monster_keys, rules)` puts a team against monsters where the team stands. Once there are maps, a fight comes from a random encounter while walking or from an NPC whose dialog starts one; until then the hub's **Leave Town** (see Towns) stands in for walking the map into a fight. A fight between players is the one a player asks for, and only against a party they meet (see Fights between parties). A hero can be in one unfinished fight at a time. **Scripted NPC fights.** A dialog starts a fight itself with `npc_fight,name,monster+monster,label` (monster keys from `monsters.json` joined by `+`, 1 to 20; the seed is refused for a monster it does not have): the party the hero acts in fights those monsters (an ordinary fight, `monster_play` off), the dialog is over, and each team of the party is tied to the fight under the dialog's own `name` (up to 64 characters; `ScriptedFight`, swept with the fight and deleted with the team). The label is where the script goes if the party cannot fight now (apart in a town, a hero already in a fight; the same refusals as any fight) and the dialog is an error without the game's `Rules`. Later, any dialog asks how it ended with `npc_fight_result,name,won|lost|running,label`: it goes on if the talking hero's team's *latest* fight under that name is in that state (`won`: the team won it by the fight's own scoring; `lost`: it is over and the team did not win, fled included; `running`: not over, which only a hero who fled it can ask, as a hero in a fight cannot talk), and otherwise, or with no such fight, to the label. A new `npc_fight` under the same name replaces the old answer. What a win or loss means (a reward, a story step) is the game's: its dialog reads the result and uses the other tags. The two tags are what games author against, so they are covered by the license exception.

- **Commands.** `POST /api/fights/{id}/commands` (login and CSRF token; a strict body: the fighter, the command, what is used, the target) commits a command for one of the *caller's own* heroes' living fighters; sending another replaces it. Nothing else can command a fighter: the monsters are on the AI.
- **Rounds.** The round plays as soon as every player's living fighter has committed, or when `Rules.round_seconds` (30 by default) run out, whichever comes first; a fighter that has not committed defends. The monsters choose with the AI (`fights.ai`) from a stream of their own under the round's, and the commands that were used are stored with the round, so replays never run the AI again. Time here is the wall clock (players are waiting); everything else is the fight's own dice.
- **Play time.** Each account has the seconds it has played, in wall-clock time (`terraforma.playtime`; `GET /api/play-time`, login, answers `{"seconds": n}`). Every call that needs `ActingAccount` (login and CSRF token) counts as the player's input and credits the next `Rules.play_credit_seconds` (10), or less if the next such call comes first; reads count for nothing, and a refused CSRF token credits nothing. A fight's playback counts too: the page tells the server it has finished showing a round with `POST /api/fights/{id}/playback-done` (`{"round": n}`, login and CSRF token, only for a fight the caller has a hero in), and the time from when the round was played (`FightActionRecord.played_at`) to now counts, at most `Rules.playback_cap_seconds` (300) so a closed tab earns nothing more. A stretch of time counts once however many ways it is claimed, so play time can never run ahead of the clock. The follow cap (Social slice b) is built on it (default 10 follows plus 1 per hour played).
- **Following, bans and the directory** (`terraforma.social`). `POST /api/follows` (`{"handle": ...}`) follows a player at once, one way: the list is private (`GET /api/follows`: who the caller follows, the most recently active first and players who never played last; the cap; how many follow the caller) and the followed player only ever sees a count (`GET /api/followers`). `POST /api/follows/remove` unfollows. The cap is `Rules.follow_cap(seconds_played)`, `Rules.follow_base` (10) plus one for every `Rules.follow_seconds_each` (3600) played (see Play time); following someone already followed changes nothing. A follower may, follow by follow, show the followed player their handle and profile link (`PUT /api/follows/share-back`, off by default; `GET /api/followers` lists those who do). `POST /api/bans` (`/api/bans/remove`, `GET /api/bans`) bars a player from the banner's profile pages (the player page and team pages, for a logged-in viewer: to them there is no such page; a viewer with no login can't be told apart, so the link still works for them). A ban does nothing in a game. It overrides the banned player's follow of the banner: the follow stays on their own list (they are not told) but counts for nothing (not in the follower count, never shared back), and it takes the share-back away. The directory is `GET /api/directory?prefix=...` (login, rate-limited): the players who opted in (`PUT /api/profile/directory`) whose handle starts with the prefix (case and spacing aside, at most 20, not the caller, not players who banned the caller), each with the handle, the bio, whether the caller follows them, and a profile link only when the player switched it on (`PUT /api/profile/directory-link`, off by default). The team directory is `GET /api/team-directory?prefix=...` (login, same rate limit): teams whose name starts with the prefix (case and spacing aside, at most 20) among those their players made visible and the caller's own (`mine`), not those of players who banned the caller; each with the team's number (`id`), its name and the player's handle only if the player is in the directory. A hidden team is found nowhere. Changes are rate-limited per account (`ratelimit.SOCIAL_BY_ACCOUNT`).
- **Fight tags and retention** (`terraforma.fighttags`). When a fight ends (in `store.apply_results`, once) it is scored for each player's team that won it: **overkill** is the team's overkill damage on killing blows over its PXP, and **underdog** is the PXP of the opposing parties over the PXP of the team's own party (`fighttags.scoring`, pure; a killing blow is credited to the fighter whose turn it is, on an enemy party, and a kill outside anyone's turn is credited to nobody; PXP is as the fighters stood when the fight ended). A team *won* when one of its heroes stands and every enemy party has gone (all down or fled). A fight is PvP for a team when an enemy party holds a player's team, else PvE, and each kind has both scores, so a team holds up to four tags (`pve_overkill`, `pve_underdog`, `pvp_overkill`, `pvp_underdog`): a fight takes a tag when its score beats the holder's (and is above nothing). `Rules.thrown_fight(fight)` (nothing is thrown by default; the coliseum will judge) keeps a PvP fight from taking any PvP tag or alliance place. An alliance lists the best `Rules.alliance_top_size` (10) fights of each kind among its teams', filled as fights end (a fight stays in the list when its team leaves, until it is bumped). A team keeps fights by hand in `Rules.team_retention_slots` (10) slots, and an alliance in `Rules.alliance_retention_slots` (50), a fight a member team was in; it stays after that team leaves. Calls (login; CSRF token and a rate limit on changes): `GET /api/teams/{id}/fight-tags` (the owner: `tags`, `kept`, `slots`), `POST /api/teams/{id}/kept` and `.../kept/remove` (`{"fight_id": n}`, a finished fight the team was in), `GET /api/alliances/{id}/fight-tags` (the owners of its teams: `top` per kind, `kept`, sizes), `POST /api/alliances/{id}/kept` (`{"team_id", "fight_id"}`, a team of the caller's whose role may speak for the alliance) and `.../kept/remove`. A finished fight that no tag, list or slot holds is deleted by the housekeeping job `old_unkept_fights` `Rules.fight_keep_days` (30) days after it ended (0: kept for good), with its rounds and what belongs to it; a table that links to `fights` must be added to `fighttags.service` (a test says so). Housekeeping jobs now also take the game's `Rules` as a fourth argument.
- **Fight pages** (`terraforma.fightpages`). A signed-in player can view a fight (running or finished) that is their own (a hero of theirs is in it), has a hero of a player they follow (unless that player barred them from their profile: a ban beats a follow), was marked public, or is among the retained or top fights of an alliance one of their teams is in. `Rules.public_fight(fight)` marks a finished fight public when it is scored (nothing is by default; a coliseum or tournament game decides); a public fight is kept for good (table `public_fights`). Calls: `GET /api/teams/{id}/fights?before=&limit=` (the team's owner: finished fights newest first with `won`, `pvp`, scores, `kept` and the `tags` each holds), `GET /api/fight-pages/viewable?before=&limit=` (each with `why`: `mine`, `following`, `alliance`, `public`), `GET /api/fight-pages/{id}/replay` (the fight as it stands plus every round's events; 404 for a fight the caller can't view). A replay answer is `{fight, start, joins, rounds}`: `fight` is the fight as it stands (what `GET /api/fights/{id}` would show, without the caller's own menus), `start` the fight before round 1 (the state a page plays the rounds on, with no deadline and nobody commanding), and `joins` has, for each round that opens with a `PartyJoined` event, the fight just after that party arrived (keyed by the round's number as text), because the event only names the party. In the browser `fight-source.js`'s `replaySource` hands those to the same fight scene: the scene plays the stored rounds like a socket's, reads its view from `start` (or `joins` where a party joins) and offers no menu. Without a login, limited by address like the public profile pages: `GET /api/public/fights/showcase?kind=` (a random best fight, chosen from the world's streams and the clock, among the tags of teams whose player made them visible), `GET /api/public/fights/coliseum?before=&limit=` (every public fight) and `GET /api/public/fights/{guid}/replay` (a public fight, or a visible team's best fight). The pages name fighters and fights by their public names and never show an account.
- **The coliseum** (`terraforma.coliseum`). One team asks another to a bout and the other answers; an accepted bout is a fight at once. `POST /api/teams/{id}/coliseum/challenge` (`{"team_id": n}`: the caller's team asks team n), `POST .../coliseum/{bout_id}/accept` and `.../decline` (the caller's team that was asked) and `.../withdraw` (the team that asked), and `GET .../coliseum` (the team's bouts, newest first) are each their own route, with a login, the CSRF token and a rate limit on changes. There is no reach, party, town or PvP-zone rule (the arena is the place), but both teams need heroes, none may be in a running fight or barred by a forced disuse, and two teams of one account may not fight each other. The fight is built like a PvP fight (the challenger is party 0), stands where the challenger's first hero stands, and is public once it is recorded (`fighttags.record_fight`), whatever `Rules.public_fight` says, so the coliseum page lists it and it is kept for good. An offer waits `Rules.coliseum_offer_seconds` (a day) of wall clock; the housekeeping job `coliseum_offers` closes the late ones. A bout fight scores PvP tags and experience like any PvP fight; throws are still the game's to judge (`Rules.thrown_fight`). No stakes are built yet, and tournaments can be manual quests of kind `coliseum`.
- **Longer rounds.** A player who needs more time can choose a longer round (an accessibility setting): `GET /api/settings/round-time` (login) shows the choice, the round length it gives and what each option costs; `POST /api/settings/round-time` (login and CSRF token; the body is `{"multiplier": 1.5}`) chooses one. A game sets the choices and prices in `Rules.time_multipliers`, pairs of `(multiplier, bonus)`; DragonStar's are `1` for nothing, `1.5` for 5% and `2` for 10%, which is the default. The price is on the monsters: each gets that much more max HP (rounded up, in whole percents), so the fight is harder and pays more experience, since a monster's PXP follows its stats. A fight waits `Rules.round_length(multiplier)` for every round, with the longest multiplier anyone in it asked for (`fights.timing.fight_multiplier`), fixed when it starts; a choice counts for fights started after it. A server-started fight reads the team owner's choice; a game that starts fights with several players calls `timing.multiplier_for`, `fight_multiplier` and `toughen` the same way (a player on the monsters' side pays nothing: they are not the ones the monsters are made tougher for). The account page (`/account/`) has a **Round time** card for this: a choice among the game's options with what each costs, the round length it gives, and the hours the player has played (`GET /api/play-time`).
- **The timer.** The server looks for overdue rounds every `fight_timer_seconds` (settings, 1 by default; `live.resolve_overdue` does one pass).
- **The end.** The round that ends a fight saves its result to the heroes and pays its gold through the game's economy, once (`store.apply_results`), and the fight is finished.
- **Finding.** `GET /api/fights` (login; `?running=true` for the unfinished ones, `?limit=` 1 to 50, 20 by default) lists the caller's fights, running first then the most recent: the number (for the calls and the socket), the public name, the round it waits for, when it plays, and which of the caller's heroes are in it.
- **Looking.** `GET /api/fights/{id}` shows a fight to its players (who is standing with how much, which fighters are theirs and have committed, when the round plays, and the `vital` resource); `GET /api/fights/watch/{guid}` shows it to anyone logged in who knows its public name.
- **The socket.** `/ws/fights/{id}` (the Origin header must be the site's own, and a login) pushes `committed` (who has committed, never what), `party_joined` (a party joined: look at the fight again), then `round` (the round's events, whether the fight is over, and the next deadline). Only the fight's players may listen by its number; anyone logged in may with `?guid=`. The page only listens: commands go through the call.

## Databases

The engine is database-agnostic. Postgres is the primary database, MySQL is supported, and SQLite serves tests and development. To keep it that way:

1. Tables are SQLAlchemy models only. Until the first release they are built from the models; after it, Alembic writes the schema changes.
2. Only generic column types are used, never database-specific ones.
3. Structured data goes in JSON columns, never serialized language objects.
4. Anything that really differs between databases lives in `terraforma/db/dialect.py`, and nowhere else.
5. There is no raw SQL outside that module and the migrations (once there are any).
6. Every database test runs on all three databases.

## Map-ready from the start

Maps (see Maps) and a changing world come later. The groundwork is there from the first commit:

- **Location.** Everything that exists somewhere has a map and a tile (`Located`).
- **Randomness.** All of it comes from the world's seed, through named streams (`WorldRng`), so worlds can be rebuilt and bugs replayed.
- **Time.** The world keeps its own clock, counted in ticks rather than wall time (`advance_clock`).
- **Checked input.** Map names and coordinates from the browser are validated like any other input (`Position`).

## Housekeeping

`terraforma.housekeeping` tidies up what has gone stale. The server runs every job each `housekeeping_seconds` (settings, 3600 by default, 0 for never; `housekeeping.run(sessionmaker, settings)` does one pass). A job is an async function `(session, now, settings)` registered with `@housekeeping.job` that returns how many rows it removed; each runs in its own transaction, and a failing job is logged without stopping the others. A job deletes only what nothing reads any more, so a repeat or a second server is harmless. Today: `old_voice_rooms` closes voice rooms (see Voice). `old_chat_messages` removes chat messages older than `chat_retention_days` (see Chat). `finished_rate_limit_windows` removes rate-limit counters whose window is over (a subject that never returns would keep its row otherwise). `old_closed_ballots` and `old_settled_rating_prompts` remove closed ballots (with their votes) and answered or dismissed rating prompts older than `ballot_retention_days` and `rating_prompt_retention_days`; both default to 0, which keeps them for good, so a game opts in through `settings.toml`. A pending prompt is never removed. `stale_pending_drops` settles a pending drop (see Held drops) that has waited longer than `pending_drop_timeout_seconds` (settings, 0 by default: it waits for ever): a need/want drop with the answers so far (hold-outs count as passing), a hand-out nobody made as `unclaimed`. `quest_needs` looks for strengths of party with no quest to progress on and proposes one (see The quests the world needs); it makes rows rather than removing them. `ended_standing_statuses` removes standing statuses whose end time has passed. `expired_remembered_browsers` and `unconfirmed_security_keys` tidy second-factor leftovers (see Second factors). Games cannot add jobs yet.

## Quest instances

`terraforma.instances` lets a quest happen in a place that only some parties share (a public interface: the license exception covers it). A quest picks one of three modes: `PUBLIC` (no instance: everyone shares the map, even a dungeon), `PRIVATE` (each party gets an instance of its own and sees itself as the only one there) or `SHARED` (several parties meet in one instance; they may cooperate or compete, but only one can complete the quest).

`instances.service.enter(session, rules, party_id, quest, mode, game_map, x, y, capacity=4, join_window_seconds=300)` takes the party to the quest's map. A shared quest puts the party into an open instance of the same quest and map that still has room and whose joining time has not run out (`join_window_seconds` after the first party came); of several it picks the one whose parties' average strength (the sum of PXP, `Rules.pxp`) is nearest the party's, else it starts one. Rank is not matched yet. A party in a town, in a fight or already in an instance is refused. `leave` puts the party back where it came in, and an instance with nobody in it is gone; a party that is deleted, or merged into another, leaves too, and parties in different instances can't merge. `complete` makes the first party to call it the winner and returns the other parties still inside, so the game can send them its notice; they may stay and explore, but cannot complete the quest, and no new party joins a won instance.

Parties in different instances (or one in an instance and one out in the world) do not meet: the nearby list leaves them out and a PvP fight is refused ("that party is not here"). Two parties of the same shared instance skip the strength window: `Rules.may_fight_in_shared_instance(allowed)` (None if they may, by default wherever the place allows PvP) replaces `may_start_pvp` for them. Instance maps, their zones and the PvP flag are ordinary map content. The dialog tags to enter a quest and to turn one in come with the Vanguard quest slices.

**Dialog tags.** A dialog (an NPC, an object or an edge) runs instances itself: `enter_instance,quest,mode,map,x,y,capacity,join_seconds,label` takes the party the hero acts in to that tile of the map (on the hero's world) with the service's rules (mode `private`, `shared` or `public`; a public quest moves no one and the dialog goes on, any other leaves the dialog like `warp`), `complete_instance,label` wins the quest of the party's instance (the dialog goes on), and `leave_instance,label` brings the party back to where it came in (and leaves the dialog). Each goes to its label when it cannot: a party apart in a town, in a fight, already in an instance, with no room in the shared one, in none to complete or leave, or when another party won first. A map or tile that is not there is a mistake in the text. `instance_won,other|self,label` goes to its label unless another party (`other`) or this party (`self`) has won the quest of the party's instance, so a shared dungeon can tell the losers wherever they talk to something in it (a herald, the way out). The tags do not push anything to the other parties when one wins: a game that wants that calls `instances.service.complete` itself and uses its answer.
