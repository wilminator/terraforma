# TerraForma

The TerraForma RPG Engine runs browser RPGs. A game is a module: its content (seed data), assets and rules settings, plugged into the engine. The engine provides the rest:
- accounts and security;
- the server calls and live fights over WebSockets;
- the database layer on Postgres, MySQL or SQLite;
- a map-ready world.

[Vanguard Tavern](https://github.com/wilminator/terraforma-vanguard-tavern) is the first game built on it. [terraforma-example-game](https://github.com/wilminator/terraforma-example-game) shows how to build your own.

## Making a game

A game is a Python package that hands the engine a `Game` and builds the app:

```python
from terraforma.app import create_app
from terraforma.game import Game
from terraforma.settings import load_settings

GAME = Game(name="My Game", seed_dir=..., assets_dir=...)

def app():
    return create_app(load_settings(), GAME)
```

To serve it, run `python -m terraforma serve my_game:app`. It checks the settings, brings the database up to date, then serves.

For tests, add `pytest_plugins = ["terraforma.testing"]` to the game's `tests/conftest.py`. Override the `game` fixture there, and `app_client` serves your game on every database under test.

## The browser client

The engine serves its own browser client: plain ES modules and CSS, no build step, no bundler, no Node. The pages know nothing of any game; they draw what the server's calls send.

| URL | What it is |
|---|---|
| `/` | The marketing site: the game's name and a way in. |
| `/play/` | The game client. Landscape only: held upright it shows "turn your device sideways". A logged-out player is sent to `/account/?next=play` (the one login, which works in any orientation) and back here once logged in; only `next=play` is understood, never an address. Then the stage (a fixed design resolution, 480 by 270, shown at the largest whole-number scale that fits), which shows the map of the party the Party panel has chosen (before a team plays: "Choose a team in Party and press Play"). **Once a player is in the game, `/play/` is the whole experience**: the map, the fight (a later slice) and every panel are drawn on this one page, and nothing loads another with the menu in the bar below it: **Teams** (the player's teams and a form that makes one by its name; each opens its own page), **Party** (a team plays as a party; in a town it says when it is ready to leave, comes back or leaves the party) and **Nearby** (what a hero can reach for an action, nearest first; an NPC in the talk list has a Talk button) and **Talk** (the conversation a hero is in: what is said, Next, the answers to pick, the shop and the inn). and **Pack** (a hero's gold and items, the forms that give gold or part of a stack of items to another hero, and the ledger of what the hero gave and received: `GET /api/heroes/{id}/inventory`, `GET .../trades`, `POST .../give-gold` and `.../give-item`; the player's other heroes are offered, or a hero's number, and who may be given to is the game's trade policy, so a refusal is shown in the server's own words; the hero is the one Nearby acts with). A panel opens over the stage's right side, so the stage keeps its size. |
| `/team/{id}` | A team's own page, for any screen and orientation, private to its player: its name (rename, delete), its heroes (rename, replace, remove, and move or exchange where the game allows it) and the form that adds a hero to an empty place. A player who is not logged in is sent to the login; a team that is not theirs is "no team with that address". |
| `/profile/` | The player's own page settings, for any screen and orientation: make the public page (and give it a new address), write the bio, list the handle in the directory or not, and show or hide each team (a shown team has its own page and address). A logged-out player is sent to `/account/?next=profile` and back; only `next=play` and `next=profile` are understood. |
| `/alliances/`, `/alliance/{id}` | The player's alliances, for any screen and orientation: the alliances their teams are in, the invitations waiting (accept or decline), and founding one; then one alliance as one of the player's teams sees it (`?team=` picks the team, and a switch appears when two of the player's teams are in it): the roster (a team links to its page only while visible, and shows its player's handle only if the player is in the directory), invite by team number and withdraw, roles, hand over, remove, leave and disband (each asks twice), the alliance's page and bio, ballots (open, vote, close) and how the alliance sees other teams. The controls shown follow what the server says the role may do (`can`); the server still decides each call. A logged-out player is sent to `/account/?next=alliances` (`next` understands `play`, `profile` and `alliances`). |
| `/p/{token}`, `/p/team/{token}`, `/p/alliance/{token}` | The public pages, no login, any screen: a player's page (handle, bio, shown teams), a shown team's page (its alliances and, if its player is in the directory, the handle) and an alliance's page (bio and teams by role). The address is a random token; a wrong or renewed one says "No such page". |
| `/account/` | The account pages, for any screen and orientation: log in (with a password or an external provider), create an account, ask for a password reset, and once logged in the handle, the email address, the ways to sign in and two-factor login. |
| `/confirm-email`, `/change-email`, `/reset-password`, `/confirm-2fa` | The pages the links in the engine's emails open. Each takes the token from the address (and removes it from the address bar) and waits for a button, so a mail scanner opening the link changes nothing. The account pages' words are all in `strings.js`, so a game changes them with `shell.text.set`. |
| `/client/...` | The engine's own code and styles (`src/terraforma/client/static/lib`). |
| `/game/...` | The game's `client_dir`. |
| `/assets/...` | The game's `assets_dir`. |
| `GET /api/client` | What a page needs to start: the game's name, the URLs of its modules and styles, and its assets folder. |
| `GET /api/jobs` | The jobs a new hero can take (login), each with its `key`, `name` and the `stats` a hero of it starts with; the Teams panel's job list. |
| `GET /api/team-rules` | What the game says about teams (login): `team_min` and `team_max` heroes in one (never above 5) and `max_teams` for a player. |
| `GET /api/session` | Who is logged in (or `account: null`, still a 200) and the CSRF token to send back; a page that reloads has lost the token it got at login. |

**Pages run only files of the engine's and the game's own**: every page answers with a Content-Security-Policy that allows nothing inline and nothing from another site, so a game's code goes in files, not in the page.

**Browser code in a game.** A game adds its own browser code with three fields of `Game` (a public interface, covered by the license exception):

```python
Game(name="My Game", client_dir=HERE / "client", client_modules=("my_game.js",), client_styles=("my_game.css",))
```

Every page, once it knows the manifest, adds the stylesheets and then imports each module in order and calls its default export with the **shell**:

```js
export default function register(shell) {
  shell.text.set({ "login.title": "Enter the tavern" });     // any of the engine's words (strings.js)
  shell.on("login", ({ username }) => { /* ... */ });
}
```

| The shell has | |
|---|---|
| `shell.page` | `"site"`, `"account"` or `"play"`. |
| `shell.game` | The manifest: `engine`, `game`, `modules`, `styles`, `assets`. |
| `shell.assetUrl(name)` | The URL of one of the game's assets. |
| `shell.text.get(key, values)` and `shell.text.set({key: text})` | The page's words; `{name}` in a text is filled in. An element with `data-text="key"` shows the key's text. |
| `shell.api` | `get`, `post`, `call` and `ApiError`: the server's calls, with the CSRF token added to the ones that change something. |
| `shell.account` | `null`, or `{username, handle}` once logged in. |
| `shell.art.load(reference)` | A picture from the game's assets: a file name or a sheet reference (see Art). Resolves to `{source, frame, grid, frames, palette, animations}`. |
| `shell.on(event, handler)` | Events `ready` (every module registered, nothing drawn yet), `login` and `logout`, and on the play page `game` (the panels are drawn; the detail is `{roster}`). Returns a function that stops listening. |
| `shell.panels.add(id, build)` | Adds a panel to the play page's menu after the engine's (Teams, Party, Nearby, Talk, Pack, Chat). `build(shell, roster)` runs once the player is logged in and returns an element, or `{element, show}` where `show()` runs each time the panel is opened. The menu button says `shell.text.get("panel.<id>")`. `roster` is the player's heroes, teams, jobs and the game's team rules (`heroes`, `teams`, `jobs`, `rules`, `heroId`, `teamId`, `onChange(listener)`, and the calls that change them). |
| `shell.actions` | The actions the Nearby panel can ask for: `talk`, `invite`, `open`, `search`, `fight`, `help`. A game pushes the names of the ones it adds (the words are `action.<name>`). |
| `shell.activities.add(command, build)` | What the Talk panel shows when an NPC's dialog reaches an *activity* (a tag the engine leaves to the browser): the engine adds the shop for `vend`, `hawk` and `shop`, and a game adds a screen for a tag its `Npcs.tag` doesn't handle. `build({shell, roster, heroId, prompt, finish, problem})` returns the element; `prompt` has the `command` and its `parts`; the conversation goes on only when the screen calls `finish()` (as Next does), and `problem` is an element to show a refusal in. A tag with no screen shows a note and a Next. |
| `shell.conversation` | The conversation the hero is in: `lines` said so far, the `prompt`, who `speaker` is, and `talk(heroId, npcId)`, `next(choice)`, `leave()` and `close()`. The server runs the dialog; the browser only shows it. |

A module that fails to load is reported in the console and on the page, and skipped; the rest still run. A game changes the look with a stylesheet, usually by setting the custom properties at the top of `engine.css`. Each later client slice adds its own hooks here (map objects).

The client's files are checked when the app is made: a module or style that isn't in `client_dir`, a name with a path out of it, or a folder that doesn't exist stops the server at start.

The map scene (`map-scene.js`) draws the party's map on the stage's canvas at the design resolution, 32-pixel tiles with the view centered on the party (held inside the map, or following it where the map wraps; a map smaller than the view sits in the middle), the pictures from the tileset's `art` (a file or a sheet reference, through `shell.art`; a tile with no picture is a flat color) and a marker for each object (S for a sign, D for a door, C for a chest). A tap or click on a tile, or the arrow keys or WASD, proposes a route (`POST /api/parties/{id}/route`: the server fills in the gaps or says why not, shown in the stage's note) and the party then walks it one tile at a time, checking in with the server at each (`.../route/step`); if the server does not confirm a tile, the party is put back where it really is. A walk stops at a fight (the fight scene takes the stage, see below), at a town (the Party panel opens to leave it) and at an event at an edge of the map (its dialog opens in the Talk panel). A tap on a chest, door or sign uses it (`POST /api/heroes/{id}/objects/{id}/use`, which the server refuses out of reach): a script that asks something opens the Talk panel, and one that only says something is shown in the note. A warp (stairs, a door) moves the party to another map and the stage loads it. The stage's `data-map`, `data-party-x`, `data-party-y` and `data-walking` attributes say what it shows. `GET /api/teams` says which party (`party`) each team is in, which is how the stage finds its party again after a reload.

The fight scene (`fight-scene.js`) is the other scene of the same stage: when a walk or the Party panel's Leave Town starts a fight, the shell is told (`shell.emit("fight", { fight })`), the map is suspended, any open panel is closed and a layer over the stage (still the 480 by 270 design resolution, scaled with it) draws the fight, so the page is never left. The scene is built from `GET /api/fights/{id}` (the `vital` it names is the resource whose loss is damage) and kept up to date by the fight socket (`fight-link.js`, `/ws/fights/{id}`: it retries a few times if the socket drops and the scene asks the server how the fight stands once it is back). Each `round` message holds the events of a round; they are played one at a time through the fight model (`fight-model.js`, which follows the events exactly as the server's replay does, so the gauges end where the server has them): what is said goes to the log under the stage, the gauges move, and the fighters move with the Web Animations API (the scene waits for each animation to finish), at a reading pace the player can speed up (1, 2, 4 times) or skip, and with no movement for a player whose system asks for less motion. Heroes of party 0 and the player's own are drawn on the left, the rest on the right, as a name and a gauge each (the pictures come with the art slices). When the fight is over the player leaves it with a button and the map comes back; a page that opens in the middle of a fight (`GET /api/fights?running=true`) goes straight back to it. The stage's `data-scene` (`map` or `fight`), `data-fight`, `data-link`, `data-round`, `data-playing`, `data-over`, `data-speed` and `data-shown` say what it shows. The command menu (`fight-menu.js`) is how the player commands their heroes on that screen: the fight view (`GET /api/fights/{id}`) gives each of the caller's own fighters a `menu` (the weapons it can attack with, its skills and spells with their cost and whether it can pay it, its items that do something when used, whether it may flee, and for each whom it is aimed at: `enemy`, `ally`, `downed` or `none` when the ability names its own targets), and the page only offers those choices. The player commands each hero in turn (Attack, Skill, Spell, Item, Defend, Flee), picks a target by its card where one is needed (the cards that can be aimed at light up, take Enter or Space, and Escape or Back steps out), may pick another of their heroes by its card to choose again before the round plays, and the command goes through `POST /api/fights/{id}/commands`. The menu hides while a round is played and when the fight is over, and asks the server again after each round (items and MP change). The stage's `data-menu` (`commands`, `list`, `target`, `waiting` or `off`) and `data-hero` say what it shows. The log names a hero's skills, spells and items by their names (the menu lists them), and a fighter that defends is told by a `Defend` event with its address at the start of the round (it takes no turn), so the log, or a game's own client code, can show it (`fight.defend`). Not in the menu yet: changing gear in a fight (the `equip` and `equip_weapon` commands). `shell.panels.close()` closes the open panel.

**Old tilesets.** `python -m terraforma.tools.qbtiles MAP.MAP out/tiles --preview out/look.png` turns a QBasic tile file (what a `PUT` of an array of 32 by 32 pictures in SCREEN 13 writes, with the `PALETTE r + g * 6 + b * 36` colors) into a tilesheet: `out/tiles.png`, `out/tiles.sheet.json` and, if some pixel has no color in the palette, `out/tiles.alpha.png`. The two 16-bit numbers the game kept with each tile are written to the sheet's JSON (`tag` and `mark`). `--preview` writes an enlarged picture to look at, and `--missing "#ff00ff"` draws pixels with no color instead of leaving them clear. Standard library only.

**Making sheets.** `python -m terraforma.tools.tilesheet knight.png out/knight --frame 32x32 --scale 2 --colors 32` turns a picture, or a GIF (`walk.gif`), into the tilesheet format of Art below: `out/knight.png` (indexed), `out/knight.alpha.png` (the 8-bit transparency, written only when some pixel is not opaque) and `out/knight.sheet.json`. A still picture is cut into frames of `--frame` (the whole picture is one frame if left out; `--frames N` keeps only the first N cells), left to right and then down; a GIF gives one frame for each of its frames, and the tool also writes its timing as `out/walk.anim.json` (an animation named `base`, or what `--animation` says; `--no-animation` writes none; the most common frame time is the animation's `ms`, a frame with another says its own, and the animation loops if the GIF does). `--scale` resizes each frame (above 1 by whole pixels), `--colors` is the most the palette may hold (2 to 256; a picture with fewer keeps its colors exactly, and the palette is made from the pixels that can be seen, so a color under a clear pixel costs none), `--columns` sets how many frames lie across the sheet, and `--combined` writes one RGBA picture instead of the color and alpha sheets. It needs Pillow, which only the tool uses: `pip install "terraforma[tools]"`.

**Making color maps.** `python -m terraforma.tools.colormap` makes and checks the recolors of Art below (`name.colors.json`), with these commands (a sheet or map is written without its extension):

- `colors out/knight` lists the sheet's palette.
- `make out/knight out/red_team --hue 150` writes a map that turns the palette colors 150 degrees round the color wheel; `--saturation` and `--lightness` multiply those, `--only "#3050a0,#7090e0"` and `--skip` choose which colors the three touch, and `--swap "#102040=#403010"` (repeat for more) sets a color outright and wins over the shifts. The map lists only the colors that change; a map that would change nothing is refused.
- `check out/red_team.colors.json --sheet out/knight` checks the format and, with `--sheet`, that every color the map changes is in the sheet's palette (a color the palette lacks never matches, so such an entry does nothing). The server runs the format check on every `*.colors.json` in the game's assets folder when it starts, and refuses to start on a bad one.
- `merge out/red_team out/dark out/dark_red --sheet out/knight` writes one map that does the first and then the second.
- `preview out/knight out/red_team out/look.png --scale 4` draws the sheet recolored the way the browser does (pixels snapped to the palette, then swapped), to look at before it goes in a game.

Only `preview` needs Pillow; the rest is standard library.

**The example game** (`terraforma.example`) is the smallest game that uses all of this: a seed with a small map drawn with a 13-picture tileset (`tiles.png`, made by Mike and converted from QBasic), a cellar, a marsh in the hub where a slime fights the party (the swamp tiles meet monsters), two jobs (Fighter and Scout), two items and three people to talk to next to where heroes start (Old Tom gives gold, Hana sells herbs and potions, Bede keeps the inn), a signpost and stairs down to a cellar map (its town is the gate tile where heroes start: a party that steps onto it waits there, and the rest of the meadow is open ground to walk), and a browser module and stylesheet that use the hooks above. `python -m terraforma serve` runs it, and it is the game the browser tests play. A game of your own can start from it. Its pictures are drawn for this repository; every asset's source and license are recorded beside it (`assets/ASSETS.md`).

## Running it

Everything runs in Docker.

```sh
cp settings.example.toml settings.toml      # then set session_secret
mkdir -m 700 keys
docker compose run --rm app python -m terraforma keys new   # the encryption key (once)
docker compose up app                       # the engine alone, http://localhost:8000 (Postgres)
docker compose run --rm test                # every test, on SQLite, Postgres and MySQL
docker compose run --rm test -m e2e         # only the browser tests (Chromium plays the example game)
```

The browser tests (`tests/e2e`) serve the example game on a real port and play it in Chromium with Playwright: a test fails on any console error or warning, uncaught error or failed request. In CI they run on SQLite for every pull request; the label `browser-all-databases` on a pull request runs them on Postgres and MySQL too. Outside Docker, `pip install -e ".[dev]"` and `playwright install chromium` set them up.

Settings come from `settings.toml`, not environment variables. The NAS the game runs on may not pass environment variables or Docker secrets into the container. `python -m terraforma check-settings` says what's wrong with the file, if anything.

On start, the container checks the settings, brings the database up to date (`python -m terraforma serve`), then serves. `GET /api/health` answers the container's health check.

## Signing in with an external provider

A game can let players sign in with any OpenID Connect provider (Google, Microsoft and others) instead of, or as well as, a password. Each provider is a `[[external_providers]]` section in `settings.toml` (see `settings.example.toml`): `name` (lowercase letters, digits, `_`, `-`), `label` (the button's words), `issuer`, `client_id`, `client_secret`, and optionally `scopes` (must include `openid` and `email`) and `authorization_endpoint` with `token_endpoint` (both or neither; by default they are read from `<issuer>/.well-known/openid-configuration`). Addresses must be https (http only for localhost). Register `<public_url>/api/external/<name>/callback` as the redirect address at the provider. Microsoft's shared issuer, `https://login.microsoftonline.com/common/v2.0`, is accepted: its `{tenantid}` is read from each token. With no providers listed nothing changes and no button appears.

The flow is the authorization code flow with PKCE, a `state` and a `nonce`, all kept in the signed session cookie and used once. The server trades the code for the ID token itself, over TLS, and checks the issuer, the audience, the expiry and the nonce; it does not read a signature, which OpenID Connect allows for a token received straight from the token endpoint. Calls: `GET /api/external/providers` (names and labels), `GET /api/external/<name>/start?next=play|profile`, `GET /api/external/<name>/callback` (always ends in a redirect to `/account/?external=<outcome>`, where `<outcome>` is `done`, `twofa`, `finish`, `linked` or `error` with a `reason`), `GET /api/external/pending`, `POST /api/external/finish`, `POST /api/external/2fa`, `GET /api/external/identities`, `POST /api/external/<name>/link`, `POST /api/external/unlink` and `POST /api/external/password`. Every call that changes an account needs the login and the CSRF token, as the other account calls do.

The rules: every login has a local account. A first sign-in uses the provider's email only when the provider calls it verified; the player then chooses a username and a handle (the handle cannot match the username or the email), and may set a password; the account is made at that step, so abandoning it leaves nothing behind. An email that already has an account never creates or links anything, and the answer does not say how that account signs in. Linking is an explicit action from the account page, needs a current two-factor code when two-factor login is on, and refuses a provider account another player has. Unlinking needs a current two-factor code when it is on and never removes the last way in: a player whose only way in is a provider sets a password first. Two-factor login applies to every way in, a provider sign-in included. A game that wants to hide the buttons leaves the providers out of `settings.toml`.

## Second factors

Two-factor login is on while at least one method counts: an **authenticator app** (TOTP, RFC 6238) or a **security key or passkey** (WebAuthn, FIDO2, through the `webauthn` library). **Recovery codes** (ten, kept only as hashes, each good once) come with the first method and go with the last; they stand in for any method. There is no SMS and no email code, and no way back in by email: a player who loses every method and the recovery codes is reset by an admin.

Calls (all under `/api/2fa`; the ones that change something need the login and the CSRF token): `GET` (state: whether it is on, the app, the keys, the recovery codes left), `POST /challenge` (the options for a key's answer, and which methods count), `POST /setup` and `POST /enable` (the app), `POST /webauthn/options` and `POST /webauthn/register` (a key), `POST /webauthn/remove` and `POST /remove-app` (one method, while another stays), `POST /disable` (all of them), `POST /recovery-codes`, `POST /confirm` (the emailed link), `GET /browsers` and `POST /browsers/forget` (remembered browsers). `POST /api/admin/2fa-reset` is the admin's reset (below).

The rules: every change to two-factor login is confirmed by an emailed link, which works once for an hour, and a newer request replaces the one waiting. Once a method is on, every change needs a live second factor first (an app code, a recovery code or a key's answer) and the call that needs one takes it as `code` or `assertion` (what `navigator.credentials.get` returned, as JSON text), never both: logging in, changing the email address, linking and unlinking a provider, setting a first password and every call above. A key's challenge is made on request (the 202 answer of `/api/login`, `GET /api/external/2fa` and `POST /api/2fa/challenge` carry the options), kept in the signed session cookie and used once, right or wrong. A registered key counts only after its link is followed; a counter that does not go up is refused as a cloned key (0, which passkeys report, is accepted). The relying party is the host of `public_url` and the one origin is `public_url` itself, so `public_url` must be the address players really use, and a browser refuses a key on a bare IP address. No attestation is requested. Every try, by any method, counts against the account's `2fa-code` rate limit.

**Remembered browsers.** A player who proved a second factor may tick "remember this browser" (`remember: true` on the login), which skips it for `SignIn.remember_browser_days` days (30 by default, 0 for never) on that browser, provider sign-ins included. The browser holds a random secret in an `HttpOnly` cookie of its own for each account; the database keeps its hash. A remembered browser stops counting when its time is up, when the account's session version moves on (a password reset or an email change), and whenever two-factor login changes (a method added or removed, new recovery codes, turned off). The player sees their browsers on the account page and can forget one or all. At most ten are kept per account.

**What a game decides**, with `Game(sign_in=...)` (a public interface): subclass `terraforma.accounts.hooks.SignIn` and set `remember_browser_days`, and/or override `single_method_note(account, methods)`, the note shown after login to a player whose second factor is a single method (`methods` is `"app"` and/or `"key"`); the default says to add a second one, and returning None says nothing. The answer of a good login carries it as `note`.

**The admin's reset.** An account with `is_admin` set (by the game's own setup, see Challenge Tokens) calls `POST /api/admin/2fa-reset` with a `username`: that player's methods and recovery codes are removed, every login and remembered browser of theirs ends, and they are told by email. They log in with their password and set it up again. It is rate-limited and logged (the log names account ids, never secrets).

Housekeeping removes expired remembered browsers and keys whose link was never followed (a day).

## Encryption keys

Secrets the engine must read back, such as 2FA secrets, are stored encrypted with a key kept in files beside `settings.toml` (the `key_dir` setting), never in the database. There are two slots: `current.key` encrypts, and `previous.key` still decrypts what the last key made, so a rotation never locks anyone out.

```sh
python -m terraforma keys new       # the first key; refuses to replace one
python -m terraforma keys rotate    # a new key, and everything stored is re-encrypted with it
```

The server won't start without a current key. Back the keys up apart from the database: a database backup is unreadable without them, and both together give everything away. A column that holds encrypted values is registered with `terraforma.keys.encrypted_column`, so rotating finds it.

## Changing the tables

Change the models, then make a migration and read it over, since autogenerate misses renames:

```sh
alembic revision --autogenerate -m "what changed"
```

A test fails whenever the models and the migrations disagree.

Migrations are numbered `0001`, `0002`, ... in the file name and the revision id, and each points (`down_revision`) at the one with the number before. Take the next free number when you cut your branch. When another branch merges first, re-point yours at the new head and rename it: a test fails on a repeated or missing number, a second head, or a revision that doesn't follow the one before it.

## Seed data

A game's starting content is JSON in its `seed/` folder (`Game(seed_dir=...)`): one file per kind of content, each a list of objects. These formats are a public interface, so changing one is deliberate and noted here.

| File | A row has |
|---|---|
| `abilities.json` | `key`, `name`, `kind` (`spell` or `skill`), `mp_cost`, `description`, `icon`, `effect`, `presentation` |
| `items.json` | `key`, `name`, `price`, `one_use`, `description`, `icon`, `use_effect`, `equip_slots`, `stat_bonus`, `stat_percent`, `attack`, `use_presentation`, `fight_presentation` |
| `jobs.json` | `key`, `name`, `xp_needed`, `stat_growth` (stats per level), `abilities` (each `{"ability": key, "level": n}`, the level a hero gets it at; a bare key means level 1) |
| `personalities.json` | `key`, `name`, an animation for each of `base equip flee hit die attack_close attack_throw attack_shoot skill spell item`, and `overworld` (`stand` and `move`, each facing `up down left right`) |
| `monsters.json` | `key`, `name`, `personality` (key), `xp_reward`, `gold_reward`, `stats`, `abilities`, `items`, `equipment` (keys), `drops` (drop table keys), `ai` |
| `drop_tables.json` | `key`, `name`, `weighted`, `rolls`, `entries` (see Item drops below) |
| `statuses.json` | `key`, `name`, `kind` (`good` or `bad`), `description`, `icon`, `duration`, `intensity`, `ticks`, `modifiers`, `xp_share` (see Statuses below) |
| `maps.json` | `key`, `name`, `wrap_x`, `wrap_y`, `safe_steps`, `tileset`, `tiles`, `zones`, `zone_tiles`, `objects`, `edges` (see Maps below) |
| `npcs.json` | `key`, `name`, `map` (a key in `maps.json`, or the default `hub`), `x`, `y`, `dialog` (the dialog language, checked when the seed loads: see NPCs and dialog), `counter` (tiles, `[[x, y], ...]`). The NPC with a key is placed, or moved and rewritten if it exists, each time the content loads; one the file no longer lists stays where it is. |

- **Keys.** Every row has a `key` (1-64 lowercase letters, digits, `_` or `-`) that the game picks and never reuses. Rows name each other by key. Only `key` and `name` are required; the rest have defaults.
- **Equipment slots.** An item's `equip_slots` lists the slots it takes. The engine's slots are `rhand rammo rarm lhand lammo larm body head back feet`; `hand`, `ammo` and `arm` are *sided* (the player picks left or right when equipping), and a two-handed weapon lists `lhand` and `rhand`. A weapon's `attack.ammo_type` has to match its ammunition's. Gear never stacks; ammunition and non-equipment stack to 250, in at most 12 stacks (for now these limits are constants in `heroes/inventory.py`).
- **Stats** are the game's `Rules.stats` (see Fight rules below), by default `HP MP Speed Accuracy Strength Dodge Block Power Resistance Focus`; a stat left out is 0, and any other name is refused.
- **An effect** is `{"effect", "targets", "base", "added", "attribute", "status", "duration"}`: `effect` is one of `none heal hurt revive slay cause_good_status remove_good_status cause_bad_status remove_bad_status restore_mp eject`, `targets` is `individual`, `group`, `party`, `all_parties` (every party, the actor's own included), `all_allies`, `all_enemies`, `all_not_allies` (enemies and neutrals), `all_not_enemies` (allies and neutrals), `random_party` (one whole party, drawn from the fight's own random stream so the fight replays, from the parties `Rules.random_party_pool` names: by default every party with someone alive, the actor's own included; a game narrows it), or a number *n* (the target and *n* neighbours each way along its group, hit less the further they are), and `attribute` is the game's own kind of damage. `slay`'s `base` is its chance out of 100. `eject`'s `base` is its chance out of 100 too (see Fleeing); `friendly: true` (for `eject` only) lets it be aimed at the user's own side. `cause_good_status` and `cause_bad_status` need a `status` (a key in `statuses.json` of the matching kind) and may set `duration` (rounds) over the status's own; `remove_good_status` and `remove_bad_status` take off the one `status` names, or every status of their kind if it is left out.
- **An animation** is `{"animation", "images", "sounds", "times"}`; pictures and sounds are plain file names under the game's assets folder (no absolute paths, no `..`).
- **Checking.** Anything unknown, mistyped or out of range is refused with the file, row and field named, and so is a repeated key or a reference to a key that doesn't exist. All problems are listed at once, and the server won't start on a bad seed.
- **Loading.** On every start the engine makes the database match the seed: new keys are added and known keys updated in place. A key the seed no longer lists is kept but marked inactive, never deleted, because heroes and fight history may still point at it. A file the seed doesn't have leaves its table alone.

`terraforma.seed.load_seed` reads the files; `terraforma.content.schema.check_seed` checks them; `terraforma.content.loader.load_content` loads them.

## Statuses

A status is something a fighter can be under, and `statuses.json` is where a game defines them. A fighter under one carries a *token* that records the status, **who placed it** (the *source*), how many rounds have gone by and how long it lasts. A stat is changed by a status and by nothing else (there is no effect that pushes a stat directly). A status lists *ticks* and *modifiers*:
   - A **tick** is `{"when", "action", "every", "amount", "percent", "resource", "attribute", "chance"}`. `when` is `round_start`, `round_end`, `turn_start`, `turn_end` (the start or end of the bearer's own turn), `helped`, `harmed` or `saving_throw` (the bearer makes one). `every` (the four timed moments only) makes it fire on every *n*-th one. `action` is `damage` or `heal` (`amount` plus `percent` of the maximum of `resource`, life if left out; damage of a given `attribute`), `skip_turn` (only at `turn_start`; the turn is lost on a roll up to `chance` out of 100) or `end` (the token goes). Ticks that `damage` or `heal` don't start further `helped` or `harmed` ticks.
   - A **modifier** is `{"kind": "damage_taken" | "damage_dealt", "attribute", "factor"}` (damage of that attribute, or `all`, is multiplied by `factor`) or `{"kind": "stat", "stat", "amount"}` (the stat is raised or lowered while the token lasts). A stat that is not a resource has no current value of its own: it is its base, the worn gear and the bearer's tokens added up, and `Rules.stat_value(stat, geared, bonus)` sums and clamps them (never below zero, by default). Only the resources (HP and MP) keep a current value.
   - `duration` is in rounds (none: until something removes it) and `intensity` is `{"shape": "flat" | "rising" | "falling", "high", "low"}`, how strong the token is over its life: `flat` is always `high`; `falling` starts at `high` and reaches `low` on the last round; `rising` the other way. Everything a token does is scaled by its intensity (a modifier's factor eases towards 1). A status with no duration is flat.
   - A status placed again by the *same* source refreshes that source's token; a different source's token is its own.

**Who earns from a status.** A token's source is the actor behind everything the token does. Damage and healing from its ticks go through the usual path with the source as the actor, so `Rules.gauge_moved` sees the source earning it, at the intensity the token had. A tick that moves no gauge (a lost turn, say) is reported to `Rules.status_acted(fight, source, target, status, intensity, ratio)`, where `ratio` is the status's `xp_share` times the intensity: the share of the bearer's PXP (its potential experience, DragonStar's measure of what a character is worth) that the source is credited. By default the bearer owes the source that share of its PXP as an `XpDebt` (harm for a bad status, help for a good one), paid out with the rest of the experience when the fight ends.

Events: `StatusApplied`, `StatusTick`, `StatusRemoved` (with the reason: `expired`, `removed`, `ended` or `died`), `TurnSkipped` and `RoundEnd` (a round has gone by for the tokens; logged only when some fighter carries one). `fights.replay.apply_events` follows them, so tokens survive replays and spectators see them. A fight starts with the statuses it knows (`build_fight(layout, statuses)`; `fights.content.status_spec` makes one from a content row), and its snapshot carries them with every fighter's tokens.

## Standing statuses

A fight's tokens last rounds and go when the fight does. A *standing status* is a long-term one that lives between fights: a dialog places it with `add_status,target,status,seconds,locked|removable,label` on the talking hero, their team or their party (`hero`, `team`, `party`; a hero with no team or party takes the label branch). The dialog gives a number of seconds and the engine turns it into a wall-clock end time (`terraforma.wallclock`); 0 seconds lasts until removed, and placing the same status again renews it. `has_status,target,status,has|lacks,label` tests for one. A status that has ended is gone at once for every read, and the `ended_standing_statuses` housekeeping job deletes the rows. `GET /api/heroes/{id}/statuses` lists what a hero is under (its own, its team's and its party's, with the seconds left).

When a fight starts, each hero's live standing statuses go on its fighter as ordinary tokens (its own source, no round limit, for the whole fight), so ticks and modifiers work as for any token. A `locked` status is *unremovable*: `remove_good_status` and `remove_bad_status` skip its token. Deleting a hero, a team or a party deletes its statuses. A *guest pass* is a team's standing status with an end time that also sends the team out of its party when it ends (`standing.place(..., ends_party=True)`; the guild gives one, see below): the housekeeping sweep takes the team out of the party and its town visit, tries again on the next pass if a hero of it is in a running fight, and a team that leaves early takes the pass with it.

## Teams and their heroes

A hero never exists without a team. A team is made first, by its name, in the game client's Teams panel (`POST /api/teams`: `name`, and optionally `heroes`, each a `name` and a `job`); the player is taken to the team's own page (`/team/{id}`), where its heroes are made. A player has at most `Rules.max_teams` teams, and a team at most `Rules.team_max` heroes (the engine's screens draw at most 5, whatever `team_max` says). A team with fewer than `Rules.team_min` heroes is incomplete: it says so, and cannot play until its empty places are filled. The engine's defaults are 1, 4 and 8; the example game sets 3 teams. The calls under a team: `POST /api/teams/{id}/heroes` makes a hero in its first empty place while it has room, `.../heroes/{hero_id}/delete` removes one, `.../heroes/{hero_id}/replace` removes one and makes another in the same place, `POST /api/heroes/{id}/move` (`team_id`) moves one to another of the player's teams and `POST /api/heroes/swap` (`hero_id`, `with_hero_id`) exchanges two. Deleting a team (`POST /api/teams/{id}/delete`) deletes its heroes.

What may change once a team is saved is the game's to decide, with `Game(roster=...)` (a public interface): subclass `terraforma.heroes.hooks.Roster` and override `may_remove` (removing or replacing a hero), `may_move` (a move, and each hero of an exchange) and `may_disband` (deleting a team). Each returns None to allow the change, or why not (shown to the player as it is). The defaults refuse removing, replacing and moving, and allow disbanding. A game that sells a change (Vanguard Tavern: a Challenge Token purchase) charges in the rule, which runs in the call's transaction, so a change that fails afterwards is not charged; a game can instead call the engine's functions (`terraforma.heroes.service.replace_hero`, `move_hero`, `swap_heroes`, `remove_hero`) from an item's use effect. A game that wants them as ordinary play returns None, as the example game does for removing and replacing.

Where a new team starts is the game's too, with `Game(start=...)` (a public interface): subclass `terraforma.heroes.hooks.Start` and override `places(session, account)` to return `StartPlace(key, title, map, x, y)` entries (the capitals, say), where `map` is the map's name in the engine's world. By default none are offered and every new hero starts on the hub. `GET /api/start-places` lists the choices for the browser; `start` (a key) in the body of `POST /api/teams` picks one (the first place offered if none is sent; an unknown key, or any key when the game offers none, is refused with 422), and the same field on `POST /api/teams/{id}/heroes` places the first hero of a team that has none yet. A hero added to a team that has heroes stands where the team does, and a replacement stands where the hero it replaces did.

## Parties

A party is a collection of *whole teams* (`terraforma.parties.service`). A team joins whole and leaves whole, never split; a team is in at most one party; the smallest party is one team; and parties merge (all of the second party's teams join the first, in their order, only if they fit together). Teams from different accounts can share a party. A party stands on a map like everything else (where its first team's first hero stands; the hub for an empty team).

A party has a **leader**, a player (account), not a team: the player who founded it (`Party.leader_account_id`), then whoever accepts another party into theirs. `join_party` and `merge_parties` take `accepted_by`, the account of the accepting player, who must have a team in the receiving party; without it the leader stays. When the leader's last team leaves, the owner of the party's first team leads (`parties.service.leader_account` settles it), and a team in no party is led by its owner. A leader hands out the party's `assign` drops (see Held drops), opens or closes the party to asks and answers them at the guild (see The adventurers guild), and may treat the party at an inn when the game allows it (see Inns); a game can use `is_leader` for more.

How many heroes a party holds is the game's rule: `Rules.party_size`, 20 by default, and `Rules.group_size`, 5 by default, the size of the groups a fight's side is laid out in (four groups of five). A team joins only if there is a place for every one of its heroes, and a hero added to a team that is in a party needs a place too (the add-hero call follows the game's `party_size`). Deleting a team takes it out of its party, and an empty party goes with its last team.

Joining and merging are service functions, not server calls of their own: they take ids, and whoever calls them decides who may. The calls that reach them are a team's `play` (below) and the guild's (see The adventurers guild); the map will add its own interactions. A party becomes one side of a fight with `fights.build.party_side(session, party_id, rules)`: its heroes team by team, in the order the teams joined, in groups of `group_size` (`build_fight({0: await party_side(...), 1: ...})`).

A team enters the game when its player selects it to play: `POST /api/teams/{id}/play` (login and CSRF token; safe to repeat; refused with 409 for a team with no heroes) makes its party, a party of just that team, where its first hero stands. After that a team is never in no party; teams meet by joining and merging parties on the map. In a town the real party and its formation are kept, and each group of teams there acts as an *ethereal* party: `towns.service.acting_party(session, team_id)` says which party a team acts in right now (the whole real party, or in a town only the team's group, `ethereal=True`, never stored and gone when the real party is put back together).

## Art

A picture in a seed file (a tile's `art`) is a file name under the game's assets folder, drawn as one image, or a sheet reference `{"sheet": "knight", "frame": 3, "colors": "red_team", "animations": "knight"}` (a public format: the license exception covers it). Names are written without the extension, `frame` is which picture of the sheet (0, the first, if left out; then left to right and down: a tile kind of a map picks its own, so one sheet can be a whole tileset), and `colors` and `animations` are optional:

- `knight.png` is the indexed-color sheet, `knight.alpha.png` its transparency (an 8-bit gray image of the same size) and `knight.sheet.json` describes it: `frame` (`[w, h]`), `grid` (`[columns, rows]`), `frames`, `palette` (hex colors) and `alpha` (`false` for a sheet with no alpha file). The browser combines the two images on a canvas when it loads the sheet.
- `red_team.colors.json` is a color map, `{"#3050a0": "#a03030"}`. Each pixel is snapped to the nearest palette color, then swapped if the map lists it; colors the map leaves out stay. Colors are `#rrggbb` (the `#` may be left out, capitals are fine, and a color listed twice is an error). `python -m terraforma.tools.colormap` makes, checks, joins and previews maps (see Making color maps). One sheet serves many recolors, and each sheet-and-map pair is combined once and cached.
- `knight.anim.json` is the sheet's animations (the sections below say what it holds). One file belongs to one sheet, so a hero's fight art and map art, which are separate sheets, each have their own.

In the browser a game calls `shell.art.load(reference)`, which resolves to `{source, frame, grid, frames, palette, animations}`; `source` goes straight to `drawImage`, and `animations` is the animation set (or `null` when the reference names no animation file). `drawFrame(context, loaded, index, x, y, width, height, ops)` from `art.js` draws a frame of a sheet, changed by the transforms an animation asks for.

### Animations

`knight.anim.json` holds the sheet's named animations and aliases (a public format; the license exception covers it). The server checks every `*.anim.json` in the game's assets folder when it starts (against the frame count of the sheet with the same name, if there is one) and refuses to start on a bad one; it never plays them.

```json
{
 "animations": {
  "stand_right": {"frames": [0, {"frame": 1, "ms": 250, "rotate": 10}], "ms": 100, "loop": true, "sync": "shared"},
  "move_right": {"frames": [2, 3, 4, 5], "ms": 80}
 },
 "aliases": {
  "stand_left": {"of": "stand_right", "flip_x": true},
  "stand_up": {"of": "stand_left", "scale": 1.5, "pivot": [8, 16]}
 }
}
```

- An **animation** has `frames`: each a number (a frame of the sheet, counting as for `frame` above) or `{"frame", "ms", ...}` with its own time and transform. `ms` is how long each frame shows unless it says (100 by default), `loop` is on by default (off: it holds its last frame) and `sync` is `shared` (the default: everything playing it is in step, counting from the same clock) or `random` (each starts at a random moment of it).
- An **alias** is another name for an animation or another alias (`of`), with a transform of its own. A loop of aliases, an alias of nothing, a name that is both an animation and an alias, or a frame the sheet doesn't have is an error. Names are lowercase letters, digits and `_`, starting with a letter.
- A **transform** is `flip_x`, `flip_y`, `scale` (above 0, at most 16), `rotate` (degrees clockwise, -360 to 360) and optionally `pivot` (`[x, y]` in pixels of the frame; the frame's center if left out), allowed on a frame and on an alias. Within one transform the order is flip, then scale, then rotate. A frame's own transform comes first, then the aliases it was reached through, the one nearest the animation first.
- **Names.** Fight art (its own sheet) uses `base`, `equip`, `hit`, `die`, `flee`, `attack_close`, `attack_throw`, `attack_shoot`, `skill`, `spell` and `item`. Map art uses `stand_<dir>` and `move_<dir>` (`up`, `down`, `left`, `right`), and the map versions of actions that can also happen there, such as `cast` and `equip`, each with an optional `_<dir>`. A game may add names of its own and play them through its client code.
- **Fallbacks.** The client plays the first of these that the file has: the name asked for, then `stand`, then `base`, each as `NAME_<dir>`, `NAME` and `NAME_down` (a missing direction becomes down). So a fight sheet's missing `hit` plays `base`, and a map sheet's `move_left` that is missing plays `move_down`, or `stand_left` if there is no `move` at all. A file with none of them plays nothing (the picture stays as drawn).
- **Playing.** `loaded.animations.play(name, {direction})` gives a player (or `null`); `player.frameAt()` says which frame to draw and which transforms to apply. All players share one clock (`Clock`, in `animation.js`, one `requestAnimationFrame` loop for everything that subscribes), so animations that are `shared` stay in step; a player who asks for less motion (`prefers-reduced-motion`) sees the first frame of each animation and the clock runs no loop. The server never depends on a frame.
- The map scene plays `base` for a tile kind whose `art` names an `animations` file (the example's cellar has a crystal), and sets the stage's `data-animated` to how many tile kinds do. The fight scene's sprites come with the slice that gives monsters and personalities their art.


## Maps

A map (`maps.json`; `terraforma.maps`) is a grid of tiles with a second grid of zones over it. Both are public formats (the license exception covers them). Walking, encounters, objects, doors and edge events are described below; the nearby list is under Reach.

- **Tiles.** `tileset` lists the kinds of tile: `name`, `passable` (default true), `poison` (default false; what it does is the game's rule), `encounter_rate` (out of 10000: the chance a step ending on it meets monsters) and `art` (a picture: a file name under the game's assets folder, or a sheet reference, see Art below). `tiles` is the grid, rows top to bottom, each tile a place in `tileset` (up to 512 by 512; every row the same length).
- **Zones.** `zones` lists the kinds of area: `name`, `encounters` (groups of `monsters`, keys in `monsters.json`, each with a `weight` against the others), `drops` (drop table keys, the area's own, see Item drops), `pvp` (whether parties may fight each other there) and `can_flee` (whether a fighter may flee from a fight there; on by default). `zone_tiles` is their grid, the same size as `tiles`; left out, the whole map is the first zone (which defaults to a plain one).
- **Edges.** `wrap_x` and `wrap_y` make walking off the left or right, top or bottom edge come out on the other side (a wrapped edge is no edge, and fires no edge event). `safe_steps` is how many steps a party takes on the map, from entering it and again after each fight, before it can meet monsters (`Party.steps` counts them; any fight, walking or not, starts it over).
- **Keys.** A map's `key` is its name everywhere else (`Position.map`, a hero's place); `name` is what players read. Maps are checked with the rest of the seed (monsters and drop tables named by a zone must exist). The default hub is a map without a grid (open ground, one plain zone); a `maps.json` row with the key `hub` draws it.
- **Loading.** Maps load into the engine's world on every start. A new key is added, a known one rewritten, and a map the seed no longer lists is kept (things may stand on it). `Map.revision` starts at 1 and goes up whenever a load changes anything about the map, so a client holding an older one can tell.
- **Asking a map.** `Map.normalize(x, y)` (wrapped, or None off the map), `Map.tile(x, y)` and `Map.zone(x, y)` give the tile kind and the zone at a place; off a grid they give open ground and a plain zone.
- **Walking.** The page proposes, the server decides. `GET /api/maps/{name}` gives a page what it draws (size, wrap flags, `revision`, tile and zone kinds and grids, never encounter rates, encounter tables or drops). The party's leader calls `POST /api/parties/{id}/route` with either `{"path": [{x, y}, ...]}` (tiles to pass, in order) or `{"destination": {x, y}}`; the server checks every tile is on the map and passable, fills the gaps between tiles that aren't neighbours with the shortest way (steps go up, down, left or right, through a wrapped edge as an ordinary step; at most `Rules.route_limit`, 100, steps in all) and answers `{map, revision, x, y, route, at}`: the route it will confirm, the tile the party stands on first. The page walks it and calls `POST /api/parties/{id}/route/step` with `{x, y}` as it arrives on each tile. The server confirms the next tile of the route (`confirmed: true`, the party moves there) or, if it can't (not the next tile, the map's `revision` changed, a party in the way, the party in a fight or apart in a town), answers `confirmed: false` with where the party really stands and ends the route, so the page goes back to that tile. `GET /api/parties/{id}/route` shows the route and position again, for a page that reloaded. Only the party's leader walks it.
- **Monsters on the way.** Each confirmed step ends with a roll: once the party has taken more than the map's `safe_steps`, the tile's `encounter_rate` (out of 10000) is rolled on a `WorldRng` stream for that party and that step, and a hit picks one of the zone's `encounters` by `weight` (those that fit `Rules.party_size`), starts the fight where the party stands and ends the route; the step's answer carries `fight` and `monsters`. Any fight started at a spot takes the zone's `drops` as its area drops unless the caller gives its own.
- **Objects.** A map's `objects` are the things a hero uses: chests, doors, signs, whatever the game draws. Each has a `key` (unique on its map), `name`, `kind` (the game's word, `chest` by default; the engine treats all kinds alike and the page may draw them differently), `action` (the kind of reach it takes: `open` by default, `search`, or a game's own), a tile `x`/`y` and a `script`: dialog text, the same language as an NPC's (see NPCs and dialog), so plain text is said, a `question` asks, and `add_item`, `have_item`, quest and status tags work as they do there. A hero uses an object with `POST /api/heroes/{hero_id}/objects/{object_id}/use` (login and CSRF token; no body). It is refused with 409 unless the hero is in reach of it (`Reach.map_object`, see Reach and the nearby list; by default within one tile) and out of a fight, and 404 for something that isn't there. The answer is the first step of the script as a conversation frame, `{"object": {id, key, name, kind}, "events", "prompt", "ended", "window"}`: `window` is true only when the script asked something of the hero (a question, an ack, an activity), which is when the page opens its dialog window; whatever else the script says is in `events`, to show without one. A script that asks goes on through the NPC calls (`GET /dialog`, `POST /dialog/next`, `POST /dialog/leave`), and the conversation ends if the hero leaves reach.
- **Doors and warps.** `warp,map,x,y,label` is a dialog tag the engine runs: it moves the party the hero acts in (and every hero of it) to that tile of that map, drops its route, starts its safe steps over, and *leaves the dialog* (the hero is somewhere else now). The label is where the script goes if the party can't go now (apart in a town, a hero of it in a fight). A door is an object whose script asks and then warps. The seed is checked: the map must be in `maps.json` (or be `hub`), and the tile on it and passable.
- **Edge events.** `edges` gives a script for any of `north`, `south`, `east` and `west` (not for a wrapped axis: a wrapped edge is no edge). A route may end by stepping off such an edge, onto the tile just beyond the map; any other tile off the map is refused. The step is checked in like the rest, but the party stays on its last tile, the route is over, and the script runs for the leader's first hero in the party. The step's answer is `{confirmed: true, done: true, edge, x, y, dialog}` where `dialog` is the first frame of the script (`window` as above). The page learns which edges have events from `GET /api/maps/{name}` (`edges`, and `objects` with `key`, `name`, `kind`, `action` and tile; never their scripts).
- **Revision.** Adding, moving, renaming or removing an object, or adding or removing an edge event, raises `Map.revision` (a page can see them); changing a script does not.
- **Heroes follow the party.** A party's tile is the one that moves, and its heroes' tiles follow it (on every step and every warp), so what a hero can reach is measured from where the party is.
- **Parties in the way.** `Rules.party_blocks(mover, other)` says whether a party standing on a tile keeps another off it. By default none does. It is checked when a route is made (routes go round blocking parties) and at each step. A public interface (the license exception covers it).
- **PvP.** The engine's default `PvpZones.allows_pvp` now reads the zone's `pvp` flag (a map with no zones allows it nowhere, as before); a game's own `Game(pvp=...)` still overrides it.

## Fights between parties (PvP)

Where a party may pick a fight with another party is a rule, in two parts. The place: `Game(pvp=...)` (`terraforma.pvp.hooks.PvpZones`) says whether a spot allows PvP, `allows_pvp(session, map_id, x, y)`; the engine's default follows the map's zone flag (see Maps), so nowhere on a map with no zones. The range window: `Rules.may_start_pvp(attacker_pxp, target_pxp, allowed)` returns None if the fight may start, otherwise why not. By default it refuses where PvP is off, and where it is on it allows a target whose party PXP is at least `Rules.pvp_window` (0.85) of the attacker's, and always a stronger one. A party's PXP is the sum of its fighters' (`terraforma.pvp.service.party_pxp`), and `terraforma.pvp.service.refusal` runs both checks. These are public interfaces (the license exception covers them).

This is the step where a player who has met an enemy party on the map confirms they want to fight it: the game asks first, then makes the call. To pick a fight, a team's owner calls `POST /api/pvp/fights` with `team_id` (their own team; its party picks the fight) and `party_id` (the party to fight), with login and CSRF token. The fight starts with the caller's party as party 0 and the other as party 1, and each player commands their own heroes. It is refused with a 409 and the reason unless both parties stand at the same spot (same map and tile), neither is in a town or in a fight, the place allows PvP and the other party is inside the window. A team not in a party, or not the caller's, is refused too (404 for a team that is not theirs). The nearby list (see Reach and the nearby list) shows the parties within reach; this call still needs both parties on the same tile until party talk is built. What a PvP fight pays out is the engine's ordinary result (experience, no gold or drops unless the game's Rules say so).

Vanguard Tavern's setup: towns and instance dungeons are PvE only, everywhere else is PvP, with the default window (a game that wants 80% sets `pvp_window = 0.8` on its Rules).

        class Zones(PvpZones):
            async def allows_pvp(self, session, map_id, x, y):
                return not (await TOWNS.is_town(session, map_id, x, y) or map_id in INSTANCE_MAPS)


## NPCs and dialog

An NPC (`terraforma.npcs`) stands on a map at a tile, like a hero, and *dialog is how a hero uses a place*: a store, an inn or a church is a tag in what an NPC says, not a separate thing to walk up to. A game stands NPCs on its maps with `npcs.service.place_npc(session, key, name, map_id, x, y, dialog, counter)` (safe to run again: the NPC with that key is moved and rewritten; the dialog is checked, and a wrong one is refused with where it went wrong). `counter` is the NPC's row of counter tiles, `[(x, y), ...]`.

A hero talks from a tile on or next to one of the counter tiles (any of the eight around it) that the NPC is also next to; an NPC with no counter is talked to from the tiles around it. Who may talk to whom, and from where, is the game's rule of reach (see Reach and the nearby list): `Game(reach=...)`, `terraforma.reach.hooks.Reach.npc(session, action, hero, npc)` returns None or the reason not (a level, a quest, a time of day), and the default is that counter rule. What an NPC's dialog does with the tags the engine leaves to the game is `Game(npcs=...)` (`Npcs.tag`). A hero in a fight that is still running can't talk, and a conversation ends when the hero is no longer where they can talk.

The calls, each its own route under `/api/heroes/{hero_id}` (writes need login and CSRF token): `GET /npcs` (who this hero can talk to from here), `POST /npcs/{npc_id}/talk` (start; a hero is in one conversation at a time), `GET /dialog` (the conversation they are in and what it last asked), `POST /dialog/next` with `{"choice": n}` or `{}` (Next, or the index of an answer; null cancels), `POST /dialog/leave`. The server runs the dialog and decides everything; each answer is `{"npc", "events", "prompt", "ended"}`: `events` are what to show and play in order (`text`, and the cues `sound`, `music`, `mute`, `pause`), `prompt` is what the hero is asked, with `accepts` listing exactly what the server will take next (`choice`: the option indexes, `next`, `cancel`; anything else is refused with 409 and the conversation stays where it was) (`{"type": "ack"}` for Next, `{"type": "choice", "kind": "question|switch|inn", "options": [{"text"}]}`, or `{"type": "activity", "command", "parts"}`) or null once it ended. Where an answer leads is never sent to the browser.

The dialog language is DragonStar's, run on the server (the full list is at the top of `npcs/script.py`). A tag is quoted in backticks (two backticks show one); text outside tags is said; a text block ends at a line break or a tag. Flow tags the engine runs itself: `label`, `jump`, `team` and `party` (text for a player's teams or party, others jump), `question` and `switch` (asked after the text that follows; an answer jumps to its label, and cancelling goes to the question's own cancel label or on with the text), `inn` (Yes or No), `ack`, `end` (leave the dialog there) and the cues. The rest are the game's: `services`, `heal`, `recharge`, `select_team`, `resurrect`, `cure`, `uncurse` and the Yes of an `inn` (which the engine does itself when this returns None, see Inns) go to `Npcs.tag(session, hero, command, parts)`, which returns a label to go to, `""` to go on, or None for not handled; a tag it does not handle reaches the browser as an *activity* to run (the shop's calls, say), and the browser finishes it with `next`. The engine also runs the tags that read or change the game's state. `have_item,item,qty,scope,label` jumps to the label unless the party has at least `qty` of the item in one hero's pack; `add_item,item,qty,label` puts `qty` in the talking hero's pack (all or nothing: it jumps if they do not all fit); `remove_item,item,qty,label` takes them from the talking hero (it jumps if they do not have that many). `quests,category,level,op,n,scope,label` compares the quests a team completed (`level` a whole number or `any`) with `n`, `quest_marker,quest,op,value,scope,label` compares a team's marker for a quest in progress with `value` (no marker is 0), and `set_quest_marker,quest,value` sets the talking hero's team's marker (0 clears it). `op` is `eq`, `ne`, `lt`, `le`, `gt` or `ge`; `scope` is `any` (any team of the party, for items any hero), `lead` (the party's leading team: the leader's first team in the formation) or `each` (every team, for items a hero of every team). The party is the one the team acts in right now (`towns.service.acting_party`), so in a town a team speaks only for its own group. Quests belong to the *team*: `terraforma.quests.service.complete(session, team_id, category, level)` adds to its permanent record (the engine awards nothing itself; a game calls it), and markers are whole numbers up to 1000000. `warp,map,x,y,label` moves the party to a tile of another map and leaves the dialog (see Maps, Doors and warps). The engine also runs the Challenge Token and gold tags, which is how a perk is sold (a perk is a dialog, not a table): `have_tokens,amount,label` jumps unless the talking hero's account holds that many Challenge Tokens, `spend_tokens,amount,label` takes them (one ledger entry, reason `spend`; it jumps if the account holds fewer, taking nothing) and `add_gold,amount,label` pays gold into the talking hero's purse, wherever the game's economy keeps it. Each step of a conversation runs in a savepoint: if one fails (a status that does not exist, say), whatever the step had already done, items, tokens and gold, is undone. Two differences from DragonStar, both stricter: a label that is neither defined nor `end` is refused when the dialog is placed (DragonStar silently leaves), and a choice at the very end of a text is still asked. The shops are *activities* the engine runs from the conversation (next section); the inn is described after them.

## Reach and the nearby list

This is an MMO: a hero is rarely on the same tile as what they want, and parties move. So interaction is by *proximity*, and what counts as in range is the game's rule (`Game(reach=...)`, `terraforma.reach.hooks.Reach`; a public interface, the license exception covers it). An *action* is a string: the engine's are `talk`, `invite`, `open`, `search`, `fight` and `help`, and a game may add its own. There is one rule per kind of target, so a game can set them apart:

- `Reach.npc(session, action, hero, npc)`: whether the hero is in range of the NPC for the action, None or the reason not. By default a `talk` is the counter rule (see NPCs), and any other action is from the tiles around the NPC.
- `Reach.map_object(session, action, hero, obj)`: the same for a chest, door or other map object (see Maps), for the object's own action. By default within one tile, on its map.
- `Reach.party(session, action, actor, party)`: the same for another party, where the actor is a hero or a party. By default within one tile, on the party's map. `Reach.party_window` (1) is how far, in tiles, a party can be and still be asked about; the engine only asks the rule about parties inside it, so a game whose rule reaches farther raises it (or sets None to ask about every party on the map).
- `Reach.lists_parties(session, action, hero)`: whether the nearby list for the action shows parties after the NPCs (by default for `talk` and `invite`, not for the rest).
- `Reach.valid_for(action)`: how many seconds the browser may show a list before asking again (`valid_seconds`: 60 for `talk` and 300 for `invite`, `default_valid` for the rest). Every call that acts asks the rule again when it runs, so a stale list is refused cleanly rather than trusted.

Distances count a diagonal step as one tile and go round a wrapped edge of a map (`terraforma.reach.hooks.distance`). `Npcs.can_talk` is gone: the NPC calls ask `Reach.npc` with `talk`.

`GET /api/heroes/{hero_id}/nearby/{action}` (login; the hero must be the caller's; `action` is lowercase letters and underscores, up to 32) answers `{"action", "valid_for", "nearby"}`. `nearby` lists the NPCs first, then the map objects whose `action` it is, then the parties, each group nearest first and ties by name and id, at most `Rules.nearby_limit` (20) in all so a crowd does not flood it. An NPC is `{"kind": "npc", "id", "key", "name", "distance"}`; an object is `{"kind": "object", "id", "key", "name", "object": <its kind>, "distance"}`; a party is `{"kind": "party", "id", "teams": [{"id", "name"}], "distance"}`, naming only the teams their players made visible (a hidden team is just part of the party). The hero's own party and parties in a town are left out. `GET /api/heroes/{hero_id}/npcs` still lists only the NPCs the hero can talk to.

Not built yet: talking to a party and helping it, and fighting a party from range instead of the same tile.

## Shops

A shop is an NPC's dialog waiting on a `vend`, `hawk` or `shop` tag; there is no shop table. A hero shops from their conversation, so the NPC's reach rules apply (walking away ends it) and the browser never names a price. The calls, each its own route: `GET /api/heroes/{hero_id}/dialog/shop` shows the wares with prices, what the hero could sell and for how much, and their gold; `POST .../dialog/shop/buy` (`item`, `qty`) and `POST .../dialog/shop/sell` (`position`, `qty`) need the CSRF token and are limited like trades; `POST .../dialog/next` leaves the shop and goes on with the text. A hero in a fight that is still running cannot talk, so cannot shop. In the browser the shop is part of the Talk panel: a ware the server marks `stacks: false` (equipment) is bought one at a time with no quantity box, and a purchase says how many did not fit in the pack. There is no player-to-player market: an auction house is not planned, so the shop is the whole of the market on screen.

- `vend,item1,price1,item2,price2,...[,cancel]` sells exactly the listed items at the listed prices, as in DragonStar. It never buys.
- `hawk,margin,item1,price1,...[,cancel]` buys: a listed item at its listed price, any other item at its own price times `margin` percent (rounded half up). It never sells.
- `shop,key[,cancel]` sells and buys by the game's rules: `Game(market=...)` takes a `Market` that says what the shop with that key sells and for how much: `level(session, rules, shop, hero, party)` (by default the total PXP of the heroes of the teams acting with the hero's), `stock(session, shop, level)` (by default every active item with a price, priced at or under the level, cheapest first), `price(shop, item)` and `sell_percent(shop, item)` (75 by default, which a game can raise or lower for one item, so a quest such as "the area needs healing herbs" makes the economy the reward). Stock is a function of the economy level, the same thing as how hard the region is, so a shop has no seed. This is a public interface (the license exception covers it).

Gold moves through the game's economy (`Game.economy`: the team's purse by default). A purchase puts what fits in the pack and charges only for that (equipment is bought one at a time; nothing fitting is refused), and a sale that would pay nothing is refused, so nothing is thrown away for no gold. A worn item is taken off when it is sold.

## Inns

`inn,price,label` asks Yes or No (No goes to the label). When the game's `Npcs.tag` leaves the Yes to the engine (it returns None, the default), the engine rests the party: the price is taken once per team from the talking hero's purse through the game's economy, and every hero of each team that paid rests through `Rules.rest` (full HP and MP by default, the dead revived as the game decides). By default each team pays its own: the talking hero's team rests and pays. `Game(inn=...)` takes an `Inn` whose `leader_pays(session, hero, price)` (False by default) lets the leading team treat the teams acting with it: when the leading team's player talks, its purse pays for its own team first and then the others in formation order, as many as it can afford. Teams that were not paid for do not rest. If no team can pay, the answer is refused with 409 ("not enough gold") and the conversation stays where it is, so the player can answer No. A hero on no team rests alone and pays their own gold. `Inn.price(session, hero, team_id, price)` (the tag's price, unchanged, by default; never below zero) is asked for each team that rests, so a game can charge teams differently (a guild member's discount); when the leader treats the party, each team's price is still its own. A game that wants something else (a room that is full) answers the Yes in `Npcs.tag` itself. This is a public interface (the license exception covers it).

## The adventurers guild

A game's guild (the Vanguard Tavern, say) is an NPC whose dialog uses the guild's tags. Three are *activities* (the browser calls the guild's routes, and the dialog waits on the tag): `add_team` lets the player add one of their own teams to the party their hero is in, `find_party` lists open parties on the hero's map and lets the hero's team ask one to take it, and `party_requests` lets the party's leader accept or decline the asks. A price is whatever the dialog charges before the tag: adding a team and asking a party each finish the activity and go on with the dialog, so one payment buys one use. For adding a team a Challenge Token price can instead go in the tag, `add_team,tokens`: the tokens are taken in the same change that adds the team, so a team that can't be added (or an account that can't pay) costs nothing. `open_party,on|off,label` (a tag the engine runs itself) opens or closes the hero's party to asks; only the leader may, anyone else goes to the label.

The calls, under the conversation like the shop's: `GET /api/heroes/{hero_id}/dialog/guild` shows what the tag allows now (own teams that could be added; open parties, with places left and the names of visible teams only; the requests to the hero's party, for its leader), `POST .../add-team` (`team_id`), `POST .../ask` (`party_id`) and `POST .../answer` (`request_id`, `accept`). The writes need the CSRF token and are limited like trades. A team can be added if it is the player's own, has heroes, is not in the party, and is in no party or in a party of just itself (which it leaves, so that party is gone). Its heroes then stand where the talking hero does. Accepting an ask brings the asking team into the party (it leaves its own), and the leader who accepted it leads. Teams join whole and only where the party has room for all of them.

Parties normally refuse changes while apart in a town; the guild is in a town, so its joins are allowed there. The joining team becomes a group of the town visit of its own, not waiting, so the party leaves only once it is ready as well. `Game(guild=...)` takes a `Guild` whose `may_ask(session, team_id, party_id)` says whether a team may ask a party (None if so, otherwise why not); by default the team must be an ally: in an alliance with one of the party's teams, or the same player's. `Guild.guest_pass(session, team_id)` returns a `GuestPass(status, seconds)` (default None) for a team a player adds with `add_team`: the team gets that standing status as a guest pass and leaves the party when the time runs out (the status can be a plain one with no effects). These are public interfaces (the license exception covers them). Requests are removed with their party or team.

## Towns

In a *town* a party comes apart. The game says which places are towns (`Game(towns=...)`, `terraforma.towns.hooks.Towns`: `is_town(session, map_id, x, y)`, nowhere by default; the map will ask it as a party moves), and `terraforma.towns.service.enter_town` suspends a party there: it is split into groups of its teams (`Towns.groups`: by default one team each; a game can keep a player's own teams together, for example because the player paid for it), and each team shops and rests on its own. The party can't be joined, merged or have a team leave while it is apart (`parties.service` refuses), with one exception: the guild adds teams in town (see The adventurers guild).

To leave, a team (with the teams in its group) says it is ready (`ready`; `Towns.may_wait` can refuse, for a team in a fight; a hero that fled from it is free) and waits in a holding queue. Every other team of the party is *told* (a notice: `view` lists who is ready) and can follow, which is the same call. A waiting team can `come_back` into the town, or `leave_party` for good (it is not waited for any more). When every team left is waiting, the party is put back as one unit, in the formation it had (its teams' order), and every hero of it is placed at the party's spot on the map (`reform`). `is_town` is true for the hub by default, and `settle` suspends a party that stands in a town. **Leave Town** is the `ready` call: when the last team presses it and the party is whole, the party's fight starts at once, against the monsters `Towns.encounter` picks (by default random active monsters while their PXP stays within the party's, at least one; a game overrides it, and none means no fight; the response's `fight` is the new fight's id or null). On a small chance (`Rules.join_chance`, 3% by default) the hub offers the party a running fight to join instead, and no fight starts until its leader answers (the response's `offer` is true; see Joining a running fight). A team with a hero in a running fight can't press it (`Towns.may_wait`), unless that hero fled from it (see Fleeing). Entering a town and putting a party back are service functions the map drives; a team's own owner calls `GET /api/teams/{id}/town` and `POST .../town/ready`, `.../town/come-back` and `.../town/leave-party` (login and CSRF token; each its own route), and the join-offer calls (see Joining a running fight). These are public interfaces (the license exception covers them).

## Joining a running fight

When a party that is whole again is about to fight at the hub (Leave Town), the hub may offer it a running fight to join instead (`terraforma.fights.joining`). The chance is `Rules.join_chance` (0.03), rolled once from a stream of the world (`WorldRng`, never the `random` module, so a test fixes `World.seed` or sets the chance to 0 or 1). If the roll hits, the hub looks at up to `Rules.join_looked_at` (10) running fights picked at random and offers the first that suits the party: it has room (`Rules.max_fight_parties`, 4: the parties that joined count) and it is in range (`Rules.may_join_fight(joiner_pxp, fight_pxps)`, which by default is the PvP window: the fight's strongest party is at least `pvp_window` of the joiner's strength, and a stronger fight is always fine). The players are never told what the fight is. The offer waits for the party's leader, and until then the party can't walk or pick a PvP fight.

- `GET /api/teams/{id}/town/join-offer` (login) says `{"offer": true|false}` for the team's party.
- `POST /api/teams/{id}/town/join-offer/accept` (login and CSRF token, the party's leader only) makes the party the next party of that fight (`joined: true`, `fight`); if the fight can't take it any more (over, full, out of range now) the party's own fight starts instead (`joined: false`).
- `POST /api/teams/{id}/town/join-offer/decline` (same) starts the party's own fight as usual.

Joining adds a party between two rounds. The `PartyJoined` event (the new party as `state.dehydrate_party` writes it, and how the other parties now count each other) is kept with the fight and written first into the next round that plays (`store.add_party`, `store.pending_joins`), so the log still replays, `store.verify(deep=True)` checks it and the hash chain covers it. The joiners act in that round (it waits for them like for any player), their heroes can be commanded and watched at once, and every watcher is sent `{"type": "party_joined", "fight": id}`. Parties never merge. The joiners earn experience only for what they do after joining, because the experience tree reads the debts the fight collects as it goes. The fight's round clock is the one fixed when it started.

How the parties stand to each other is settled as the party joins. Every pair of teams (one of the joiner's, one of a party already there) with no relationship yet gets one in both directions, neutral (`Relations.initial`). A team's view counts at face value (`Relations.stance(score)`: by default friendly and close are allies, wary and enemy are enemies, neutral is neutral), and `Rules.party_stance(stances)` makes a party's stance toward another party of the stances of its teams' pairs: allies and no enemies, ally; enemies and no allies, enemy; both, neutral; none at all, as for strangers and for monsters (who have no teams), enemy. It is one way: the joiner may count a party as an ally while that party counts the joiner as an enemy. The result is written into each party's `allies` and `enemies` (a party in neither is neutral to it). `Rules.fight_is_over` now also ends a fight whose parties that are left count none of the others as enemies, so neutral parties do not fight on forever. `Rules.join_chance`, `join_looked_at`, `max_fight_parties`, `may_join_fight`, `party_stance`, `Relations.stance` and the `PartyJoined` event are public interfaces (the license exception covers them).

## Monster-party play

A player can volunteer to command the monsters of a new fight instead of a hero party (`terraforma.monsterplay`; built in slices, this is the queue and the seating). Volunteers wait in a queue, longest first. When the server *creates* a fight that allows it, it seats the longest-waiting volunteer the game accepts as the controller of the monster party (`MonsterSeat`); with nobody queued, or nobody accepted, the AI plays as always. A volunteer is never seated into a running fight, and a fight never waits for one. The seat is recorded (the fight view says `monsters_played`) and the player commands the monsters, is rewarded and may be locked out (below); only guests who are not logged in come later.

- **Which fights.** `FightRecord.monster_play`: on for random encounters on the map and the hub's Leave Town fight, off for any other fight (`live.start_team_fight` and `start_party_fight` take `monster_play=False`; a scripted fight leaves it off unless a game asks), and never for PvP or coliseum fights. A fight another party joins keeps its volunteer.
- **The calls.** `GET /api/monsters/queue` (login) says whether the caller waits and where (`position`, 1 is next), the `seat` they hold (the fight and party), a `locked_until`, why they may not volunteer (`refusal`) and how often to check in. `POST .../join`, `.../leave` and `.../check-in` (login and CSRF token; each its own route, rate-limited) volunteer, leave and say "still here". A volunteer who has not checked in for `Rules.monster_checkin_seconds` (60) is no longer waiting: the next seating drops them, and joining again puts them at the back.
- **The rules.** `Rules.may_queue_monsters(volunteer)` says who may wait (None, or the reason): by default a logged-in account with a team, no unfinished fight (as a hero or as a monster player) and no running lockout (admins are exempt from a lockout). It is given a `Volunteer` whose `account_id` may be None, so a game can accept and tell apart people who are not logged in; the engine's own calls always have an account. `Rules.may_play_monsters(volunteer, seating)` says who may take the seat of a particular new fight: by default not an account with a hero in it, not one with *any* team that counts a team of the heroes as an ally (`Relations.stance`, judged across all its teams), and not one in another fight. A volunteer the rules refuse stays queued for the next fight. `Volunteer` and `Seating` are in `terraforma.monsterplay.facts`. These are public interfaces (the license exception covers them).
- **Commanding.** The player who holds a fight's seat is, for every fighter of the monster party, what a hero's owner is for theirs: `GET /api/fights/{id}` shows the fight to them (their fighters are `yours`; a `seat` key tells them `{party, absent, admin}`), `GET /api/fights` lists it (`monsters: true`), the fight socket lets them listen, and `POST /api/fights/{id}/commands` takes their commands. The heroes' pending commands are never shown to anyone (only who has committed). Rounds wait for them like for any player. The monsters never flee unless the game lets them (`Rules.monster_flee_allowed(fight, address)`, on top of `flee_allowed`).
- **Absence.** A round in which the player gave *none* of their fighters a command is *missed*: it is counted (`MonsterSeat.missed`, kept for the rewards), their monsters repeat the commands they had last round (the AI chooses when there were none, or the old command no longer makes sense: its target is down, say), and `Rules.monster_absent(missed)` says whether the monsters now go to the AI (by default after the first miss, DragonStar's way). While absent the AI plays the monsters and the round does not wait for them. The player returns by commanding a monster again or by `POST /api/fights/{id}/monsters/back` (login and CSRF token; the page calls it when it loads the fight); the count stays.
- **Admin takeover.** `POST /api/fights/{id}/monsters/take-over` (login and CSRF token, admins only) sits an admin in a *running* fight that allows monster play, in an empty seat or one whose player is absent (never over a player who is commanding), and not if the admin has a hero in it. The round's end is pushed back by a whole round (never made earlier) so they can finish the playback and decide, and the fight's watchers get a `deadline` message. The seat is marked `admin`: it earns nothing, whatever the rules pay.
- **When the fight ends.** The seat is settled once (`monsterplay.service.settle`, called from `store.apply_results`). It is given a `SeatResult` (`played_through`: no round missed; `won`: the monster party was still standing; `absent`: the AI was playing when it ended; `rounds_missed`; `admin`). `Rules.monster_challenge_earned(result)` says how many Challenge Tokens it earns, **none by default**; DragonStar's way is `int(result.played_through) + int(result.won and not result.absent)`. They are paid through the daily and purse caps (`challenge_daily_cap`, `challenge_purse_cap`) like any fight's. `Rules.monster_lockout_seconds(result)` says how long the player may not volunteer again: by default `Rules.monster_lockout_default` (an hour) for one who missed rounds, was not back in control at the end and whose monsters lost. A longer lockout already running is kept. A seat an admin took pays nothing and locks nobody out, whatever the rules say, and an admin account is never locked out. Monster players earn no gold, experience or drops.
- **The heroes' bonus.** The heroes of a party still standing get extra experience for beating monsters a player commanded at any point of the fight, even briefly: `Rules.monster_player_bonus(fight, party, overkill, monster_hp)` gives the share of what each hero earned, by default the overkill they dealt those monsters (damage past the last hit point, from the log's `Died` events) as a share of the monsters' total hit points, up to `Rules.monster_bonus_cap` (0.15, DragonStar's). It is a second `XpEarned` event for the hero, so the log shows it and it replays. A game turns it off with a cap of 0.
- **Tables.** `monster_volunteers` (one place per account), `monster_lockouts` (written when seats are settled, a later slice) and `monster_seats`. None stands on a map: a volunteer waits for any fight, and a seat belongs to its fight.

## Item drops

A drop table (`drop_tables.json`) says what a monster, or an area, leaves behind. A monster names the tables it rolls when it dies (`drops`); a fight may carry *area* tables of its own (`live.start_team_fight(..., area_drops=[keys])`; the map's, once there are maps).

- **A plain table** rolls every entry on its own: an entry is `{"item", "chance", "min", "max", "for"}`. `chance` is out of `Rules.drop_chance_scale` (10000 by default, so 10000 is a sure thing and 1 is one in ten thousand); `min` and `max` (default 1) say how many. **A weighted table** (`"weighted": true`) instead picks an entry by `weight`, `rolls` times; an entry with no `item` means nothing drops.
- **Who gets it.** An entry's `for` is `one` (one person, the default), `each_team` (one in each team of the winning side) or `each_member` (every hero of the winning party). Who that person is, is the game's rule: `Rules.drop_recipients(fight, party, monsters, share, rng)`. The default picks one at random among the heroes who *contributed*, which it reads off the experience debts the fight keeps: whoever harmed a monster that died (a hit, or through a status, or by placing a bad status on it) and whoever placed a good status on one of those. Healing does not count. Everyone in the pool has the same chance, and a hit for 1 HP counts the same as any other. A game overrides it for a leader's choice, the last strike, round robin, a team chest and so on (choices that need players to answer later are *held*: see **Held drops** below).
- **When.** `Rules.roll_drops` runs when a fight ends, after the experience and the gold, for each party of players that won: the tables of every monster that died, and the area's tables once for the fight (`Rules.map_drops_once_per_fight`, on by default; off rolls them for every monster instead). The dice are the fight's own stream, so a fight replays exactly.
- **What lands.** A `Drop` event, and the item goes into the hero's inventory in the fight; what does not fit (twelve stacks, 250 to a stack, gear never stacking: `Rules.inventory_stacks` and `stack_size`) is a `DropLost` event, never lost silently. `store.apply_results` puts the dropped items in the heroes' inventories, once.
- **Held drops.** `Rules.drop_mode(fight, party, monsters, share, rng)` says how one drop is given out: `"auto"` (the default, `drop_recipients` at once), `"need_want"` or `"assign"`. A held drop is a `DropHeld` event `[party, item, quantity, mode]`, nobody is given it, and `store.apply_results` makes a row of it in `pending_drops` (once, however often it is saved) standing where the fight did. A *need/want* drop waits until every hero of the party that fought has said `need`, `want` or `pass` (changing their mind is fine until the last one answers); then those who needed (or, if none did, wanted) roll 1 to 100 from a stream of the fight's own (`"drop", n`), the highest wins and a tie goes to the lower hero id. If all pass it is `unclaimed`. An *assign* drop is given to a hero of the party by whoever `Rules.may_assign_drop(hero_ids, hero_id, is_leader)` allows: by default the hero's player, if they lead the party (see Parties), and nobody else; a game overrides it to say otherwise. (`is_leader` is a new third parameter: an override written with two parameters needs it added.) What does not fit the winner's pack is counted in `lost`, not lost silently. Calls (each its own route, login and CSRF token on the writes): `GET /api/heroes/{id}/pending-drops`, `POST .../{drop_id}/choose` (`{"choice"}`) and `POST .../{drop_id}/assign` (`{"to_hero_id"}`). Others' answers stay hidden until the drop is settled.
- **Checks.** The seed refuses a table that names an unknown item, a chance outside 1 to the scale, a minimum above its maximum, an empty table, a plain entry with no item or a weight, a weighted one with no weight or a chance, and a monster that names an unknown table.

## Gold and the economy

Where gold lives is the game's decision, so the engine asks `Game(economy=...)` (`terraforma.economy.Economy`). `TeamGold`, the default, is DragonStar's way: a hero on a team spends and earns from the team's gold (`Team.gold`), and a hero on no team has gold of their own (`Hero.gold`). `HeroGold` keeps every hero's gold on the hero and splits what a team earns between its heroes, the first by slot getting the odd coins. A game subclasses `Economy` for anything else, overriding `purse(session, hero)` (the row whose `gold` is the hero's money) and `credit_team(session, team_id, amount)` (what a team earns).

`balance`, `credit` and `debit` work on the hero's purse; a debit that would take more than is there raises `NotEnoughGold` and takes nothing. Gold moves with single statements, so two calls at the same instant never lose a coin. The inventory call shows the hero's purse in the game's economy. A fight's gold is paid by `economy.credit_fight_gold(session, economy, fight_record, [(team_id, amount), ...])`: once per fight (the fight records that it has paid), however often it is called. `fights.store.apply_results` does it from the fight's `Gold` events, through the game's economy. These are public interfaces (the license exception covers them).

## Trading

Heroes give each other gold and items, if the game's economy allows it. Who may trade with whom is `Economy.can_trade(session, giver, receiver, what)`, which asks the economy's `trade_policy` (`terraforma.trading.policy`). The stock policies are `NoOne`, `Anyone`, `WithinTeam` (the default: heroes on the same team), `WithinParty` (the same team, or teams in the same party), `Related` (whatever the economy's `related(session, giver, receiver)` says, the hook a game fills in for its own relationships; nobody until it does) and `AnyOf(...)` to combine them. A game sets one on its economy (`trade_policy = AnyOf(WithinTeam(), Related())`) or subclasses `TradePolicy` and writes `allows(economy, session, giver, receiver)`. These are public interfaces (the license exception covers them).

The calls, each its own route, for the hero's owner and with the CSRF token: `POST /api/heroes/{id}/give-gold` (`to_hero_id`, `amount`) and `POST /api/heroes/{id}/give-item` (`to_hero_id`, `position`, `qty`), and `GET /api/heroes/{id}/trades` for the hero's ledger. They are limited to 120 gifts an hour per account. An item moves only if it is not worn and all of it fits in the other pack; gold moves between the two heroes' purses in the game's economy, so heroes who share a purse (teammates under `TeamGold`) have nothing to give each other. Whether the other hero does not exist or may not be traded with, the answer is the same (404, "you can't trade with that hero"), so the calls cannot be used to find heroes. Every gift is a line in the ledger (`TradeRecord`), which keeps the heroes' ids and names so the history outlives a deleted hero.

## Relationships

A team has a relationship with another team: how it feels about it, as a score from -100 to 100 and a short private note. It is *directed* (Aria's view of Bram and Bram's view of Aria are separate rows) and private: only the team's owner reads it, and the other side never sees a score or a note. Scores have named *bands* (`enemy`, `wary`, `neutral`, `friendly`, `close` by default). Alliances are the same kind of side (see Alliances).

The game has the say, through `Game(relations=...)` (`terraforma.relations.hooks.Relations`). A fight can move them too, only if the game says so: when a fighter moves the gauge of one on another team whose party is not its enemy (an ally, a neutral or a partymate), `Rules.relation_moved(fight, actor, target, resource, before, after, maximum)` returns how much the actor's team's view of the target's team changes (the default is 0, so nothing moves). The rule may instead return `AskPlayer(delta, reason)` (from `terraforma.fights.rules`) to let the player decide: the log gets a `RelationPrompt` event (team, other team, suggested change, reason) for the owner of the actor's team to be asked about, and nothing moves until they answer (the engine's way to ask and record the answer is the after-fight rating prompt, below). A non-zero number is a `RelationChange` event (team, other team, change) in the fight's log, and `fights.store.apply_results` applies what the log holds, added up per pair, through `Game(relations=...)` once (the fight records that it has: a change the game's rules refuse, or for a team that has gone, is dropped). The engine never changes a score on its own; every change goes through `Relations.resolve(session, subject, object, current, change)`, which by default gives what was asked, within the scale. A game also sets `bands`, says where a new relationship starts (`initial`) and who may form one at all (`may_form`), and moves scores from its own rules by calling `terraforma.relations.service.apply(session, relations, Change(subject, object, delta=-5, by="game", reason=...))`. A `Change` says who asked (`by` is `"player"` for the owner in a call, `"game"` for the rules). These are public interfaces (the license exception covers them).

The calls, each its own route, for the team's owner (the ones that change something with the CSRF token, limited to 120 an hour per account): `GET /api/teams/{id}/relationships` (the bands, and this team's own views by name), `POST .../relationships/set` (`id` of the other team, and a `score`, a `note`, or both) and `POST .../relationships/forget` (`id`). A team's relationships go when it is deleted.

## Alliances

An alliance is a formal power structure of teams: a name, member teams in roles, and invitations. The game defines the roles and what each may do through `Game(alliances=...)` (`terraforma.alliances.hooks.Alliances`): `roles` (highest rank first; `leader`, `officer`, `member` by default), `founder_role` and `default_role`, `permissions` (which of `invite`, `withdraw`, `remove`, `set_role`, `hand_over`, `disband` and `speak` each role may do), `max_members` (counting invited teams) and `max_per_team`, and the hooks `may_found`, `may_join` and `allowed`, the one place to say otherwise (by default a team acts only on a team of a lower rank and gives only a role below its own). These are public interfaces (the license exception covers them). Voting and how an alliance is run beyond roles are the game's, on top of this.

A team's owner acts for it. A team founds an alliance and holds its founder role; a role that may invite invites a team, whose owner accepts or declines (it joins in the default role); a team leaves, or is removed; the only holder of the founder role can't leave while others remain and hands the role over first; the last team out, or a disband by a role that may, takes the alliance with it. A team that is deleted leaves its alliances, and an alliance left without a founder gives the role to its best-ranked, longest-standing team. Someone with no team in an alliance cannot tell that it exists (404).

The calls, each its own route (the ones that change something with the CSRF token, limited to 120 an hour per account): `GET /api/alliances` (your teams' alliances and the invitations waiting), `POST /api/alliances` (`team_id`, `name`), `GET /api/alliances/{id}` (`?team_id=` reads it as that one of your member teams), `GET /api/alliances/{id}/roster` (members: each team by name and role, with the token of its page only while it is visible and its player's handle and page token only if the player is in the directory), `POST /api/alliances/{id}/invite|withdraw|remove|hand-over` (`team_id` of the acting team and `target_team_id`), `.../role` (also `role`), `.../leave` and `.../disband` (`team_id`), `GET /api/teams/{id}/invitations` and `POST /api/teams/{id}/invitations/accept|decline` (`alliance_id`).

**Ballots** put a question to the alliance. A role that may `open_ballot` gives a title (and `kind` and `payload` for the game's own use, which the engine keeps and never reads), two to ten options, whether it is `secret`, and when it closes; each team whose role may `vote` votes once, weighted as `Alliances.vote_weight` says (1 each by default). A ballot closes when its time is up, when everyone who could vote has (`close_when_all_voted`), or when a role that may `close_ballot` closes it; the game decides who wins (`Alliances.decide`, most weight by default, a tie decides nothing) and acts on it in `Alliances.on_ballot_closed`. Nothing waits on a timer: a ballot is closed, if its time is up, the next time anyone looks at it or votes, and `ballots.close_due` closes every due ballot for a game to call on its own schedule. A *public* ballot shows who voted for what, and a team may change its vote until it closes; a *secret* ballot keeps who voted apart from what was voted (the stored vote has no team on it), shows only the turnout until it closes and the totals after, and its votes are final. The calls: `GET /api/alliances/{id}/ballots` and `.../ballots/{ballot_id}` (members read; `?team_id=` picks which of your teams you read as), `POST .../ballots` (`team_id`, `title`, `options`, `kind`, `payload`, `secret`, `closes_in_hours`), `POST .../ballots/{ballot_id}/vote` (`team_id`, `option`) and `.../close` (`team_id`).

Alliances are sides in relationships too (see Relationships): a team can have a view of an alliance (`kind: "alliance"`), and an alliance has views of teams and of other alliances, read by its members and set by a role that may `speak` (`GET`/`POST /api/alliances/{id}/relationships`, `.../set`, `.../forget`).

**Rating after a fight.** When a fight between player teams ends, a team that was helped or harmed by another player team (read off the experience debts the fight kept: a hit, a heal, a status) and has no opinion of it is asked to rate it (`terraforma.relations.ratings`): a question kept until the player answers or dismisses it. Nothing changes by itself: an answer is an ordinary change to the relationship, so the game's `Relations.resolve` still decides the score that results, and `Relations.ask_after_fight(session, subject, object, interaction, score)` decides whom to ask at all (by default: only a team in the neutral band, `interaction` being `helped`, `harmed` or `both`). Monsters and a team's own side are never asked about. A game's own rule can ask too: a `RelationPrompt` event in the log (from `Rules.relation_moved` returning `AskPlayer`) always raises a question (the game said so), which carries the suggested change and the reason and can be accepted as it stands. The calls (each its own route, a login; the two that change something with the CSRF token, in the same 120 an hour): `GET /api/ratings` (the bands and the open questions, with the teams' names, the fight's public name and any suggestion), `POST /api/ratings/{id}/answer` (a `score`, -100 to 100, or `accept: true` for the suggestion) and `POST /api/ratings/{id}/dismiss`. A team's questions go when it is deleted.

## Using items in the field

A potion, an ether or a revive can be used outside a fight: `POST /api/heroes/{id}/use-item` (login and CSRF token; a strict body: the item's `position` and an optional `target_hero_id`, the user's own hero when left out) spends one of the item on one of the *caller's own* heroes (`terraforma.heroes.field.use_item`). What it does is `Rules.field_use(rng, effect, vitals, maximums)`: by default the item's own `use_effect` as in a fight (heal and restore mana for the living, revive for the dead; anything else is for fights only), and a game overrides it to allow more or less. The new HP and MP are kept on the hero (`Hero.vitals`). A hero in a fight that is still running can neither use nor receive an item (the fight has its own item command), and a use that would change nothing is refused and costs nothing. The roll comes from the world's stream for that hero, item and stack size, so it never uses the `random` module.

## Chat

Players talk in *channels*. A channel is a kind and a key (`("party", "12")`), and every kind answers the same few questions (`terraforma.chat.hooks.ChannelKind`): how a key the player gave becomes the stored one (`resolve`), who is in the channel (`member`, which means read and speak), which channels a player is in now (`channels`), and who hears a message said from a place (`hears`). The calls know nothing about any one kind, so a game adds a channel (a guild, a dungeon run) by writing a `ChannelKind` and listing it in `Chat.kinds`, and drops one by leaving it out. The engine has six: `party` (players with a team in the party; key: the party id), `alliance` (players with a team in the alliance; key: the alliance id), `nearby` (the map the player stands on, heard within `NearbyChat(range=10)` tiles; key: the map id), `town` (whoever stands where `Towns.is_town` says; key: the map id), `global` (every player; key `all`) and `whisper` (two players; the key is the other player's handle, or the pair as the channel list gives it). A team's chat is not a kind: a team belongs to one player.

A game hands `Game(chat=...)` a subclass of `Chat` to set `kinds`, `body_max` (500), `history` (50), `flag_reasons` (`tou`, `spam`, `harassment`, `other`), `clean` (how the text is kept; a place to filter words) and `may_speak(session, speaker, kind, key, body)` (a reason a player may not say this now, or None). This is a public interface (the license exception covers it).

Messages are saved with the place the speaker stood, and fetched, not pushed: a page asks for the lines after the last one it holds, so any server can answer. A player needs a handle to chat, and only the handle is ever shown. The calls (each its own route, a login; those that change something with the CSRF token): `GET /api/chat/channels`, `GET /api/chat/messages?kind=&key=&after=&limit=` (latest lines, or the lines after `after`, oldest first; lines from muted players and ones out of hearing are left out), `POST /api/chat/say` (`kind`, `key`, `body`; 600 an hour), `GET /api/chat/mutes`, `POST /api/chat/mute` and `/unmute` (by handle; a mute follows the player into every channel and hides their whispers too), `GET /api/chat/reasons` and `POST /api/chat/flag` (`message_id`, `reason`, `note`; the player must be able to see the message, and flagging twice is one flag). For admins: `GET /api/chat/admin/flags?state=open` (each flag with the message and the five lines before it) and `POST /api/chat/admin/settle` (`flag_id`, `state` `actioned` or `dismissed`; what acting on a flag means is the game's own). The Chat panel (`chat.js`, one of the engine's panels) lists the player's channels, polls the open channel every three seconds for the lines after the last one it holds, and has a send box, a whisper box (by handle), a mute list, a Flag button on every line that is not the player's own, and, for an admin (`admin` in the channel list), the flags to settle. An admin can bar a player from speaking (`POST /api/chat/admin/ban`: `handle`, `hours` or none for good, `reason`; they can still read; `GET /api/chat/admin/bans`, `POST /api/chat/admin/unban`; an admin can't be barred, and one ban per player, a new one replacing the old). Settling a flag as `actioned` calls `Chat.actioned(session, admin, sender_id, message, reason)`, the game's place for its own consequence (a warning, `chat.service.ban`); the engine does nothing more by itself. The Chat panel shows the bans to an admin, with a Ban 24 hours button on every flag and a Lift button. Housekeeping removes messages older than `chat_retention_days` (settings, 7 by default, 0 keeps them for good), except those with a flag no admin has settled.

## Voice

The engine does not carry audio. A voice *provider* outside it makes the rooms, and the engine gives a member a link to one (`terraforma.voice`). Discord is the provider the engine ships; it is optional and off unless `settings.toml` sets both `discord_bot_token` and `discord_guild_id` (the id of the Discord server the bot may make voice channels in; the bot needs Manage Channels and Create Instant Invite there). A room belongs to a chat channel (see Chat): `Voice.kinds` says which kinds have one (`party` and `alliance` by default), `Voice.room_name(kind, key)` what it is called, and `Game(voice=...)` hands a game's subclass in. The membership is the chat channel's own, so whoever is in the party or alliance may join its room and nobody else gets a link.

The calls (each its own route, a login; the second with the CSRF token, 60 an hour): `GET /api/voice` (`enabled` and the `kinds` that have rooms; the Chat panel shows a Join voice button for those) and `POST /api/voice/join` (`kind`, `key`; the answer is `url` and `seconds`). The first member to ask makes the room (`voice_rooms`, one per channel, kept so two servers share it: a room made twice is closed again), and every member gets a fresh single-use invite that lasts five minutes. Housekeeping (`old_voice_rooms`) closes a room at Discord `voice_room_hours` (24) after it was made; one Discord will not close is tried again at the next pass. Discord's REST API is called over the standard library, so there is no new dependency, and the bot token is never logged. A refusal or an unreachable Discord is a readable 502.

What it cannot do: Discord voice cannot be embedded in the browser, so players need the Discord app or site and an account, and an invite lets whoever holds it join the Discord server. The rooms are visible to everyone in that server (names like `party-12`, never a player), so use a Discord server meant for the game. Making a room private to its members needs each player's Discord account linked (OAuth) and a permission per member: not built yet. Built-in browser voice (WebRTC) is a later option behind the same `VoiceProvider` interface (`open_room`, `invite`, `close_room`).

## Profiles

A player, a team and an alliance can each have a public page, reached by a **random token** (22 characters, from `secrets`) rather than a name or number, so a page can't be guessed. The owner can replace the token at any time; the old one stops working at once. A page shows only what its owner chose, and never an account id, username or email.

- **Visibility** is set per team, and it is the real switch: a team is *hidden* until its player makes it *visible* (`PUT /api/profile/team-visible`, `team_id` and `visible`; the player can hide any or all of their teams). A visible team's page can be reached from the player's page and from the pages of the alliances it is in; a hidden team has no link or page (404), though its name still shows on its alliance's page. The *directory* is a separate opt-in (`PUT /api/profile/directory`, `enabled`, off by default): while a player is in it, their handle appears next to their visible teams in an alliance's roster, and alliance members can go from a team's page to the player's page.
- **The player's page** (`GET /api/p/{token}`, no login): the player's public handle (`null` if none is set), a short bio of up to 500 characters, and the player's visible teams, each named with the token of its page. It is always public to anyone holding the link. The owner makes it with `POST /api/profile/token` (which also replaces it), reads it with `GET /api/profile` (the teams with their `visible` flags, and `directory`), sets `PUT /api/profile/bio` (`bio`) and replaces a team's address with `POST /api/profile/team-token` (`team_id`).
- **A team's page** (`GET /api/p/team/{token}`): the team's name and the alliances it is in (each with its page token once the alliance has one), and the player's handle only if the player is in the directory. It exists only while the team is visible (otherwise 404).
- **An alliance's page** (`GET /api/p/alliance/{token}`): its name, a short description and *every* team in it by name and role, so anyone can see which teams belong (never their members). Only a *visible* team also has its page token, and its player's handle if the player is in the directory; a hidden team shows its name alone (`page` is null). Members read the alliance's own profile with `GET /api/alliances/{id}/profile`; a team whose role may `speak` (`Alliances.permissions`) makes and replaces it with `POST .../profile/token` and writes it with `PUT .../profile/bio`. Members of an alliance open a visible member team's page with `GET /api/alliances/{id}/teams/{team_id}/profile` (a login; 404 to anyone else, or for a hidden team), which also carries `player`, the token of the player's page, when the player is in the directory. The directory's listing of players, where others find a page, comes later; this opt-in is what it will read.

The owner's calls need a login and, to change anything, the CSRF token, and are limited to 60 an hour per account. The public pages need neither, and are limited per address (120 per 15 minutes) so a token can't be hunted for. Deleting a team or disbanding an alliance deletes its page. These routes and their response shapes are public interfaces (the license exception covers them).

## Challenge Tokens

Challenge Tokens are a special currency: one balance per account (`ChallengeBalance`), with a ledger of every change (`ChallengeEntry`: who, how many, why, which fight or purchase) so a balance can always be re-derived (`challenge.service.audit`). The game decides what they are worth and what limits them; the engine keeps the books.

- **Earning.** `Rules.challenge_earned(fight, address)` says what a hero's fighter earns when a fight ends (this is where a game sets its earning rates); it pays nothing by default, so a game opts in. `fights.store.apply_results` pays it, once per account per fight (the ledger holds a unique fight and account pair, so saving the result again pays nothing more). Tokens are only ever paid to the account that owns a hero in the fight, so an admin (`Account.is_admin`) earns only when fighting as a player, never for a monster or a fight they watched. No call sets `is_admin`: a game's own setup does, with `challenge.service.set_admin`.
- **Limits** (both default to none; the game decides). `Rules.challenge_daily_cap(account_id)` is the most an account may *earn from fights* in a UTC day: what would go over is not paid. `Rules.challenge_purse_cap(account_id)` is the most an account may hold: earnings are cut to fit, and a purchase that would not fit is refused whole (nobody pays for tokens that are thrown away). The daily cap does not limit purchases or spending, and neither cap ever takes tokens away (a purse over a lowered cap keeps what it has and earns nothing until it is under). A fight whose pay was cut to nothing is still recorded as paid, so it does not pay again the next day. The daily total is read before it is paid, so two fights that end at the same instant for one account can overshoot the day's cap slightly; the purse cap is exact.
- **Spending.** A game spends through `challenge.service.change(session, account_id, -amount, reason)`, which refuses to take the balance below zero (`NotEnoughTokens`).
- **Buying.** A game that sells tokens sets `challenge_purchase_secret` in `settings.toml` (at least 32 characters; empty, the default, turns the call off and it answers 404). Its own backend (a shop or payment service, never a browser) then credits a purchase with `POST /api/server/challenge/purchase`, sending `Authorization: Bearer <secret>` and `{"account_id": 7, "amount": 50, "key": "order-1234"}`. There is no login, cookie or CSRF token for this call; the secret takes their place. `key` is the caller's idempotency key (8 to 64 letters, digits and `_.:-`): sending the same key again with the same account and amount (a retry) credits once and answers the same with `"duplicate": true`. The answer is `{"credited": 50, "balance": 120, "duplicate": false}`. 401: wrong or missing secret. 404: the call is off, or no such account. 409: the key was used for a different purchase, or the purse cap would be passed (nothing is credited). Every attempt counts against the caller's address (600 per 15 minutes), the secret is compared in constant time and logs scrub the header. The game's backend does the charging and credits only what was paid; the engine takes no payment.

`Rules.challenge_earned`, `challenge_daily_cap`, `challenge_purse_cap`, the `challenge.service` functions and the purchase call are public interfaces (the license exception covers them). They replace `Rules.tokens_earned` and `terraforma.tokens` of the admin tokens: a game that overrode `tokens_earned` renames it to `challenge_earned`, and migration 0030 moves the balances and ledger over.

A game's own rules set the limits and rates. Example for Vanguard Tavern, which adopts DragonStar's numbers (from DragonStar's `MonsterToken`: in DragonStar tokens are earned by playing the monsters in a fight, 1 for playing it through and 1 more for winning it, with at most 3 earned in any 24 hours and no limit on how many are held):

```python
class VanguardRules(Rules):
    def challenge_earned(self, fight, address):
        return 1  # DragonStar: 1 for playing a fight through (a win earns 1 more: see the note below)

    def challenge_daily_cap(self, account_id):
        return 3  # DragonStar: at most 3 earned a day

    def challenge_purse_cap(self, account_id):
        return None  # DragonStar has no limit on what is held
```

The engine differs from DragonStar in three ways, so the example is close, not identical. (1) The engine pays the heroes' owners, as `challenge_earned` is called for hero fighters only; paying a player who controls the monsters, as DragonStar does, is for the game's own code (``challenge.service.change`` with `reason` ``fight``, which the daily cap counts) until the engine has a monster side. (2) The engine's day is the UTC day; DragonStar's is a rolling 24 hours. (3) DragonStar pays a fight's whole award to a player still under the limit when it ends (so a winning fight can carry them to 4); the engine cuts the award to fit the cap (to 3). A game that wants DragonStar's exact behaviour, a win's extra token included, would need hooks for these; say so and they can be added.

## Fight rules

A fight is DragonStar's process: every fighter has chosen a command (attack with the left or right hand, use an item, change gear, use a skill, cast a spell, defend, run), then the round resolves in one pass and returns *events* (`Turn`, `Attack`, `Damage`, `Miss`, `Died`, ...) that say what happened. The fight's state after the round is what you get by applying its events in order (`terraforma.fights.replay.apply_events`), so a stored fight can be replayed and shown to spectators.

- **The rules** are the class `terraforma.fights.rules.Rules`, and `Game(rules=...)` hands the engine yours. `Rules()` is DragonStar's, unchanged: speed (the fighter's Speed spread by 15%, a caster slowed by the spell's cost against their Focus, multi-strike weapons acting several times, ties shuffled), the hit roll (always out of 100: it hits on a roll up to Accuracy ÷ (Accuracy + Dodge) as a percentage, so a critical, a roll of 1 that doubles Strength, is one hit in a hundred whatever the stats are), damage (Strength against Block, scaled by how cleanly the roll hit, from half at the edge of the hit chance to full at a 1, halved when defending, never under 1), the saving throw (Power against Resistance: none, half or all of a harmful spell gets through), and what each effect does. A game overrides any of them:

  ```python
  class MyRules(Rules):
      stats = (*Rules.stats, "Luck")

      def chance_to_hit(self, rng, accuracy, dodge):
          ...
  ```

  This is a public interface (the license exception covers it): the method names and signatures are what games build on.
- **Stats and resources.** `Rules.stats` is the list seeds are checked against. A *resource* is a stat that is a pool: its base is the maximum and its current value what's left. `Rules.resources` lists them (HP, which is life, and MP by default); a game adds its own (rage, technique points) and fills and drains them from the hooks `ability_cost`, `gauge_moved` (called whenever one fighter moves another's resource) and `after_event` (called for every event, and may add more).
- **Statuses and stat values.** `Rules.stat_value(stat, geared, bonus)` sums a stat's geared base and its statuses' bonus and clamps it; `Rules.slay_chance(rng, effect)` decides a slay; `Rules.status_acted(...)` is the hook for a token's source earning from it (see Statuses).
- **Allies, enemies and neutrals.** How parties stand to each other is `Rules.alignment(fight, party)`, returning that party's (allies, enemies); a party in neither is neutral to it. A party is always its own ally. Each `Party` may carry its own `allies` and `enemies` sets; with neither set, as in DragonStar, each party is for itself and every other party is an enemy. The seed's `all_allies`, `all_enemies`, `all_not_allies` and `all_not_enemies` targets follow it, and a game can override `alignment` for alliances and factions.
- **Fleeing.** The `flee` command is a try: it rolls against `Rules.flee_chance(fight, address)` (the fighter's Speed against the Speed of every enemy still in the fight, added up: `100 * mine / (mine + theirs)`) with `Rules.flee_succeeds(rng, chance)`, a `Run` event and then `Fled` or `FleeFailed`. A try that fails costs only the fighter's turn. When it works, `Rules.flee_party(fight, address)` says who leaves: by default the whole party (every fighter of it still standing, one `Fled` event each); a game that wants only the fighter returns `[address]` (Vanguard Tavern's way: the fighter comes back to its party's place when the fight is over). A fighter that fled stays in the fight's layout, so its address and earnings are kept, but it has left: it takes no turn, can't be aimed at (an attack at its place lands on a neighbour who stayed), its statuses don't tick, and its party counts as gone once no one of it is left (`Combatant.present`, `Party.dead`; a fighter that fled is still `alive`). `Rules.flee_allowed(fight, address)` says whether it may be tried at all: the fight's `can_flee` flag, which the map's zone sets (`can_flee`, on by default) or a scripted fight turns off (`live.start_team_fight(..., can_flee=False)`); where it is off the live fight refuses the command (409) and a `Run` in a replay comes to nothing. Monsters never flee by their own choice (the AI does not pick it). **Eject** is an ability (`"effect": "eject"`) that forces its target out the same way: its `base` is the chance out of 100, moved by the user's Power against the target's Resistance to between half and double of it (`Rules.eject_chance`, never over 100); a success is a flee for the target (so `flee_party` and `flee_allowed` apply), it refuses the user's own side unless the effect is `friendly`, and one that does not work says `NoEffect`. **What it pays.** A fighter that fled still earns what it did (half of its own credit) but loses its share of its party's and its team's pools, which are worked out for those left as if it had stayed (they claim the share its work earned). Gold and drops go only to a team with a hero alive at the end (one that fled counts; the gold is split between those teams), and a monster that was ejected is not dead, so it leaves no gold or drops. A party of players that stayed to the end and is all down has suffered a loss: a `PartyLost` event, and `Rules.party_lost(fight, party)` for the game's own rule (where it wakes up, what it pays; nothing by default). A party that all fled has lost nothing; a game decides other outcomes by how many fled in `Rules.fight_is_over` and `party_lost`. A hero that fled is free of the fight (`FightParticipant.fled`) while the others play on: it can walk, leave a town or start another fight, its HP and MP are saved as they stood when it left, and when the fight ends what the end of it paid the hero (experience, level-ups) is *added* to the hero, once, rather than written over what it has become since. These are public interfaces (the license exception covers them).
- **Experience, gold and advancement.** Whenever one fighter moves another's life or mana, `Rules.gauge_moved` makes the target *owe* the actor experience (an `XpDebt` event: the share of the gauge that moved, at the target's `Rules.pxp`, DragonStar's potential experience). When `Rules.fight_is_over` first holds (one party left, or only allies), `Rules.on_fight_end` pays the debts out with DragonStar's experience tree (`fights.experience`): half to whoever earned it, 20% pooled across its party and 30% across its team, for harm done to non-allies and help given to non-enemies; only fighters on a team (`Party.teams`) earn, monsters and NPCs only dilute the pools. Dead enemies' gold is split between each party's teams (`Gold` events), and `Rules.advance` levels up whoever has the experience (`LevelUp`: each stat grows 75 to 100% of the job's growth, from the fight's stream, up to `Rules.max_level`; `Rules.experience_needed` says how much each level takes). Override `on_fight_end` or `advance` for other rewards. Once the payout is made the fight is *over* (a `FightOver` event, and `Fight.over`): it plays no more rounds, so nothing is paid twice, and `fights.store.play_round` raises `FightOver` if asked for another. `fights.store.apply_results` then saves each hero's experience, level and stats to the database and teaches it the abilities its job grants at its new level (it sets rather than adds, so calling it again is harmless). It also saves what each hero's resources (HP, MP, ...) stand at in `Hero.vitals`, and `fights.build.hero_fighter` brings a hero into its next fight with them (never above the maximum in `Hero.stats`; a hero that has never fought, or been rested, is full). A hero that ended a fight at zero HP starts the next one dead. The engine never regenerates heroes between fights: a game calls `heroes.service.rest_hero(hero, rules)` from its inn, potion, camp or level rest, and `Rules.rest(vitals, maximums)` decides what that does, for the living and the dead alike. The default fills everything and revives the dead in full; a game overrides `rest` to bring them back at 1 HP, at half, or to heal only a part (a game that wants regeneration over time calls `rest_hero` itself). A team's heroes reach a fight with `fights.build.team_party`, which also gives the `Party.teams` the experience tree needs.
- **Monster AI.** `fights.ai.choose_command(rules, fight, address, rng)` picks a fighter's command from its four numbers (a monster's `ai` block: `action`, `goal`, `target`, `experience`; DragonStar's meanings, in `fights.ai`): what kind of player it is, what it wants, how well it judges its target, and how much it misjudges stats. `profile_for_level` gives a hero on autopilot its numbers. It draws only from the stream it is given, so fights replay. The engine adds what DragonStar left as notes: what statuses and stat changes are worth to the AI (`Rules.status_worth`, reckoned in hit points by `fights.ai_status`; override it for your own way) and its own play for the Protector (heals, cleanses and buffs the weak and afflicted), Hinderer (bad statuses first), Smart (weighs every command and takes the best) and Omnipotent (as Smart, seeing every stat exactly) actions. It departs from DragonStar in three places, each noted in `fights/ai.py`: stats are read skewed by the fighter's experience percent (DragonStar's formula reads them as a hundredth), a command that reaches neighbours adds up the neighbours' values, and the Fighter and Mage actions keep the better half of their targets, not the first half.
- **Dice.** Never the `random` module: every roll comes from a `WorldRng` stream, one per fight under its map (`fight_stream(world_rng, map_name, fight_id)`), drawn in a fixed order, so the same fight replays exactly.
- **Storing a fight** (`terraforma.fights.store`): a fight is its *initial state*, written once when it starts (`fights.state.dehydrate` turns a `Fight` into plain JSON and `hydrate` back), plus an append-only log of rounds. Each round records the commands that led to it, the events it produced, and a hash of the round before (the first chains from a hash of the initial state), so a changed or missing round shows. `load_state` rebuilds the fight now by replaying the log; `verify` checks the chain, and with `deep=True` plays every round again from its commands and its own dice (`fight_stream(world_rng, map, fight_id, round)`) and expects the same events. Anyone not given a command in a round defends. Heroes and monsters become fighters with `fights.build.hero_fighter` (with the HP and MP the hero has kept, see Experience above) and `monster_fighter`.
- **Pure.** `terraforma.fights` (apart from `store` and `build`) has no database or web code. Heroes and monsters become fighters through `terraforma.fights.content`.

## Live fights

A fight waits for its round (`terraforma.fights.live`). **Starting** one is the server's business: a player has no call to start a fight against monsters. `live.start_team_fight(session, team, monster_keys, rules)` puts a team against monsters where the team stands. Once there are maps, a fight comes from a random encounter while walking or from an NPC whose dialog starts one; until then the hub's **Leave Town** (see Towns) stands in for walking the map into a fight. A fight between players is the one a player asks for, and only against a party they meet (see Fights between parties). A hero can be in one unfinished fight at a time.

- **Commands.** `POST /api/fights/{id}/commands` (login and CSRF token; a strict body: the fighter, the command, what is used, the target) commits a command for one of the *caller's own* heroes' living fighters; sending another replaces it. Nothing else can command a fighter: the monsters are on the AI.
- **Rounds.** The round plays as soon as every player's living fighter has committed, or when `Rules.round_seconds` (30 by default) run out, whichever comes first; a fighter that has not committed defends. The monsters choose with the AI (`fights.ai`) from a stream of their own under the round's, and the commands that were used are stored with the round, so replays never run the AI again. Time here is the wall clock (players are waiting); everything else is the fight's own dice.
- **Play time.** Each account has the seconds it has played, in wall-clock time (`terraforma.playtime`; `GET /api/play-time`, login, answers `{"seconds": n}`). Every call that needs `ActingAccount` (login and CSRF token) counts as the player's input and credits the next `Rules.play_credit_seconds` (10), or less if the next such call comes first; reads count for nothing, and a refused CSRF token credits nothing. A fight's playback counts too: the page tells the server it has finished showing a round with `POST /api/fights/{id}/playback-done` (`{"round": n}`, login and CSRF token, only for a fight the caller has a hero in), and the time from when the round was played (`FightActionRecord.played_at`) to now counts, at most `Rules.playback_cap_seconds` (300) so a closed tab earns nothing more. A stretch of time counts once however many ways it is claimed, so play time can never run ahead of the clock. The follow cap (Social slice b) is built on it (default 10 follows plus 1 per hour played).
- **Following, bans and the directory** (`terraforma.social`). `POST /api/follows` (`{"handle": ...}`) follows a player at once, one way: the list is private (`GET /api/follows`: who the caller follows, the most recently active first and players who never played last; the cap; how many follow the caller) and the followed player only ever sees a count (`GET /api/followers`). `POST /api/follows/remove` unfollows. The cap is `Rules.follow_cap(seconds_played)`, `Rules.follow_base` (10) plus one for every `Rules.follow_seconds_each` (3600) played (see Play time); following someone already followed changes nothing. A follower may, follow by follow, show the followed player their handle and profile link (`PUT /api/follows/share-back`, off by default; `GET /api/followers` lists those who do). `POST /api/bans` (`/api/bans/remove`, `GET /api/bans`) bars a player from the banner's profile pages (the player page and team pages, for a logged-in viewer: to them there is no such page; a viewer with no login can't be told apart, so the link still works for them). A ban does nothing in a game. It overrides the banned player's follow of the banner: the follow stays on their own list (they are not told) but counts for nothing (not in the follower count, never shared back), and it takes the share-back away. The directory is `GET /api/directory?prefix=...` (login, rate-limited): the players who opted in (`PUT /api/profile/directory`) whose handle starts with the prefix (case and spacing aside, at most 20, not the caller, not players who banned the caller), each with the handle, the bio, whether the caller follows them, and a profile link only when the player switched it on (`PUT /api/profile/directory-link`, off by default). Changes are rate-limited per account (`ratelimit.SOCIAL_BY_ACCOUNT`).
- **Fight tags and retention** (`terraforma.fighttags`). When a fight ends (in `store.apply_results`, once) it is scored for each player's team that won it: **overkill** is the team's overkill damage on killing blows over its PXP, and **underdog** is the PXP of the opposing parties over the PXP of the team's own party (`fighttags.scoring`, pure; a killing blow is credited to the fighter whose turn it is, on an enemy party, and a kill outside anyone's turn is credited to nobody; PXP is as the fighters stood when the fight ended). A team *won* when one of its heroes stands and every enemy party has gone (all down or fled). A fight is PvP for a team when an enemy party holds a player's team, else PvE, and each kind has both scores, so a team holds up to four tags (`pve_overkill`, `pve_underdog`, `pvp_overkill`, `pvp_underdog`): a fight takes a tag when its score beats the holder's (and is above nothing). `Rules.thrown_fight(fight)` (nothing is thrown by default; the coliseum will judge) keeps a PvP fight from taking any PvP tag or alliance place. An alliance lists the best `Rules.alliance_top_size` (10) fights of each kind among its teams', filled as fights end (a fight stays in the list when its team leaves, until it is bumped). A team keeps fights by hand in `Rules.team_retention_slots` (10) slots, and an alliance in `Rules.alliance_retention_slots` (50), a fight a member team was in; it stays after that team leaves. Calls (login; CSRF token and a rate limit on changes): `GET /api/teams/{id}/fight-tags` (the owner: `tags`, `kept`, `slots`), `POST /api/teams/{id}/kept` and `.../kept/remove` (`{"fight_id": n}`, a finished fight the team was in), `GET /api/alliances/{id}/fight-tags` (the owners of its teams: `top` per kind, `kept`, sizes), `POST /api/alliances/{id}/kept` (`{"team_id", "fight_id"}`, a team of the caller's whose role may speak for the alliance) and `.../kept/remove`. A finished fight that no tag, list or slot holds is deleted by the housekeeping job `old_unkept_fights` `Rules.fight_keep_days` (30) days after it ended (0: kept for good), with its rounds and what belongs to it; a table that links to `fights` must be added to `fighttags.service` (a test says so). Housekeeping jobs now also take the game's `Rules` as a fourth argument.
- **Longer rounds.** A player who needs more time can choose a longer round (an accessibility setting): `GET /api/settings/round-time` (login) shows the choice, the round length it gives and what each option costs; `POST /api/settings/round-time` (login and CSRF token; the body is `{"multiplier": 1.5}`) chooses one. A game sets the choices and prices in `Rules.time_multipliers`, pairs of `(multiplier, bonus)`; DragonStar's are `1` for nothing, `1.5` for 5% and `2` for 10%, which is the default. The price is on the monsters: each gets that much more max HP (rounded up, in whole percents), so the fight is harder and pays more experience, since a monster's PXP follows its stats. A fight waits `Rules.round_length(multiplier)` for every round, with the longest multiplier anyone in it asked for (`fights.timing.fight_multiplier`), fixed when it starts; a choice counts for fights started after it. A server-started fight reads the team owner's choice; a game that starts fights with several players calls `timing.multiplier_for`, `fight_multiplier` and `toughen` the same way (a player on the monsters' side pays nothing: they are not the ones the monsters are made tougher for).
- **The timer.** The server looks for overdue rounds every `fight_timer_seconds` (settings, 1 by default; `live.resolve_overdue` does one pass).
- **The end.** The round that ends a fight saves its result to the heroes and pays its gold through the game's economy, once (`store.apply_results`), and the fight is finished.
- **Finding.** `GET /api/fights` (login; `?running=true` for the unfinished ones, `?limit=` 1 to 50, 20 by default) lists the caller's fights, running first then the most recent: the number (for the calls and the socket), the public name, the round it waits for, when it plays, and which of the caller's heroes are in it.
- **Looking.** `GET /api/fights/{id}` shows a fight to its players (who is standing with how much, which fighters are theirs and have committed, when the round plays, and the `vital` resource); `GET /api/fights/watch/{guid}` shows it to anyone logged in who knows its public name.
- **The socket.** `/ws/fights/{id}` (the Origin header must be the site's own, and a login) pushes `committed` (who has committed, never what), `party_joined` (a party joined: look at the fight again), then `round` (the round's events, whether the fight is over, and the next deadline). Only the fight's players may listen by its number; anyone logged in may with `?guid=`. The page only listens: commands go through the call.

## Databases

The engine is database-agnostic. Postgres is the primary database, MySQL is supported, and SQLite serves tests and development. To keep it that way:

1. Tables are SQLAlchemy models only, and Alembic writes the schema changes.
2. Only generic column types are used, never database-specific ones.
3. Structured data goes in JSON columns, never serialized language objects.
4. Anything that really differs between databases lives in `terraforma/db/dialect.py`, and nowhere else.
5. There is no raw SQL outside that module and the migrations.
6. Every database test runs on all three databases.

## Map-ready from the start

Maps (see Maps) and a changing world come later. The groundwork is there from the first commit:

- **Location.** Everything that exists somewhere has a map and a tile (`Located`).
- **Randomness.** All of it comes from the world's seed, through named streams (`WorldRng`), so worlds can be rebuilt and bugs replayed.
- **Time.** The world keeps its own clock, counted in ticks rather than wall time (`advance_clock`).
- **Checked input.** Map names and coordinates from the browser are validated like any other input (`Position`).

## Housekeeping

`terraforma.housekeeping` tidies up what has gone stale. The server runs every job each `housekeeping_seconds` (settings, 3600 by default, 0 for never; `housekeeping.run(sessionmaker, settings)` does one pass). A job is an async function `(session, now, settings)` registered with `@housekeeping.job` that returns how many rows it removed; each runs in its own transaction, and a failing job is logged without stopping the others. A job deletes only what nothing reads any more, so a repeat or a second server is harmless. Today: `old_voice_rooms` closes voice rooms (see Voice). `old_chat_messages` removes chat messages older than `chat_retention_days` (see Chat). `finished_rate_limit_windows` removes rate-limit counters whose window is over (a subject that never returns would keep its row otherwise). `old_closed_ballots` and `old_settled_rating_prompts` remove closed ballots (with their votes) and answered or dismissed rating prompts older than `ballot_retention_days` and `rating_prompt_retention_days`; both default to 0, which keeps them for good, so a game opts in through `settings.toml`. A pending prompt is never removed. `stale_pending_drops` settles a pending drop (see Held drops) that has waited longer than `pending_drop_timeout_seconds` (settings, 0 by default: it waits for ever): a need/want drop with the answers so far (hold-outs count as passing), a hand-out nobody made as `unclaimed`. `ended_standing_statuses` removes standing statuses whose end time has passed. `expired_remembered_browsers` and `unconfirmed_security_keys` tidy second-factor leftovers (see Second factors). Games cannot add jobs yet.
