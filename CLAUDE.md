# Working on TerraForma

- The engine's name is TerraForma (the TerraForma RPG Engine). "TerraFroma" is a common typo for it: always correct it.
- Mike runs the tests for validation. Write tests with every change, run them where you can, and say which ones you ran. The full suite runs with `docker compose run --rm test`.
- This is the public engine (AGPL-3.0 plus the module permission in LICENSE-EXCEPTION.md). Never add game content, secrets or anything from the private Vanguard Tavern repo here. The engine runs in Docker; games deploy it (Vanguard Tavern on a QNAP NAS). Settings come from `settings.toml`, never from environment variables. The only exception is `TERRAFORMA_TEST_DATABASES` for the test runner.
- The target is Python 3.14.
- No warnings: keep builds, tests and CI free of deprecation and other warnings. Mike treats visual noise as something that hides real problems, so fix a warning rather than tolerate it.
- The engine never imports a game. Games plug in through the public interfaces (Game, create_app, seed formats, terraforma.testing): changing those is a change to what the license exception covers, so keep them deliberate and documented.
- Database-agnostic: follow the rules in README.md. Database-specific code goes only in `terraforma/db/dialect.py`. Every database test must pass on SQLite, Postgres and MySQL.
- Map-ready: new things that exist somewhere get a location. Randomness comes from `WorldRng` streams, never the `random` module. Time comes from the world clock.
- Every server call is its own route, with a strict Pydantic model for its arguments. Calls that change something depend on `ActingAccount` (login plus CSRF token); calls that only read use `CurrentAccount`. The fight WebSocket checks the Origin header.
- Security rules carried from DragonStar:
  - Passwords use Argon2id.
  - An email change needs an OTP (when 2FA is on) or an email link, never the password.
  - Changes to 2FA are confirmed by a link.
  - Logs are scrubbed.
  - Logins and sensitive calls are rate-limited.
  - Encryption keys have two slots.
  - A player's public handle can't match their username or email.
  - Admins earn tokens only when fighting as a player.
- Any asset in this repo (art, sound, music, fonts) must be legally usable and compatible with a public repo: Mike's own, or openly licensed (CC0, CC-BY with credit). Record each asset's source and license beside it, and never add one whose license is unknown. Nothing from DragonStar's assets.
- The browser code ported from DragonStar gets no feature work until DragonStar's features are ported. Fixes needed for the new server are fine.
- The plan lives in the TerraForma plan doc. Work goes on branches with pull requests; tag releases (v0.x.y) for games to depend on.

They share the models module and the migration chain, so they run in order, one pull request each. Each takes the next free migration number when its branch is cut.
   - **5a. Content models and seed loading** (done: engine PR from branch `content-models`, migration 0005): models for abilities, items, jobs, monsters and personalities; strict Pydantic checks of each seed file (`seed.py`); an idempotent load into the database at startup (`db.dialect.upsert`), so a game's seed is data the engine understands. The seed file formats are a public interface (the license exception covers them): document them in the README. Unblocks the game module loading real content.
   - **5b. Heroes and teams** (done: engine PR from branch `heroes-teams`, migration 0006, stacked on 5a): a hero belongs to an account (a job, stats, a location), a team groups heroes; calls to create, list and rename them, with limits per account.
   - **5b2. Inventory, equipment and abilities for heroes** (done: engine PR from branch `inventory`, migration 0007): heroes get what DragonStar's heroes have, adapted to this framework (read `include/hero.php`, `character.php`, `item.php` in the private repo for the concepts; write fresh code): an inventory of items with counts, equipment slots (the slot names come from items' `equip_slots`), the abilities a hero knows (from the job), and gold. Calls to equip, unequip and list; limits and rules as DragonStar has them. Needed before fights can use a hero's weapon and spells.
   - **5c-a. Rules framework and pure resolution** (done: engine PR from branch `fight-rules`, no migration; everything after it waits for this): carries DragonStar's rules over as the engine's defaults, "the process mirrored, functionally equivalent" (the format may differ). Pure code, no database or web, heavily unit-tested.
     - Rounds: every combatant commits a command (attack left or right hand, item, equip, skill, spell, defend, run), then the round resolves in one pass. Order is by Speed randomised +-15%, spell casting slowed by Focus against MP cost, multi-attack weapons appear several times, ties shuffled. Hit roll `1..Accuracy+Dodge` (a roll of 1 is a critical that doubles Strength); damage from Strength against Block scaled by roll quality, halved when defending, minimum 1; harmful skills can be dodged; harmful spells get a Power against Resistance saving throw (none, half, full). Same rules, same numbers.
     - Randomness: a named `WorldRng` stream per map (`stream("map", name)`), and each fight draws from its own stream under it (`stream("map", name, "fight", id)`), so any fight replays exactly. Never the `random` module.
     - Events are typed (DragonStar's `FightAction` messages: Turn, Target, Damage, Miss, Died, Restore, AlterStat, UseItem, ...) and the fight state is the fold of them, so spectators and replays work.
     - Pure functions for order, hit, damage, saving throw and effects; combatant and event types; party, group and character addressing as `FighterRef` already has. (The tables come in 5c-b.)
     - **The framework a game overrides** (the public interface; document it): a `Rules` base class holding the formulas (speed, chance to hit, damage, saving throw, effects), the stat list, and the *resource* list. Resources are the pools like HP and MP; a game can define others (rage, technique points) with their own maximum, gain and spend rules; HP-style death at zero stays the default. Seed checking takes its stat names from the game's rules instead of a fixed list. Advancement is a hook as well (`on_fight_end` and friends), with level-based advancement as the default implementation, so a game can later grant stat bonuses for performance or sell abilities for an experience currency. Build only what is there now (the DragonStar behaviour), shaped so those additions don't need a rewrite; if one is cheap, include it.
   - **5c-b. Fight persistence** (done: engine PR from branch `fight-persistence`, migration 0008, stacked on 5c-a; can run beside 5c4): fight, participant and action tables; the append-only event log, one row per action with a sequence number, each row storing a hash of the previous one (a plain hash chain: tamper-evident and cheap, not a blockchain, because the server is the only authority and there is nothing to agree on); replaying a fight from its log and seed; the per-map and per-fight `WorldRng` streams wired in.
   - **5c2. Statuses** (needs 5c-a; adds a content kind, so a migration; don't run beside 5c-b, which touches the same persistence): a content kind (`statuses.json`, a public seed format) and a token on a combatant. Two mechanisms, both supported: (1) *status tokens* that process at their own times (start or end of round, start or end of every turn or the nth turn, when helped, when harmed, on a saving throw, ...) and can do damage, skip turns, modify damage by element and so on, with an optional duration and an intensity that is a function of the time left (rising, falling or flat); (2) *direct stat adjustment*, where the current value of a non-resource stat moves and drifts back to its base over time. Event types for each, so the log still replays.
   - **5c3. Experience and rewards** (needs 5c-b, since it writes to the event log; can run beside 5c2): DragonStar's experience tree (who earned what from whom, the debts and credits, distribution when a party leaves or wins), gold and drops at a fight's end, written to the event log, with advancement going through the rules framework's hook.
   - **5c4. Monster AI** (needs 5c-a only, since it picks commands from combatant state with no database; can run beside 5c-b and 5c2): how monsters (and NPCs) choose a command each round, from the `ai` fields the monster seed has (action, goal, target, experience) and DragonStar's AI process; draws only from the fight's stream so fights still replay.
   - **5d. Fights live** (needs 5c-a, 5c-b and 5c4; 5c3 for rewards; statuses are optional): the command call stops being a stub and feeds the engine; the WebSocket pushes real events; the round timer runs on the clock. Admins earn tokens only when fighting as a player.
   - **5e. Maps and movement** (not before the map generator and editors exist, so parked): map tiles, a move call (wrapping maps included), heroes and monsters placed on maps. Independent of 5c and 5d except for the migration number, so it can run beside them.
   - **5f. Parties** (needs 5b; a migration; map-free, so it can run beside 5c2; the map's interactions that form and merge parties are 5e): a *party* is a collection of characters made of **whole teams**. A team is never split: if a team joins a party, everyone on it must have a place in that party, and a team is in at most one party. The smallest party is one team (a team with no stored party counts as a party of one). Parties merge into bigger ones, and a whole team can leave one; DragonStar allowed several teams in a party mainly to try the system out, and the map will let players merge their parties. The size of a party is the game's to set (a rule on `Rules`, defaulting to DragonStar's: four groups of five, room for 20). Tables for the party and its teams (a team can be in only one party); service functions to put a team in a party, merge two parties and take a team out, each refusing when a whole team would not fit (no calls yet: the map and live fights use them); a fight's side is built from a party, all its teams reaching `fights.fight.Party.teams`.
   - **5g. Economy: wallets and trading** (needs 5f; finishes 5c3's gold): the game decides, through `Game(economy=...)`, an overridable `Economy` class like `Rules`.
     - **5g-a. Gold:** where gold lives is the game's choice. The engine supports gold on the team (a `Team.gold` column, DragonStar's way, and the default) and on the hero (already there), and a game can use both; `Economy` routes each kind of income and says which wallet a spender uses. `store.apply_results` credits the fight's `Gold` events through it, once (it records that a fight's gold was paid). Mike's game keeps gold on the team.
     - **5g-b. Trading:** `Economy.can_trade(giver, receiver, what)` says whether an item stack or some gold may go from one hero to another, with a reason when not; `what` also covers auction listings later, so a game can say "use the auction house". Stock policies a game can pick or build on: within a team (the default), within a party, anyone, nobody; a game that lets players trade with parties they interact with supplies the relationship through the hook (the engine has no alliance model). The service moves items and gold atomically after asking, writes a ledger of every trade, and the calls (give an item, give gold) are rate-limited and need login and the CSRF token; the hook is told who is asking, and a hero should only be reachable by those who may trade with it. Mike's game: trading only within a team, otherwise an auction house if one is added. The auction house itself is not planned yet.
   The game module can start on its seed files, assets and rules settings right after the v0.2.0 release; loading them works since 5a, playing them waits for 5c to 5d.
   **Order and what can run side by side** (everything after 5c-a plugs into its combatant, event and `Rules` interfaces, so it comes first and alone): 5c-a; then 5c-b beside 5c4; then 5c2 beside 5c3; then 5d. Parallel runs save time, not credits, and each costs its own session plus the rebase and a fresh test run, so run two at a time at most. Each takes the next free migration number when its branch is cut and rebases before its pull request.
